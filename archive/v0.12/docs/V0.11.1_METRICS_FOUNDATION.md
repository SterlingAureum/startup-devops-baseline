# v0.11.1 Metrics Foundation

## Outcome

v0.11.1 replaces the active hand-written local Prometheus Deployment with an
operator-managed metrics foundation and adds the same bounded shape to the
AWS dev, test, and production declarations. The version pins
`kube-prometheus-stack` `88.5.0`; it does not follow a floating latest release.

The active metrics components are Prometheus Operator, Prometheus,
kube-state-metrics, node-exporter, and their CRDs. Grafana, Alertmanager,
default alert rules, Loki, Alloy, tracing, Thanos, and remote write remain
disabled or absent until their planned increments.

The machine-readable contract is:

```text
delivery/contracts/v0.11.1-metrics-foundation.json
```

Run the offline gate with:

```bash
./scripts/validate-v0.11.1-metrics-foundation.sh
```

## Deployment Shape

Each cluster owns one independent `observability-metrics` Helm release in the
`observability` Namespace. Metrics do not cross environment boundaries and no
central Thanos, Mimir, AMP, or remote-write backend is introduced.

The Prometheus endpoint is cluster-only:

```text
http://observability-metrics-prometheus.observability.svc.cluster.local:9090
```

No observability Ingress, LoadBalancer, or NodePort is created. Operators use
`kubectl port-forward` for temporary access.

## Environment Profiles

| Environment | Retention | Size limit | Storage | Claim |
| --- | ---: | ---: | ---: | --- |
| local | 6h | 2GiB | bounded `emptyDir` | functional only |
| aws-dev | 24h | 8GiB | encrypted 10Gi gp3 | development qualification |
| aws-test | 48h | 8GiB | encrypted 10Gi gp3 | controlled validation |
| aws-prod | 7d | 16GiB | encrypted 20Gi gp3 | requires live v0.11 acceptance |

The AWS StorageClass uses `ebs.csi.aws.com`, `WaitForFirstConsumer`, expansion,
and `Delete` reclaim behavior. CSI volumes receive `Project`, `Environment`,
and `Component` tags so the existing residual-cost audit can find them.

## Scheduling

On AWS, Prometheus Operator, Prometheus, kube-state-metrics, and the webhook
patch job select `workload=system`. node-exporter tolerates all worker taints so
it can run on system, application, and database nodes. A dedicated
observability NodePool is not required for the current bounded stack.

The local profile omits the AWS-only node selector because kind nodes do not
carry `workload=system`.

## Application Compatibility

The Chart creates one compatibility ServiceMonitor in `observability`. It
selects the existing demo-api Services in `startup-apps`, scrapes the named
`http` port at `/metrics`, and rewrites `job` from the Kubernetes Service name.
This preserves all current shapes:

```text
demo-api
demo-api-stable
demo-api-canary
```

Therefore the existing local Rollout query remains valid:

```promql
sum(up{job="demo-api-canary"})
```

v0.11.2 will move application telemetry ownership into the application Chart
and add stable release-correlation dimensions. v0.11.1 deliberately preserves
only the current compatibility contract.

The AWS `startup-apps` default-deny policy now explicitly allows Prometheus
Pods from `observability` to reach demo-api port `8080`.

## Local Migration

The active `monitoring` Argo CD Application keeps its Application name but
changes its source to the pinned Helm Chart and its destination to
`observability`. The historical manifests remain under:

```text
platform/monitoring/prometheus
```

No active Application references that directory after this increment. It is
retained as historical material instead of being silently presented as the
production-oriented stack.

Because this is a local disposable environment, the single-Application
cutover may contain a short metrics gap while Argo CD prunes the old
`monitoring` resources and creates the new release. It does not claim a
zero-downtime production migration.

After the merge, sync the root Application and confirm the new child:

```bash
kubectl -n argocd get application monitoring
kubectl -n observability get pods
kubectl -n observability get service observability-metrics-prometheus
```

If the legacy Namespace remains after the new release is Healthy, confirm no
active Application references it before removing it:

```bash
kubectl -n argocd get applications -o yaml | grep -F 'platform/monitoring/prometheus' || true
kubectl get all -n monitoring
```

## Local Live Validation

Generate traffic first:

```bash
for path in health ready version metrics; do
  curl -fsS -H 'Host: demo-api.local' "http://localhost/${path}" >/dev/null
done
```

In one terminal:

```bash
kubectl -n observability port-forward \
  svc/observability-metrics-prometheus 19090:9090
```

In another terminal:

```bash
curl -fsS http://127.0.0.1:19090/-/ready
curl -fsS --get http://127.0.0.1:19090/api/v1/query \
  --data-urlencode 'query=demo_api_requests_total'
curl -fsS --get http://127.0.0.1:19090/api/v1/query \
  --data-urlencode 'query=sum(up{job="demo-api-stable"})'
curl -fsS --get http://127.0.0.1:19090/api/v1/query \
  --data-urlencode 'query=sum(up{job="demo-api-canary"})'
```

The repository helper performs the readiness and non-empty metric query:

```bash
./scripts/check-monitoring.sh
```

Finally trigger a normal local Canary revision and confirm its AnalysisRun
passes without changing the PromQL contract.

## AWS Validation Boundary

AWS desired state is included now, but the contract does not claim live AWS
evidence. On the next aws-dev rebuild, verify:

```bash
kubectl -n observability get pods -o wide
kubectl -n observability get pvc
kubectl get storageclass gp3-observability -o yaml
```

Prometheus must run on a system node, the PVC must bind to an encrypted gp3
volume, application and cluster targets must be up, and only port-forward
access may exist. After destroying a disposable dev or test environment, run:

```bash
AWS_ENVIRONMENT=aws-dev ./scripts/validate-aws-cost-cleanup.sh
```

The audit must report zero tagged EBS volumes.

## Explicit Deferrals

This increment does not add dashboards, recording rules, alert routing,
structured-log collection, distributed tracing, SLOs, or SLI-based rollout
gates. It also changes no v0.10 release orchestration, production approval,
automatic merge, automatic environment creation, or rollback boundary.
