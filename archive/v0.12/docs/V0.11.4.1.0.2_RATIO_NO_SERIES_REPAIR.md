# v0.11.4.1.0.2 Ratio No-Series Repair

## Goal

Return bounded success-ratio series when a workload has observed traffic but
the optional numerator label set has never been created. Preserve no-data when
the workload or target itself is absent.

## Incident

The local observability acceptance generated successful `/health` and `/ready`
requests. `demo_api:http_requests:rate5m` therefore existed, but no request had
created a `status_class="5xx"` counter series. The error recording rule was
empty, and PromQL propagated that empty vector through the success-ratio
division. Additional warm-up could not create a `5xx` label set.

The dependency ratio had the symmetric failure mode: an observed dependency
with failures but no success series could disappear instead of returning zero.

## Bounded repair

The HTTP rule fills a missing error numerator only for label sets already
present in the request-rate rule:

```promql
demo_api:http_errors:rate5m
or
0 * demo_api:http_requests:rate5m
```

The dependency rule uses the same pattern, anchored to the aggregated total of
`success|failure` outcomes. It does not create a series when no dependency
checks exist.

The repair deliberately does not use a global fallback:

```promql
or vector(0)
```

A global zero could turn a missing scrape target or inactive workload into an
apparently healthy result. Request-anchored zero fill has these semantics:

| Source state | HTTP success ratio | Dependency success ratio |
| --- | --- | --- |
| Traffic/checks and no errors/failures | `1` | `1` |
| Traffic and some errors | Calculated | Calculated |
| Checks with failures and no success series | Not applicable | `0` |
| No traffic/checks or missing target | No series | No series |

## Diagnostics

When a ratio is unexpectedly empty, the local acceptance script prints the
cardinality of its input recording rules. Warm-up is suggested only when the
source rate is also empty. A present source rate with a missing ratio indicates
a recording-rule mismatch rather than insufficient waiting.

## Grafana ReplicaSet boundary

This repair does not change Grafana Deployment history. An old Grafana
ReplicaSet with zero desired, current, and ready replicas is a normal rollback
record and should not be manually deleted for acceptance.

## Acceptance

After the feature commit is pushed and deployed through the local feature
GitOps workflow, run:

```bash
./scripts/validate-v0.11.4.1.0.2-ratio-no-series-repair.sh
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-controller-metrics.sh
```

The live observability check must reach its final Grafana and Dashboard success
message without requiring synthetic `5xx` traffic.

## Boundary

This repair changes two recording-rule expressions, Chart metadata, validation,
and documentation. It adds no recording-rule name, Dashboard, alert, component
upgrade, Grafana Deployment setting, ReplicaSet cleanup, AWS desired state, or
production automation.
