# v0.11.4.1.0 Controller Metrics Discovery

## Goal

v0.11.4.1.0 establishes the verified metric inputs for the later Delivery,
Data, and Platform Dashboards. It enables controller metric Services where
required, adds repository-owned ServiceMonitor and PodMonitor resources, and
provides stable diagnostic recording rules. It does not add the three final
Dashboards; those remain the next v0.11.4.1.1 increment.

The machine-readable contract is:

```text
delivery/contracts/v0.11.4.1.0-controller-metrics-discovery.json
```

## Version Contract

The monitored controller surface is version-specific:

| Component | Version boundary | Verified metric boundary |
| --- | --- | --- |
| Argo CD | observed semantic version; existing install boundary retained | `argocd_app_info` on `argocd-metrics:8082` |
| Argo Rollouts | Chart `2.41.1`, application `v1.9.1` | phase, replica, and reconciliation metrics on port `8090` |
| CloudNativePG | Chart `0.29.0`, application `1.30.0` | instance exporter on port `9187`; AWS profiles only |
| kube-prometheus-stack | Chart `88.5.0` | kube-state-metrics and Prometheus target health |

The Argo Rollouts Chart advances from `2.41.0` to `2.41.1` so its pinned
application version is `v1.9.1`.

This increment deliberately does not upgrade Argo CD. The local baseline still
uses Kubernetes 1.30, while current Argo CD 3.5 releases are tested against
newer Kubernetes versions. A control-plane compatibility upgrade is outside a
controller-metric discovery change. Live acceptance instead requires the
installed Argo CD controller image to carry a semantic version, prints that
observed image, and verifies its required metric. Operators may set
`EXPECTED_ARGOCD_VERSION` to require an exact already-approved version.

## Discovery Ownership

The external Charts own their controller Deployments and metric Services. The
repository-owned `platform/observability/helm` Chart owns cross-namespace
discovery:

- `ServiceMonitor/argocd-application-controller` selects the Argo CD
  application-controller metrics Service;
- `ServiceMonitor/argo-rollouts-controller` selects the Argo Rollouts metrics
  Service;
- `PodMonitor/cloudnative-pg-operator` discovers the AWS operator Pods;
- `PodMonitor/cloudnative-pg-cluster` discovers the three AWS PostgreSQL
  instances.

CloudNativePG exports its database-cluster identity in a label named
`cluster`. Prometheus also uses the external `cluster` label for Kubernetes
cluster identity. The PodMonitor copies the exporter value to `cnpg_cluster`
and removes the original metric label before ingestion, preserving both
identities without an ambiguous collision.

## Recording Rules

Twenty-one rules are divided into three groups:

- `delivery:` summarizes Argo CD sync/health and Argo Rollouts phase and
  reconciliation activity;
- `data:` summarizes demo-api dependency outcomes and the bounded
  CloudNativePG health metrics available in AWS;
- `platform:` summarizes Deployment readiness, unavailable replicas,
  container restarts, and Prometheus target health.

Missing raw series remain missing. The rules do not use `or vector(0)`, do not
turn an absent target into a healthy target, and contain no alert definitions.
Pod names and UIDs are not retained in the recording-rule output.

## Offline Validation

Run:

```bash
./scripts/validate-v0.11.4.1.0-controller-metrics-discovery.sh
./scripts/validate-ci-quality-gates.sh
```

The complete quality gate requires the repository's pinned Helm and Docker
toolchain. The focused validator checks the immutable versions, monitor
selectors and endpoints, recording-rule names, local/AWS profile boundary,
predecessor-validator compatibility, documentation ownership, and negative
contract mutations.

## Local Live Acceptance

Push the accepted feature commit, deploy the feature revision, complete the
normal demo-api Canary flow, and run the existing v0.11.4.0 acceptance first:

```bash
./scripts/check-observability-views.sh
```

Then run:

```bash
PROFILE=local ./scripts/check-controller-metrics.sh
```

The script requires:

1. a semantic-versioned Argo CD image and the Argo Rollouts `v1.9.1` image;
2. Healthy Argo CD Applications and repository-owned monitor resources;
3. active Prometheus targets on the expected controller ports;
4. the required raw metric names;
5. all twenty-one recording rules loaded exactly once;
6. non-empty Delivery, Data dependency, and Platform rule results.

To require an exact already-approved Argo CD version, run:

```bash
EXPECTED_ARGOCD_VERSION=vX.Y.Z \
  PROFILE=local ./scripts/check-controller-metrics.sh
```

Do not introduce an Argo CD control-plane upgrade merely to satisfy this
increment. Kubernetes and Argo CD compatibility must be planned and accepted
as a separate change.

## AWS Boundary

AWS observability views additionally enable the two CloudNativePG PodMonitors.
When an AWS environment is created later, run:

```bash
PROFILE=aws ./scripts/check-controller-metrics.sh
```

That mode additionally requires the CloudNativePG `1.30.0` operator image,
active operator and instance targets, all four bounded `cnpg_collector_*`
metrics, and non-empty PostgreSQL recording rules. Formal dev/test/prod
observability evidence remains v0.11.8 work.

## Deferred

v0.11.4.1.0 does not add Delivery, Data, or Platform Dashboards, alerts,
Alertmanager, SLOs, burn rates, centralized logs, tracing, cloud billing, or a
new Rollout Analysis gate. Dashboard construction continues in v0.11.4.1.1;
capacity, resource efficiency, and conditional no-data presentation remain
v0.11.4.2.
