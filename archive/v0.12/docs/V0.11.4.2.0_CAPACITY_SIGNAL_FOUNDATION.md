# v0.11.4.2.0 Capacity Signal Foundation

## Goal

Establish stable capacity and resource-efficiency recording rules before a
Capacity Dashboard is created. The signals answer how much Kubernetes
allocatable capacity exists, how much is reserved by active workloads, how
namespace usage compares with requests, and whether active containers omit
CPU or memory requests.

This is an observability increment. It does not make an autoscaling,
scheduling, cost, or release decision.

## Existing source ownership

The increment reuses the kube-prometheus-stack core targets accepted in
v0.11.1 and v0.11.2:

| Source | Metrics used | Purpose |
| --- | --- | --- |
| kube-state-metrics | `kube_node_status_allocatable` | Node CPU, memory, and Pod allocatable capacity |
| kube-state-metrics | `kube_pod_status_phase` and `kube_pod_container_info` | Active Pod and container inventory |
| kube-state-metrics | `kube_pod_container_resource_requests` and `kube_pod_container_resource_limits` | Container reservation proxies |
| kubelet/cAdvisor | `container_cpu_usage_seconds_total` | Namespace CPU usage rate |
| kubelet/cAdvisor | `container_memory_working_set_bytes` | Namespace memory working set |

No ServiceMonitor, PodMonitor, exporter, kube-prometheus-stack value, or
component version is added or changed.

## Recording-rule ownership

The observability views Chart owns a separate resource:

```text
PrometheusRule/capacity-efficiency-recording-rules
```

Its source is:

```text
platform/observability/helm/templates/capacity-recording-rules.yaml
```

The Capacity group records cluster-level allocatable CPU, memory, and Pod
capacity; active Pod count; active container requests and limits; and bounded
request-to-allocatable ratios.

The Efficiency group records namespace requests, actual CPU and memory usage,
usage-to-request ratios, active container count, and active containers without
positive CPU or memory requests.

## Semantics and limitations

`Pending` and `Running` Pods are active for requests and limits. This excludes
completed Pods from reservation totals while retaining pending demand.

Container request sums are a stable reservation proxy, not an exact scheduler
fit calculation. They do not model Pod overhead, init-container maximums,
topology constraints, fragmentation, taints, or instance launch latency. The
future Dashboard must label them accordingly.

CPU usage is a five-minute rate. Memory usage is working set, not RSS or
requested memory. A namespace usage-to-request ratio exists only when its
request total is positive.

Missing-request counts use the real active-container set as their zero anchor.
When active containers exist and all have positive requests, the result is a
scoped zero for that namespace. When the source inventory is absent, no series
is created. A global `or vector(0)` fallback is forbidden.

## Live discovery

After committing, pushing, and deploying the exact feature revision, run:

```bash
./scripts/check-monitoring.sh
PROFILE=local ./scripts/check-capacity-signals.sh
```

The capacity check verifies:

1. the monitoring and observability Applications are Synced and Healthy;
2. the new PrometheusRule is present;
3. every required source metric name and representative source series exists;
4. all twenty recording rules are loaded;
5. required capacity and namespace rule results exist and ratios are finite;
6. `startup-apps` has an active-container request-coverage result, including a
   legitimate scoped zero when every active container is covered.

The AWS profile is available for an already-running environment:

```bash
PROFILE=aws AWS_ENVIRONMENT=aws-dev \
  ./scripts/check-capacity-signals.sh
```

The script does not create an AWS environment or write to production. Formal
AWS evidence remains v0.11.8 work.

## Dashboard and clean-replay boundary

No Dashboard is added or changed in this increment. The immutable Capacity and
Resource Efficiency Dashboard is v0.11.4.2.1 work and must query these accepted
rules instead of raw kube-state-metrics or cAdvisor series.

The clean local GitOps replay closes v0.11.4.2 after the Dashboard exists. It
is not claimed by this signal-foundation increment.

## Cost boundary

Requests, limits, and usage can reveal waste risk, but they are not currency
cost. This increment adds no Kubecost, AWS Billing, CloudWatch cost query,
chargeback model, price table, or savings claim.
