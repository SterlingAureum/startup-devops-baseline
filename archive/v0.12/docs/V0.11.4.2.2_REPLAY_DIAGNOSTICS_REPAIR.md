# v0.11.4.2.2 Replay Diagnostics Repair

## Purpose

Repair the local observability acceptance path after clean replay exposed a
false-positive target-discovery message and an insufficiently explicit image
transition between the neutral feature baseline and the exact feature
acceptance state.

This repair changes validation scripts, contracts, and documentation only. It
does not change a Kubernetes resource, Dashboard, recording rule,
ServiceMonitor, application image, Canary step, AWS desired state, or
production automation.

## Observed failure

After the neutral feature baseline was restored, capacity signals and all five
Grafana Dashboards remained healthy while these application signals were
absent:

```text
demo_api_http_requests_total
demo_api:http_requests:rate5m
data:demo_api_dependency_checks:rate5m
```

The old monitoring check reported the stable and Canary jobs as discovered
because its query required a non-empty `sum(up{...})` result but did not require
the numeric value to be positive. A discovered target with `up=0` therefore
looked successful, and the later rule checks reported only the downstream
no-series symptom.

The neutral feature baseline deliberately removes the four local-image Helm
parameters. It is a clean replay start state, not an observability acceptance
state. Rebuilding and loading a fresh local image tag and redeploying the exact
feature revision restored the application telemetry.

## Repair

`scripts/lib/observability-live.sh` now provides one shared implementation for:

- bounded `/health` and `/ready` traffic;
- direct `/metrics` preflight for populated HTTP and dependency telemetry;
- current Rollout image, Git revision, and Helm-parameter diagnostics;
- a numeric `min(up{job="..."}) >= 1` requirement;
- active-target diagnostics containing `health`, `scrapeUrl`, `lastError`, and
  `lastScrape`.

The monitoring, service-view, controller-metric, and operator-Dashboard live
checks use the shared implementation. No check converts absent telemetry into
a healthy zero.

## Required clean replay

Use a new local image tag for the replay so Kubernetes receives a changed Pod
template and cannot reuse an ambiguous mutable tag.

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
  ./scripts/restore-local-feature-baseline.sh

IMAGE_TAG=v0.11.4.2.2-replay-local \
  ./scripts/build-load-demo-api-image.sh

TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_TAG=v0.11.4.2.2-replay-local \
  ./scripts/deploy-local-feature-gitops.sh
```

Complete any intentional manual Canary pause, then run:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-controller-metrics.sh
PROFILE=local ./scripts/check-operator-dashboards.sh
PROFILE=local ./scripts/check-capacity-signals.sh
PROFILE=local ./scripts/check-capacity-dashboard.sh
```

After evidence is collected, return to the neutral pre-merge feature baseline:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
  ./scripts/restore-local-feature-baseline.sh
```

Do not run `restore-local-gitops-head.sh` before this feature reaches the
stable branch.

If the kind cluster name differs from `startup-devops-baseline`, provide the
same `CLUSTER_NAME` to `build-load-demo-api-image.sh` that was used when the
cluster was created.

## Acceptance

The repair is accepted when:

1. the offline repair validator and complete quality gate pass;
2. a synthetic target with `up=0` is rejected and its `lastError` is printed;
3. direct image telemetry preflight succeeds before Prometheus rule checks;
4. the exact feature image is active after neutral-baseline restoration;
5. the full monitoring, Dashboard, controller, capacity, and efficiency suite
   passes from the clean replay;
6. the cluster is returned to the neutral feature baseline after evidence is
   collected.

Successful repair acceptance closes the local v0.11.4 Dashboard and recording-
rule phase. Formal AWS observability evidence remains v0.11.8 work.
