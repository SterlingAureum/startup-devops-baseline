# v0.11.5.0.1 Alertmanager Matcher Normalization Repair

## Purpose

The first v0.11.5.0 local live replay proved that Alertmanager was Ready and
that its active configuration contained the intended critical and warning
routes and inhibition matchers. The acceptance script nevertheless failed
because it compared one serialized matcher string byte for byte.

The repository declaration uses `severity = "critical"`. Alertmanager returns
the same matcher from `/api/v2/status` in canonical form as
`severity="critical"`. Whitespace around the equals sign is not part of the
matcher meaning.

## Repair

`scripts/check-alertmanager.sh` now validates severity matchers with optional
whitespace around the equals sign. It still requires exactly two critical and
two warning matcher lines:

1. one critical and one warning route matcher;
2. one critical source and one warning target inhibition matcher.

The check still requires the stable receiver, grouping, timing, and
`alert_family` markers and still rejects every external notification receiver.
If a severity count is wrong, it prints the observed matcher lines before
failing.

An offline fixture mode exercises the same function used by the live check.
Regression coverage accepts both the repository-spaced and
Alertmanager-canonical compact forms and rejects a configuration that contains
only the route matchers.

## Boundary

This repair changes validation code, a contract, and documentation only. It
does not change Alertmanager Helm values, routes, receivers, inhibition,
Kubernetes resources, storage, images, AWS desired state, or production
automation. It does not add an alert rule or external notification path.

No image build, kind image load, Argo CD deployment, Pod restart, or persistent
volume operation is required solely for this repair.

## Acceptance

Run the focused offline regression and the complete available quality gate:

```bash
./scripts/validate-v0.11.5.0.1-matcher-normalization-repair.sh
./scripts/validate-ci-quality-gates.sh
```

Because the already-deployed v0.11.5.0 runtime configuration was correct, run
the repaired live check directly against the existing local cluster:

```bash
REQUIRE_NO_ALERT_RULES=true ./scripts/check-alertmanager.sh
```

The check passes only when both route and inhibition severity matchers exist,
the private Alertmanager runtime is healthy, Prometheus discovers and scrapes
it, and the v0.11.5.0 no-alert-rule boundary remains true.

After it passes, continue any remaining v0.11.5.0 live acceptance commands
that have not already completed. A GitOps redeployment is unnecessary unless
the cluster itself has drifted for an independent reason.
