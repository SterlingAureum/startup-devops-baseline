# v0.11.5.1 Actionable Alerts and Runbooks

## Goal

v0.11.5.1 adds the first bounded, repository-owned alert inventory after the
accepted Alertmanager routing foundation. It deliberately contains eight
high-signal alerts instead of enabling the large kube-prometheus-stack default
rule set.

Every alert is backed only by recording rules accepted in v0.11.4, has stable
routing labels, and links to one version-controlled Runbook. The local clean
baseline must load all eight rules while keeping all of them inactive.

## Alert inventory

| Alert | Severity | Condition | For | Profile |
| --- | --- | --- | --- | --- |
| `DemoApiHttpSuccessRatioLowWarning` | warning | HTTP success ratio `< 0.99` with traffic | 10m | all |
| `DemoApiHttpSuccessRatioLowCritical` | critical | HTTP success ratio `< 0.95` with traffic | 5m | all |
| `DemoApiDependencySuccessRatioLowWarning` | warning | dependency success ratio `< 0.99` with checks | 10m | all |
| `DemoApiDependencySuccessRatioLowCritical` | critical | dependency success ratio `< 0.90` with checks | 5m | all |
| `ArgoRolloutProblem` | critical | problem-phase Rollout count `> 0` | 5m | all |
| `ArgoCDApplicationUnhealthy` | critical | unhealthy Application count `> 0` | 10m | all |
| `KubernetesDeploymentUnavailable` | critical | unavailable Deployment replicas `> 0` | 10m | all |
| `PostgreSQLCollectionFailed` | critical | CNPG collection error `> 0` | 5m | AWS; no-data local |

The HTTP and dependency warning/critical pairs use the same environment,
cluster, component, and alert-family labels. Therefore the v0.11.5.0
critical-over-warning inhibition rule applies only to the matching family.

No-data remains no-data. Application ratio alerts additionally require an
observed traffic or dependency-check rate. The local profile does not invent a
healthy or failing CloudNativePG value when PostgreSQL metrics are absent.

## Required labels and annotations

Every alert carries `severity`, `environment`, `cluster`, `component`, and
`alert_family`. Every alert also carries a summary, description, and stable
`runbook_url` targeting the main-branch Runbook path.

The feature-branch live replay validates the repository-relative Runbook file;
the public main-branch URL becomes canonical after merge.

## Runbook policy

There is one English Runbook per alert under `docs/runbooks/alerts`. Each starts
with read-only observation, preserves release and incident identity, avoids
printing secrets, and keeps production mutations behind the repository's
existing reviewed approval path.

The Runbooks do not authorize Pod, PVC, Cluster, ReplicaSet, or Secret deletion.
They do not turn a diagnostic observation into an automatic rollback,
switchover, restart, scaling action, or Promotion.

## Offline acceptance

Run:

```bash
./scripts/validate-v0.11.5.1-actionable-alerts-runbooks.sh
./scripts/validate-ci-quality-gates.sh
```

The focused validator enforces the exact inventory, thresholds, durations,
recording-rule sources, labels, annotations, Runbook mapping, Chart identity,
Alertmanager inhibition compatibility, and explicit scope boundaries.

## Local live acceptance

Commit and push the exact feature revision, then reconcile
`observability-views`. This increment changes no demo-api source or image. If
the existing local feature baseline already uses a valid telemetry-capable
image, preserve that image identity.

Run the preceding Alertmanager check without the old no-alert-rule flag, then
run the new live check:

```bash
./scripts/check-alertmanager.sh
PROFILE=local ./scripts/check-actionable-alerts.sh
```

The live check requires the monitoring and observability-views Applications to
be Synced and Healthy, the `actionable-alerts` PrometheusRule to exist, all
eight alert rules to be loaded exactly once with health `ok`, all required
labels and annotations to be present, and every clean-baseline alert to remain
inactive.

If an alert is pending or firing, acceptance stops. Follow its Runbook and fix
or explicitly explain the unhealthy baseline; do not weaken or silence the
rule merely to pass acceptance.

## Deferred drills

v0.11.5.1 does not claim that a real notification was delivered. The bounded
firing, severity routing, critical-over-warning inhibition, resolution, and
environment-owned notification-path drills remain v0.11.5.2 work. Formal AWS
dev/test/prod evidence remains v0.11.8 work.

## Semantic-repair successor

v0.11.5.1.1 preserves this accepted eight-alert contract and repairs
`platform:prometheus_targets_down:count` before adding it as the source of the
ninth alert, `PrometheusTargetDown`. See
`docs/V0.11.5.1.1_PROMETHEUS_TARGET_DOWN_SEMANTICS_REPAIR.md` for the Boolean
counting and live cross-check acceptance contract.

## Explicit exclusions

This increment adds no default alert rules, external receiver, notification
credential, Dashboard, recording rule, monitor, application metric, image,
Alertmanager route, SLO, burn-rate expression, Rollout Analysis gate, automatic
rollback, AWS mutation, or production write.
