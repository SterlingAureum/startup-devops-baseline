# v0.11.6.1.1.1 Alloy RBAC Rendering and Historical Validator Repair

## Purpose

The v0.11.6.1.1 static contract checks passed, but the pinned Alloy `1.11.0`
Chart failed before producing Kubernetes manifests. The same quality-gate run
also showed that the historical v0.11.2 validator still required the demo-api
Chart identity that existed before the accepted structured-logging successor.

This repair corrects both failures without changing the intended logging
architecture or application runtime.

## Incident

The Alloy values supplied a non-empty `rbac.rules` list and an explicitly empty
`rbac.clusterRules` list. The Chart template serializes both fields when either
one is non-empty. Serializing the empty list immediately after the non-empty
list produced invalid YAML in `alloy/templates/rbac.yaml`.

The complete quality gate then failed independently because the v0.11.2 and
v0.11.3.2 historical validators required demo-api Chart `0.5.1` and application
version `0.3.0`. v0.11.6.1.0 intentionally advanced those identities to Chart
`0.6.0` and application version `0.4.0`.

Repair regression exposed one additional masked incompatibility: the
v0.11.4.0.1 fake Helm successor fixture did not emit the two logging
Applications now required by the v0.11.3.4 renderer validator.

No local logging workload acceptance was reached by the failed run.

## Repair

Alloy keeps exactly the same least-privilege resource inventory:

```text
namespaces
pods
pods/log
```

The permissions remain read-only:

```text
get
list
watch
```

The resources are divided between two non-empty Chart values lists. They are
still concatenated into one ClusterRole by the pinned Chart; the split exists
only to avoid the Chart's invalid empty-list rendering path.

The v0.11.2 and v0.11.3.2 validators now use the presence of the authoritative
v0.11.6.1.0 structured-logging contract to select the accepted successor Chart
identity. Their historical behavior remains unchanged when that successor
contract is absent.

The v0.11.4.0.1 fake Helm fixture now adds the pinned logging Applications only
when the v0.11.6.1.1 logging contract exists. Its historical six-child fixture
and contract remain unchanged before that successor.

The v0.11.6.1.1 validator now rejects empty `rules` or `clusterRules` values and
checks the exact rendered ClusterRole resource inventory after real Helm
rendering.

## Unchanged Boundary

This repair does not change:

- the local platform Chart `0.5.0` / application version `v0.11.6.1.1`;
- Loki Chart `18.11.3`, Loki `3.7.6`, or any Loki value;
- Alloy Chart `1.11.0`, Alloy `1.18.0`, the DaemonSet, or the log pipeline;
- the six-label Loki index contract or Pod structured metadata;
- demo-api Chart `0.6.0`, application version `0.4.0`, code, or image;
- Grafana data sources, Kubernetes Event collection, or tracing;
- AWS state, public endpoints, credentials, or production automation.

## Acceptance

Run the repair validator, the repaired focused validator, and the complete
quality gate:

```bash
./scripts/validate-v0.11.6.1.1.1-alloy-rbac-rendering-historical-validator-repair.sh
./scripts/validate-v0.11.6.1.1-local-loki-alloy-pod-logs.sh
./scripts/validate-ci-quality-gates.sh
```

The focused validator must successfully render the pinned Loki and Alloy
Charts. Static contract success without external Chart rendering is not an
accepted result.

After committing and pushing the repaired feature revision, reconcile the
local GitOps feature state and rerun:

```bash
./scripts/validate.sh
./scripts/check-local-logging-runtime.sh
```

No demo-api image rebuild is required.
