# v0.11.6.1.1.5 Application-Scoped Alloy and Loki Acceptance Repair

## Incident

The repaired Loki and Alloy workloads became Ready and the demo-api emitted
the expected `/version` JSON record. Alloy discovered the demo-api containers,
but its cluster-wide Kubernetes API readers repeatedly returned:

```text
failed to create fsnotify watcher: too many open files
```

Each target handled by `loki.source.kubernetes` owns a Kubernetes log reader.
The one-node local profile therefore created readers for application,
database, GitOps, ingress, monitoring, and system containers at the same time.
The resulting node watcher pressure caused streams to terminate and reconnect,
and Loki received the watcher error instead of the bounded acceptance record.

The investigation also proved that Loki query results merge structured
metadata such as `pod_name`, `pod_uid`, and automatically detected level into
the returned stream label map. That query representation is not an indexed
label inventory. The previous checker both looked for a nonexistent
`kubernetes.pod.name` field in the application JSON and used the label API as
if all returned names were index labels.

## Repair

The local Alloy discovery scope is now explicitly restricted to the
`startup-apps` namespace. It remains node-local, uses the Kubernetes API, and
requires neither a host log mount nor privilege. This increment proves the
business-application logging path first; cluster-wide platform log expansion
requires a separate capacity-qualified design.

The live checker now:

- filters Loki results to the generated demo-api completion record;
- reads `pod_name` and `pod_uid` from metadata merged into the query result;
- reads release, route, status, and message fields from the JSON line;
- uses the Loki Series API to inspect actual indexed stream labels;
- rejects any new fsnotify watcher-exhaustion entry in the bounded acceptance
  window; and
- retains the existing old-Pod log persistence check.

The five-second lookback begins immediately before the generated request. It
allows small clock skew without treating historical watcher errors already
stored in Loki as a failure of the repaired collector.

## Boundary

This repair changes the Alloy discovery scope and the live acceptance logic.
It does not change Loki configuration, Chart versions, retention, storage,
security contexts, RBAC, NetworkPolicy, the six indexed-label contract,
demo-api code or image, Grafana, Kubernetes Event collection, tracing, AWS
state, public access, credentials, or production automation.

The repair deliberately does not raise host, Docker, WSL, or kind-node sysctl
limits. Host tuning would make the local baseline depend on mutable external
state and would not bound the collector's API reader count.

## Acceptance

Run the offline gates first:

```bash
./scripts/validate-v0.11.6.1.1.5-application-scoped-alloy-loki-acceptance-repair.sh
./scripts/validate-ci-quality-gates.sh
```

Commit and push the repair, then reconcile the existing local feature GitOps
deployment with the already accepted demo-api image parameters. Only the
Alloy configuration changes; no application image rebuild is required.

After `logging-alloy` is `Synced/Healthy` and its DaemonSet rollout completes,
run:

```bash
./scripts/check-local-logging-runtime.sh
```

The checker intentionally replaces one selected demo-api Pod after proving
the first Loki result. Success requires that the old record remain queryable
after the replacement Pod is Ready.
