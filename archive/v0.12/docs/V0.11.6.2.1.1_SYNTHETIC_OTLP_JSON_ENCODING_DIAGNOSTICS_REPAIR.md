# v0.11.6.2.1.1 Synthetic OTLP/JSON Encoding and Diagnostics Repair

## Incident

The first v0.11.6.2.1 local tracing acceptance reached the private
OpenTelemetry Collector but received HTTP 400 during synthetic OTLP ingest.
Both tracing Applications were `Synced/Healthy`, both Deployments were ready,
the Collector OTLP/HTTP receiver was listening, and Tempo was ready. This
proves the failure was not Argo CD reconciliation, RBAC, DNS, Service,
NetworkPolicy, Collector startup, or Tempo startup.

The acceptance script applied standard protobuf JSON byte encoding and sent
`traceId` and `spanId` as Base64. OTLP/JSON deliberately differs from standard
protobuf JSON: those two fields must be case-insensitive hexadecimal strings.
The receiver therefore correctly rejected the malformed request.

The original checker also allowed Python's `HTTPError` traceback to hide the
bounded response body and used a shared `app.kubernetes.io/part-of` selector
that excluded the external Collector Chart from the resource summary.

## Repair

`scripts/generate-synthetic-otlp-trace.py` now owns the acceptance payload. It:

- accepts exactly 32 hexadecimal trace-ID characters;
- accepts exactly 16 hexadecimal span-ID characters;
- rejects all-zero identifiers;
- emits lowerCamelCase OTLP/JSON field names;
- emits the identifiers directly as lowercase hexadecimal strings;
- retains integer enums and decimal-string nanosecond timestamps;
- produces only the one bounded synthetic span required by acceptance.

The live checker now prints the HTTP status and up to 4096 bytes of response
body for an OTLP HTTP failure. Transport failures are reported separately. Its
failure diagnostics explicitly list both tracing Applications, both
Deployments, both Pod sets, both Services, both NetworkPolicies, and both
workload log tails.

## Unchanged runtime

This is an acceptance-only repair. It changes no Kubernetes resource, Helm
value, Chart version, application code, image, Collector configuration, Tempo
configuration, NetworkPolicy, Grafana data source, AWS state, workflow, public
endpoint, or production claim. demo-api export remains disabled. No rebuild,
restart, Argo CD sync, or redeployment is required.

Tempo startup messages that the metrics generator is disabled and that the
backend scheduler currently has no jobs are expected within the accepted
single-binary local boundary; they were not the cause of HTTP 400.

## Validation

Run the repair validator:

```bash
./scripts/validate-v0.11.6.2.1.1-synthetic-otlp-json-encoding-diagnostics-repair.sh
./scripts/validate-ci-quality-gates.sh
```

Then reuse the already running v0.11.6.2.1 runtime and execute:

```bash
./scripts/check-local-tracing-runtime.sh
./scripts/check-local-tracing-runtime.sh
```

Each run must ingest and query a unique valid synthetic trace, replace the
Collector Pod, and prove the accepted trace remains queryable from Tempo.
Application export must remain disabled. Do not advance to v0.11.6.2.2 until
both consecutive runs pass.
