# v0.11.7.0.1 Immutable Feature Root Reconciliation Troubleshooting

## Symptom

The `observability-views` Application reported `Synced` and `Healthy`, but the
new SLO resources were absent:

```text
PrometheusRule/demo-api-slo-recording-rules: NotFound
ConfigMap/observability-dashboard-slo-overview: NotFound
```

Local and remote Git both pointed at `f95581d...`, while the Root and child
Applications still declared and reported `2375fd6...`.

## Root cause

Feature validation intentionally resolves a branch into one immutable commit.
The Root Application then writes that exact commit into every same-repository
child Application. This prevents a moving branch from changing live resources
without an explicit operator action.

Applying and pushing a later increment does not automatically advance that
immutable Root. `Synced` means that the cluster matches the commit currently
declared in `spec.source.targetRevision`; it does not mean that the Application
matches the latest remote branch commit.

A hard refresh only refreshes repository data for the declared revision. A
direct child sync is temporary and does not change Root ownership. The correct
repair is to redeploy the feature Root through the repository-owned workflow.

## Recovery

Reuse the already accepted demo-api image; this reconciliation repair does not
require another image build:

```bash
LIVE_IMAGE="$(
  kubectl -n startup-apps get rollout demo-api \
    -o jsonpath='{.spec.template.spec.containers[?(@.name=="demo-api")].image}'
)"
IMAGE_REPOSITORY="${LIVE_IMAGE%:*}"
IMAGE_TAG="${LIVE_IMAGE##*:}"
APPLICATION_VERSION="$(
  kubectl -n startup-apps get rollout demo-api \
    -o jsonpath='{.spec.template.spec.containers[?(@.name=="demo-api")].env[?(@.name=="APP_VERSION")].value}'
)"

TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_REPOSITORY="${IMAGE_REPOSITORY}" \
IMAGE_TAG="${IMAGE_TAG}" \
APPLICATION_VERSION="${APPLICATION_VERSION}" \
  ./scripts/deploy-local-feature-gitops.sh
```

The deployment script resolves the latest remote feature commit, requires the
local checkout to match it, preserves the accepted image, updates Root source
and `git.targetRevision`, and synchronizes the same-repository children.

## Verification

```bash
for app in startup-devops-root namespace-guardrails demo-api observability-views; do
  kubectl -n argocd get application "${app}" \
    -o custom-columns=NAME:.metadata.name,TARGET:.spec.source.targetRevision,SYNC:.status.sync.status,HEALTH:.status.health.status,REVISION:.status.sync.revision
done
```

Every `TARGET` and `REVISION` must equal the remote feature HEAD. Only then run:

```bash
./scripts/check-local-slo-foundation.sh
```

The repaired check performs this revision alignment before inspecting any SLO
resource, so an old healthy target can no longer produce a misleading
`NotFound` later in the workflow.

## Operational rule

After each committed and pushed feature increment, rerun
`deploy-local-feature-gitops.sh` with the currently accepted image parameters.
Do not patch child `targetRevision` fields directly; Root reconciliation owns
and may restore them.
