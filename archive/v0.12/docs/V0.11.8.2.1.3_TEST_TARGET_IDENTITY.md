# v0.11.8.2.1.3 — Test Prometheus target identity repair

Baseline: v0.11.8.2.1.2. Only validation, tests and documentation change.
No ServiceMonitor, Service, IAM, Terraform or application release is modified.

## Incident and cause

Test infrastructure and application were healthy, but qualification reported
`No up demo-api target.` The ServiceMonitor relabels the Kubernetes Service name
into `job`. The test ALB canary topology exposes `demo-api-stable` and
`demo-api-canary`, while the observer required the literal `demo-api` job.
The original mocked target fixture used only that single-Service spelling;
therefore offline tests missed this live topology mismatch.

Initial manual diagnostics also queried dev: returned labels said `aws-dev`,
with a different release and Pod addresses. The operator confirmed different
shells used different temporary kubeconfigs. A subsequent test query showed
the targets up. This is a diagnostic-context error separate from the observer
bug; the automated observer uses its own guarded test kubeconfig.

## New checks

- Read stable/canary Service names from the already checked healthy Rollout;
  retain the single `demo-api` Service topology when names are not declared.
- Require the expected ServiceMonitor scrape pool, namespace, app, `aws-test`,
  declared version and digest, HTTP endpoint, live Pod name, Service and job.
- Every discovered demo candidate must be up; stable targets must cover every
  active application Pod. Canary targets may be absent after convergence, but
  any discovered canary target must match identity and be up.
- Ignore unrelated monitoring jobs, but reject mixed dev/test demo candidates.
- Failures include candidate labels, health and lastError in the local console.
  Review/redact diagnostic output before sharing. Evidence retains its existing
  schema and conservative failed status. Targets are not summed into traffic
  counts; this repair does not establish SLO or canary experiment evidence.

No arbitrary job-name regex or environment-label rewrite is used to force a pass.
The observer takes a snapshot, not a readiness retry loop. Transient discovery
or scrape failures can still fail; inspect diagnostics before retrying.

## Resume after applying this repair

Run the new focused validator and full local quality gate, review then commit
and push on `feature/v0.11-observability-sre-baseline`. Keep your existing cloud
resources. Re-export account/SHA/version in the shell used for qualification
as shown in section 6 of the updated main runbook. Wait for GitOps to reconcile
the new SHA. Run qualification with a new output path; do not reuse old evidence.

`status=qualified` and exit 0 are the expected result. `Healthy` alone is not
full qualification; later checks may still report independent problems.

## Multi-shell diagnostics

In the port-forward shell, set the independently reviewed account again:

```bash
read -r -p 'Reviewed target AWS account (12 digits): ' EXPECTED_AWS_ACCOUNT_ID
TEST_CONTEXT="arn:aws:eks:us-east-1:${EXPECTED_AWS_ACCOUNT_ID}:cluster/startup-devops-baseline-test"
kubectl --context="$TEST_CONTEXT" -n argocd get application observability-views-aws-test \
  -o jsonpath='{.spec.destination.namespace}{"\n"}'
kubectl --context="$TEST_CONTEXT" -n observability get pods
kubectl --context="$TEST_CONTEXT" -n startup-apps get servicemonitor demo-api -o yaml
kubectl --context="$TEST_CONTEXT" -n observability port-forward \
  service/observability-metrics-prometheus 19091:9090
```

The named context must exist in THAT shell's kubeconfig. Stop on missing context
or a port bind error; do not fall back to the current context. Keep forwarding
running. `observability-views-aws-test` is an Application, not its namespace.
In the query shell:

```bash
curl -fsS 'http://127.0.0.1:19091/api/v1/targets?state=any' \
  -o /tmp/aws-test-prometheus-targets-19091.json
jq '.data.activeTargets[] | select(.labels.namespace == "startup-apps")
    | {labels, scrapeUrl, health, lastError}' /tmp/aws-test-prometheus-targets-19091.json
```

Expect `deployment_environment_name=aws-test` and the declared test release.
Do not infer environment from the local port number alone. Stop your own
forward with Ctrl-C after diagnosis; no deployment restart is needed.

## Producer verification limits

Offline positive and mutation tests cover topology, identity, down/missing/partial
targets and the real ServiceMonitor job relabeling source. Prior feature tests
remain enabled. No live AWS qualification is performed by the producer; renderer
SKIP and a Docker-blocked full gate are not successful runtime/render validation.
