## What the observer checks

- Exact approved AWS account and IAM/STS actor; fixed us-east-1 prod cluster.
- Clean local main, exact remote main SHA, declared prod version and digest.
- Cluster ARN/status and isolated temporary kubeconfig endpoint/context.
- Root plus 8 same-repository Applications and 9 external chart Applications,
  compared with the rendered prod sources, destinations and projects. The ALB
  controller VPC ID is matched to the discovered cluster, not a copied dev value.
- Healthy stable Rollout, exact image and ready application Pods.
- Ready monitoring workloads, identity-bound stable/canary targets, required
  Prometheus rules, six dashboard ConfigMaps and Alertmanager readiness.
- Absence of undeclared Loki/Tempo/Alloy/OTel workloads in observability.

SLO and progressive delivery telemetry remain supported-not-verified: this tool
does not generate traffic or infer a full SLO/Canary experiment from readiness.
Dashboard ConfigMaps do not prove browser rendering; rules/readiness do not
prove notification delivery. Operator mode does not prove least privilege.
No new prod RBAC Application or credential is created. Required read/port-forward
permissions must already be authorized outside this tool; denial is a stop.

## Approval trust model

The record is an **operator-attested reference to prior external approval**,
not a signature, an independent approver or a GitHub protected-environment check.
An operator able to edit it can forge it. Use organizational review, trusted
execution and IAM/RBAC to enforce actual authority; do not advertise this JSON
guard as a security boundary against a malicious operator.

Both a scoped approval file and explicit CLI confirmation are required. An
environment variable alone does not approve this entrypoint. Local checks run
before any subprocess/network access. The file binds environment, account,
region, cluster, SHA, version, image, action, mode and exact actor ARN, with an
external reference and a maximum one-hour validity window. Future/expired scopes
are rejected. The record's bytes and expiry are rechecked before successful
evidence, along with source SHA and actor. A changed/expired approval fails the
observation. Failed evidence retains the originally accepted approval reference;
it is not a claim that approval remained valid at completion.

AWS IAM/RBAC still applies. The observer does not assume roles, create sessions,
change permissions or call deployment helpers. Its operations are metadata reads,
Kubernetes get/auth checks and port-forward to monitoring HTTP reads. Temporary
kubeconfig/evidence writes are local; no application workload mutation is used.
Port-forward permission uses the Kubernetes `create pods/portforward` verb but
does not create an application Pod. There is no pods/exec call.

## Future live procedure — do not execute in this increment

At the v0.11 tail, after separately approved main integration and prod deployment:

1. Review the exact main commit and existing prod release file. Preserve all
   earlier raw evidence privately; do not relabel test evidence as prod.
2. Obtain external approval for the fixed target and intended operator. Capture
   that operator's exact IAM/STS ARN through the approved access process. A new
   STS session ARN requires a new record. Do not switch identity mid-observation.
3. Place the approval record outside the repository with private permissions.
   The following is a deliberately non-runnable shape (not granted approval):

```json
{
  "approved": false,
  "environment": "aws-prod",
  "account": "<reviewed-account>",
  "region": "us-east-1",
  "cluster": "startup-devops-baseline-prod",
  "sha": "<reviewed-main-full-sha>",
  "application_version": "<declared-prod-version>",
  "image": "<declared-prod-repository>@sha256:<digest>",
  "actor_arn": "<approved-exact-IAM-or-STS-ARN>",
  "action": "observe",
  "mode": "operator-observation",
  "reference": "<external-review-reference>",
  "issued_at": "<UTC-ISO8601>",
  "expires_at": "<UTC-ISO8601-within-one-hour>"
}
```

4. Use an already authenticated approved operator shell, at clean reviewed main.
   Fill the record only from that external approval; do not self-authorize by
   changing false to true without approval. Then prepare inputs:

```bash
export EXPECTED_CONTROL_PLANE_SHA="$(git rev-parse HEAD)"
export EXPECTED_APPLICATION_VERSION="$(python3 -c 'import yaml; print(yaml.safe_load(open("apps/demo-api/helm/values/releases/aws-prod.yaml"))["release"]["applicationVersion"])')"
read -r -p 'Reviewed target account: ' EXPECTED_AWS_ACCOUNT_ID
read -r -p 'Private external approval record path: ' PROD_APPROVAL_FILE
```

5. Only within the approved window, execute the read-only observation:

```bash
./scripts/check-aws-prod-observability-qualification.py \
  --account "$EXPECTED_AWS_ACCOUNT_ID" \
  --sha "$EXPECTED_CONTROL_PLANE_SHA" \
  --application-version "$EXPECTED_APPLICATION_VERSION" \
  --approval "$PROD_APPROVAL_FILE" \
  --confirm approved-prod-read-only --operator-observation \
  --output "/tmp/aws-prod-observability-$(date -u +%Y%m%dT%H%M%SZ).json"
```

6. Exit 0/qualified means the bounded checks passed. Exit 2/waiting-runtime
   means approved discovery found no prod cluster, not success. Exit 1 means
   refusal/failure; preflight refusal produces no runtime evidence. Permission
   and network failures are not absence. Existing output files are never reused.
7. Archive evidence privately and redact sharing copies. Fresh evidence retains
   schema v0.11.8.0 and qualificationVersion v0.11.8.3. Do not commit approval
   files, kubeconfigs, credentials or unredacted account details.

No real production deployment, cleanup or recovery is authorized by this
