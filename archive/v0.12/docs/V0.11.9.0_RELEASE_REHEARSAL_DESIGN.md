# v0.11.9.0 Release rehearsal design

## Boundary

This increment adds a scenario contract and an **offline**, read-only plan
preflight. It executes no cloud or Kubernetes commands, generates no traffic,
and does not qualify a release. Continue on the feature branch. Do not merge
main, create prod, or rerun earlier live drills to accept this increment.
Prod live acceptance remains separately approved at the v0.11 tail.

The v0.11.8.4 evidence archive is historical, not a current release permit.
Local is the first implementation target; dev/test follow separately, and
environments are sequenced to limit concurrent cost.

## Scenario acceptance matrix (future live work)

| Scenario | Required fresh evidence | Stop condition |
| --- | --- | --- |
| Successful candidate | Exact source SHA, image/version, both distinct release-bound successful AnalysisRuns, reviewed 50% pause, final Healthy stable/current convergence | Missing data, provider error, wrong release, failed gate or deadline |
| Candidate SLO rejection | Healthy baseline first; bounded candidate-only test traffic/fault; exact failed SLO measurement and AnalysisRun for that candidate; no promotion; stable availability preserved | Baseline impact, wrong target, missing recovery owner or deadline |
| Baseline restoration | Approved known-good Git desired release restored; Argo desired/observed convergence; Ready pods/version/image and stable service endpoints; current metrics recover | Runtime-only rollback diverges from Git, unresolved degradation or deadline |
| Evidence and cleanup review | Preserve successful/failed analyses, timestamps, context and release identities, reviewer decision; remove only owned temporary processes/fixtures after review | Unreviewed destructive cleanup or missing incident evidence |

A Healthy revision-1 Rollout is not successful Canary evidence. A provider error
or no-data failure is not evidence of the intentional SLO rejection scenario.
An aborted candidate alone does not prove baseline restoration. Thresholds and
bounded injection mechanism must be implemented/reviewed in the next increment;
this document does not supply an executable fault command.

Reuse the local phase semantics in
[v0.11.7.3](V0.11.7.3_LOCAL_SLO_PROGRESSIVE_DELIVERY_CLOSURE.md) and the bounded
[final convergence wait](V0.11.7.3.1_FINAL_ROLLOUT_CONVERGENCE_WAIT_TROUBLESHOOTING.md).
The human-governed 50% checkpoint remains policy, not a universal prescription
for small teams. Changing it requires a separate policy decision.
AWS metrics qualification does not imply AWS log/trace correlation or Canary
qualification. Keep unsupported evidence explicitly unverified.

## Accept this increment (no cluster required)

```bash
bash scripts/validate-v0.11.9.0-release-rehearsal-design.sh
```

Optional plan preparation, not required to submit this design increment:

```bash
PLAN_DIR=$(mktemp -d /tmp/release-rehearsal-plan.XXXXXX)
cp delivery/examples/release-rehearsal-plan.json "$PLAN_DIR/plan.json"
# Edit every REPLACE field in your own file before running:
python3 scripts/check-release-rehearsal-plan.py --plan "$PLAN_DIR/plan.json"
```

The unedited template MUST fail. Supply the intended exact target context,
full source commit, current known-good baseline release, and distinct intended
candidate version. Image references require immutable digests (a local image
without one must be resolved as part of later rehearsal preparation; do not
invent a digest). Baseline and candidate may share a digest with distinct
application versions. These are planned values, not automatically discovered
from dev, the current shell context, or a previous report.

Output `plan_validated_offline` means only structural safety checks passed.
The checker does not inspect Git, authenticate approvals, resolve images,
validate kubeconfig, check readiness, or contact any environment. It writes
no evidence file and never authorizes execution. Keep private plans outside
Git; review secret/account/context data before sharing. This plan is not a
v0.11.8 observability qualification report and must not be registered as one.

Before any future live step, separately confirm clean/pushed exact source,
explicit cluster identity (and AWS account/region where applicable), fresh
baseline health, image availability, gate resources, bounded traffic, reviewer
and recovery owner, maximum duration, and a reviewed recovery procedure.
No current-context implicit fallback is acceptable. Preserve failure evidence
before recovery and do not automatically promote on retry.
