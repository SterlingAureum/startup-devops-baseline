# v0.11.9.2.2.2 baseline restoration traffic guard

## Incident

Revision 66 reached the reviewed 50% pause, but it was promoted without an
active second-analysis traffic producer. The second AnalysisRun received zero
eligible requests and correctly aborted the candidate. Revision 67 was then
created by `restore-local-feature-baseline.sh`; that script synchronized Argo CD
without arming traffic, so its first AnalysisRun failed for the same reason.

The stable ReplicaSet remained Ready and served all traffic. These are failed
qualification/restoration attempts, not an application outage.

## What the AnalysisRun measures

The AnalysisRun does not generate traffic. The local observer port-forwards the
`demo-api-stable` and `demo-api-canary` Services and sends bounded `GET /version`
request pairs across multiple Prometheus scrape intervals. The template then
queries metrics scoped to the exact candidate release ID:

- Prometheus target availability;
- at least 20 eligible Canary requests in the five-minute window;
- Canary availability error-budget burn rate;
- Canary latency error-budget burn rate for the 0.5 second objective;
- remaining stable availability and latency budgets.

Zero requests are not success. They produce an empty burn-rate vector and make
`canary-minimum-eligible-requests` fail with value zero.

## Contract change

`restore-local-gitops-baseline.sh` now distinguishes GitOps synchronization
from runtime restoration. It exits `2`, prints Rollout/AnalysisRun diagnostics,
and refuses to print `restored` unless the Rollout is `Healthy`, not aborted,
and current/stable hashes match.

`run-local-baseline-restoration-analysis.sh` is an observer and bounded traffic
producer. It never restores, promotes, retries or aborts. It counts all existing
AnalysisRuns for the exact release and requires one new run, so historical
failed runs cannot satisfy a recovery checkpoint.

## Recover the observed revision 67

Preserve the revision 66/67 evidence first. This recovery does not convert either
failed AnalysisRun into successful qualification evidence.

Terminal 2:

```bash
export LOCAL_CONTEXT=kind-startup-devops-baseline
export EXPECTED_APPLICATION_VERSION=sha-3e50802
export CONFIRM_LOCAL_BASELINE_RECOVERY=observe-reviewed-local-baseline-recovery

bash scripts/run-local-baseline-restoration-analysis.sh first-analysis
```

After terminal 2 prints `ACTION SIGNAL`, terminal 1 performs the separately
reviewed recovery retry exactly once:

```bash
kubectl argo rollouts retry rollout demo-api \
  -n startup-apps --context "$LOCAL_CONTEXT"
```

Wait for terminal 2 to pass and for the Rollout to reach `Paused`, step `4`.
Review the new AnalysisRun; do not use revision 66/67 failed runs as approval.

Then start terminal 2 again:

```bash
bash scripts/run-local-baseline-restoration-analysis.sh second-analysis
```

Only after `Generating bounded traffic` is visible, terminal 1 promotes once:

```bash
kubectl argo rollouts promote demo-api \
  -n startup-apps --context "$LOCAL_CONTEXT"
```

Wait for the second observer to pass. Finally:

```bash
bash scripts/run-local-baseline-restoration-analysis.sh final
argocd app diff startup-devops-root
argocd app diff demo-api
```

Require a Healthy Rollout, matching current/stable hashes, two new successful
AnalysisRuns, and empty Argo CD diffs. Stop on Failed, Error, Inconclusive,
identity drift or timeout. Never repeat retry or promote to obtain a green run.

## Future restoration ordering

When a future restore will change the Rollout template, start the
`first-analysis` observer in terminal 2 before starting the restore in terminal
1. The observer waits for the exact expected application version and Canary
identity. A restore command may exit `2` while runtime progression is pending;
that is an accurate checkpoint rather than a restoration failure. Complete both
analysis checkpoints and final observation before calling the baseline restored.
