# v0.11.9.3.0 remote release rehearsal design

## Status and boundary

This checkpoint defines the final v0.11 remote rehearsal sequence and validates
a private operator plan offline. It performs no AWS, Kubernetes, Argo CD,
GitHub workflow, pull-request, image, DNS, database, traffic, Canary, teardown,
or cost action. A valid plan still returns `execution_authorized: false`.

The design baseline is feature commit
`d2ab89b22e5e048ed4d9121170e04d7fe7156f2c`. The feature must not receive
remote runtime credentials. Before any final aws-dev or aws-test runtime
workflow, all active AWS GitOps overlays must be restored from the temporary
feature revision to `main`, the complete feature must be reviewed and merged,
and the exact merged main SHA must be captured as the control-plane identity.

## Build-once candidate

The accepted local binary remains the remote build-once candidate:

```text
repository: ghcr.io/sterlingaureum/startup-devops-baseline/demo-api
tag/application version: sha-cf0a6bc
digest: sha256:cdffd3d71763540976570da1f201661d24c641ec459be812b20f1517f3fd2623
image source commit: cf0a6bcbc466b61f2018a0a92c961d7c03f128e8
workflow run: 34070524953
release ID: demo-api-cf0a6bcbc466-cdffd3d71763
```

The image source commit and control-plane commit are different identities. The
former proves which source built the binary; the latter proves which exact main
revision declared and observed the environments. This difference is expected
because the later commits changed validation, restoration, evidence and design
logic without changing the demo-api binary.

Do not rebuild merely to make the two SHAs equal. Before using the existing
artifact, a later live preflight must prove that the metadata artifact and both
attestations remain available, the digest is readable, and the image source
commit is an ancestor of the selected main revision.

## Missing build-to-dev handoff

Workflow run `34070524953` intentionally used `create_promotion_pr=false`.
Existing build-to-aws-dev automation creates its release PR only in the same
image-build run. Replaying that old source would execute obsolete quality gates,
while rebuilding from the final main commit would replace the accepted
candidate identity.

Therefore remote execution is blocked until v0.11.9.3.1 implements a reviewed
existing-image metadata handoff. It must validate the stored identity and
attestations, require the source commit to be contained in main, change only
`apps/demo-api/helm/values/releases/aws-dev.yaml`, create or reuse a PR, and
never merge automatically. v0.11.9.3.0 does not implement that handoff.

## Environment sequence and cost boundary

Only one EKS environment is active at a time:

1. Validate the private plan and implement the existing-image handoff.
2. Restore active AWS GitOps overlays to main, review and merge the feature, and
   capture the exact main SHA.
3. Prepare and manually merge the candidate release-only aws-dev PR.
4. Create/deploy aws-dev, then collect fresh runtime and observability evidence.
5. Prepare and manually merge the aws-dev-to-aws-test release-only PR.
6. Preserve fresh dev evidence, then separately approve and tear down aws-dev.
7. Create/deploy aws-test, complete its reviewed Canary checkpoint, and collect
   fresh runtime and observability evidence.
8. Prepare the protected aws-test-to-aws-prod release-only PR and obtain the
   production approvals; never auto-merge it.
9. Preserve test evidence, then separately approve and tear down aws-test.
10. Create/deploy aws-prod, complete its reviewed Canary checkpoint, and run
    the separately approved read-only production observer.
11. Review the final evidence set, separately approve production teardown, and
    perform the residual-cost audit.

Source qualification evidence must remain fresh when it authorizes the next
promotion. Absence is `waiting-runtime`, not success. Teardown never happens
automatically and begins only after successor release state and source evidence
are preserved.

## Failure scenario disposition

The intentionally failed Canary requirement is satisfied by the reviewed local
v0.11.9.2 evidence: failed revision 69 was isolated from stable traffic and the
immutable baseline recovered as Healthy revision 70. That evidence is a
failure/recovery scenario record, not aws-dev, aws-test, or aws-prod
qualification.

The implemented fault gate rejects enabled mode whenever `APP_ENV` is not
`local`. It must not be enabled in AWS. Repeating the fault remotely would
expand the security and recovery boundary and requires a separate design; it is
neither required nor allowed by this checkpoint.

## Offline plan

Copy the template into a private directory outside the repository, set mode
`600`, and replace every placeholder. Do not commit or upload the populated
plan because it contains account, context, operator, approval and evidence
locations.

```bash
PLAN_PARENT=$(mktemp -d /tmp/v0.11-remote-rehearsal.XXXXXX)
PLAN_FILE="$PLAN_PARENT/plan.json"

cp delivery/examples/v0.11.9.3.0-remote-release-rehearsal-plan.json \
  "$PLAN_FILE"
chmod 600 "$PLAN_FILE"

python3 scripts/check-v0.11.9.3.0-remote-release-rehearsal-plan.py \
  --plan "$PLAN_FILE"
```

The repository template must fail because private fields and the future merged
main SHA are intentionally unresolved. A fully populated plan may produce
`remote_rehearsal_plan_validated_offline`, but it still lists blocking reasons
and does not authorize execution. The checker does not inspect Git ancestry,
GitHub artifacts, attestations, AWS identity, kubeconfig, runtime state,
qualification freshness, approvals, or costs.
