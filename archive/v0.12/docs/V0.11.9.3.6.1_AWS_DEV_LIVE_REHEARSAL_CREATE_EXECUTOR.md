# v0.11.9.3.6.1 aws-dev live-rehearsal create executor

## Status and implementation baseline

This checkpoint implements and tests the guarded aws-dev infrastructure create
executor. Applying and validating the checkpoint uses mocked commands only. It
does not run a fresh preflight, access AWS, produce a Terraform plan, create an
environment, bootstrap GitOps or tear anything down.

The implementation baseline is protected-main commit:

```text
4ecf8515c636066a4e8e9cc640ee96473fbfd21d
```

The implementation must be reviewed and merged before preparing live inputs.
The merge produces a later control-plane SHA; all live private files must bind
that later SHA, not the implementation baseline above.

## Two executor phases

The entrypoint is:

```text
scripts/execute-v0.11.9.3.6.1-aws-dev-live-rehearsal-create.py
```

`verify` validates the three private files, exact Git identity, reviewed time
window, candidate, cost limits and saved ready preflight result. It performs no
AWS, Terraform or Kubernetes command and returns `execution_authorized=false`.

`execute` repeats every verification, requires three environment confirmations,
runs the same read-only preflight immediately, and requires its stdout to be
byte-identical to the reviewed result. Only then can it invoke the existing
`scripts/apply-aws-dev.sh` entrypoint.

## Machine Terraform plan gate

Initial creation now renders the saved plan through `terraform show -json` and
passes that temporary JSON to `scripts/check-aws-dev-create-terraform-plan.py`.
The checker accepts only:

- `create`;
- `read`;
- `no-op`.

At least one `create` is required. `update`, `delete`, both replacement action
orders, an empty plan, unknown actions and malformed JSON stop before the
interactive confirmation and before `terraform apply`.

The JSON contains plan details and remains an owner-only temporary file. The
checker emits counts only and does not persist raw plan values.

## Prepare live inputs after merge

After this checkpoint reaches protected main, capture the new full SHA. Use a
new private directory with mode `0700`; every JSON file must use mode `0600`.

Create and populate a fresh `.3.5` preflight plan bound to that exact SHA, then
capture the command's stdout without reformatting it:

```bash
CONFIRM_AWS_DEV_PREFLIGHT='observe-reviewed-aws-dev-rehearsal' \
  python3 scripts/preflight-v0.11.9.3.5-aws-dev-live-rehearsal.py \
    --plan "$FRESH_PREFLIGHT_PLAN" \
    > "$FRESH_PREFLIGHT_RESULT"
chmod 600 "$FRESH_PREFLIGHT_RESULT"
```

Compute both fresh fingerprints:

```bash
sha256sum "$FRESH_PREFLIGHT_PLAN" "$FRESH_PREFLIGHT_RESULT"
```

Populate a private copy of the `.3.6` create-plan template with those exact
hashes, the later main SHA, intended account, current reviewed pricing data and
an active UTC window. Validate it using the `.3.6` checker.

Do not commit or share the raw files. The preflight result contains the AWS
account ID. Share only the two SHA-256 fingerprints and the redacted outputs.

## Zero-write verification

Run this first:

```bash
python3 scripts/execute-v0.11.9.3.6.1-aws-dev-live-rehearsal-create.py \
  verify \
  --create-plan "$CREATE_PLAN" \
  --fresh-preflight-plan "$FRESH_PREFLIGHT_PLAN" \
  --fresh-preflight-result "$FRESH_PREFLIGHT_RESULT"
```

A successful result ends with `aws-dev-create-executor-inputs-verified` and
still reports `execution_authorized=false`. Preserve that output privately and
obtain the separate live-create approval.

## Separately approved execute phase

The execute phase requires all three controls:

```text
CONFIRM_AWS_DEV_PREFLIGHT=observe-reviewed-aws-dev-rehearsal
CONFIRM_AWS_DEV_REHEARSAL_CREATE=execute-reviewed-aws-dev-rehearsal-create
CONFIRM_AWS_DEV_APPLY=create-ephemeral-aws-dev
```

The existing Terraform prompt remains a fourth, interactive decision. Review
the human-readable plan and type `apply-aws-dev` only after the machine gate
reports a nonempty create-only plan.

Do not run execute merely because this checkpoint was merged. First submit the
redacted verify output, fresh hashes, planned window and cost summary for the
separate live approval.

## Success and failure boundary

Success means infrastructure creation completed and the EKS Kubernetes API is
ready from the current workstation. The executor then stops. It does not:

- run `bootstrap-eks-argocd.sh`;
- run `deploy-aws-dev-root-app.sh`;
- generate traffic or qualification evidence;
- promote to aws-test;
- automatically destroy aws-dev.

Those are later reviewed phases. On any error, preserve Terraform state and
private evidence, inspect the exact failing stage and do not automatically
retry or destroy. Remote replay of the local fault remains forbidden.
