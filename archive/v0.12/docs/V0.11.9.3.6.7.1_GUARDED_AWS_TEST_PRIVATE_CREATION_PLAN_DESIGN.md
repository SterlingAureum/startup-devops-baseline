# v0.11.9.3.6.7.1 guarded aws-test private creation-plan design

## Purpose and status

This checkpoint records the reviewed boundary of the successful `.6.7`
aws-test readiness result and implements an offline validator for a private,
cost-bounded Terraform creation plan. Applying and validating this increment
executes no GitHub, AWS, Terraform, Kubernetes or Argo CD command.

The implementation baseline is protected-main commit:

```text
05f481b5ce06705e130e5674175028f6645a63e1
```

The reviewed private preflight result is represented only by SHA-256:

```text
e1cf8f0fed49292b45ea3f79f5f43b51ce879f01e3d6f64753b429cab41b60f2
```

It reported the expected account, no active rehearsal environment, an empty
version-4 local aws-test state, the reviewed dev/test release identity and held
production release. It did not run Terraform or authorize creation. Its
private `/tmp` path, account identity and any AWS inventory remain outside Git.

## Why this checkpoint does not run Terraform plan

Merging this design changes protected main. A live Terraform plan must not be
bound to the older `05f481...` code identity. After merge, run a fresh `.6.7`
preflight against the new exact main and populate a private copy of the plan
template. The next `.6.7.2` checkpoint will implement the guarded executor for
Terraform init/plan/show.

The legacy `scripts/apply-aws-test.sh` remains forbidden because it plans and
immediately applies in one process. The historical
`scripts/prepare-aws-test-feature.py` is also not the live entrypoint for this
main-based rehearsal: its branch and qualification assumptions belong to the
earlier feature workflow. Neither script is invoked by this checkpoint.

## Private plan contents

Copy this repository template outside Git only after `.6.7.1` reaches
protected main:

```text
delivery/examples/v0.11.9.3.6.7.1-aws-test-live-creation-plan.json
```

The populated plan contains private operational data:

- expected AWS account ID;
- current globally routable management IPv4, without committing it;
- operator, recovery owner, review reference and UTC session window;
- current pricing estimate and reviewed session budget;
- SHA-256 of the ignored local `terraform.tfvars`;
- SHA-256 of the fresh post-merge `.6.7` preflight result;
- an owner-only plan-bundle path outside the repository.

Use an eight-hour maximum window, no more than USD 50 reviewed session budget,
and a budget large enough to cover eight hours at the reviewed hourly
estimate. These are operator review limits, not claims of implemented AWS
Budgets or automatic shutdown.

The committed qualification profile is fixed at four test nodes and is pinned
by SHA-256. Review the local `terraform.tfvars` separately, including its
non-placeholder `Owner` tag. Do not commit that local file merely to make its
fingerprint reviewable.

## Planned Terraform artifact boundary

The successor plan executor must create a new owner-only bundle containing:

- saved binary Terraform plan;
- `terraform show -json` output;
- no-color human-readable plan;
- redacted machine-gate summary and stderr files;
- fingerprints for the plan, variable inputs and fresh preflight.

The bundle directory must be `0700` and every file `0600`. Terraform plugin
data must use a private directory outside the repository. Raw plan JSON and
text may contain account, network and resource identities and must never be
committed or pasted into review messages.

The machine gate will accept only action vectors:

```text
[create]
[read]
[no-op]
```

At least one create is required. Update, delete, both replacement orders,
unknown actions and an empty plan stop. A human must then review cost and
resource scope. The saved plan expires after one hour and still cannot be
applied until a later apply executor is implemented, merged, verified and
separately approved.

## Failure-stop boundary

Stop and preserve private evidence when:

- account, region, exact main or release identity changes;
- the fresh preflight differs from the reviewed bytes;
- any rehearsal EKS environment becomes active before initial planning;
- local state is nonempty, partial, malformed or redirected;
- ignored variable inputs change;
- the aws-test cluster already exists;
- any update, delete, replacement or unknown Terraform action appears;
- the plan or reviewed session window expires.

Do not delete state to force an empty create, import or adopt resources
automatically, retry plan/apply automatically, or start teardown without a
separate approval.

## Offline validation before merge

```bash
bash scripts/validate-v0.11.9.3.6.7.1-aws-test-live-creation-plan-design.sh
bash scripts/validate-ci-quality-gates.sh
git diff --check
```

The repository template intentionally fails because it contains placeholders.
The unit tests populate a private fixture and test main/preflight/candidate,
infrastructure, management-IP, variable-input, cost/time, Terraform-action,
sequence and no-execution boundaries without reaching live tools.

## Post-merge preparation boundary

After merge, first capture the new exact protected-main SHA and rerun the `.6.7`
private preflight. Do not reuse the older result as the fresh result. Then copy
the template into a new private `0700` directory, populate all placeholders,
set the file to `0600`, and validate it offline with:

```bash
python3 scripts/check-v0.11.9.3.6.7.1-aws-test-live-creation-plan.py \
  --plan "$AWS_TEST_PRIVATE_CREATE_PLAN"
```

A successful result still reports:

```text
terraform_plan_authorized=false
terraform_apply_authorized=false
environment_creation_authorized=false
commands_executed=[]
```

Submit only the redacted validator result and SHA-256 fingerprints for review.
Do not submit the private plan, account, management address, Terraform values
or bundle path.

## Next boundary

The next checkpoint is `.6.7.2`: a guarded plan executor with separate
`verify` and `execute` phases. `verify` must remain zero-command; `execute`
will require a new explicit plan-only approval, repeat a byte-identical
immediate preflight, generate and machine-check the private Terraform plan,
and stop before apply. GitOps bootstrap, qualification, promotion and teardown
remain later independent phases.
