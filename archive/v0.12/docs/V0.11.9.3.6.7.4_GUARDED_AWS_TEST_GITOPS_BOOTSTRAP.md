# v0.11.9.3.6.7.4 Guarded aws-test GitOps Bootstrap

This increment implements the next aws-test live checkpoint without executing
it. Applying or validating the increment performs no AWS, Terraform,
Kubernetes, Argo CD, GitOps or traffic operation.

## Fixed predecessor

The executor binds the recorded `.7.3.1.1` apply/resume evidence, the private
creation plan fingerprint, the resulting owner-only Terraform state and the
existing shared EKS bootstrap script. The infrastructure was created from
protected main `1376129d42c6dbc19ffb57c97244d2b31ddd4ff7`; this increment is
implemented against protected main
`8ff28f9f047d866c494db04cf71333efcdfe1f34` and requires another exact clean
protected-main commit after merge.

The existing `scripts/bootstrap-aws-test.sh` is forbidden because it continues
from the platform bootstrap into the aws-test Root Application. The guarded
executor calls `scripts/bootstrap-eks-argocd.sh` exactly once and stops after
the AWS Load Balancer Controller child Application exists.

## Phase 1: private verify

The operator supplies the existing owner-only `.7.1` private creation plan and
a new, nonexistent private output path. The verifier requires at least 900
seconds before `2026-09-12T17:38:53Z`, validates exact Git and repository
fingerprints, and requires the live Terraform state to remain byte-identical.

After the observation confirmation is set, only these live reads run:

- STS caller identity;
- EKS cluster inventory and aws-test cluster description;
- Secrets Manager metadata only;
- `terraform state list` and two `terraform output -raw` reads;
- kubeconfig endpoint inspection, Kubernetes `/readyz`, and Kubernetes object
  reads proving that the Argo CD namespace, both bootstrap ServiceAccounts and
  the aws-test Root Application are absent.

The returned JSON is redacted and leaves GitOps execution unauthorized. Review
and hash that exact JSON before considering execution.

## Phase 2: separately approved execute

Execution requires both the observation and execution confirmations plus the
reviewed verify file and its SHA-256. It reruns the full read-only preflight and
captures every raw stdout/stderr stream in a new `0700` directory with `0600`
files. It then runs the exact shared bootstrap once with:

- environment `aws-test` and region `us-east-1`;
- cluster `startup-devops-baseline-test`;
- Terraform directory `infra/terraform/aws/environments/test`;
- exact Argo CD version `v3.5.2`.

The allowed mutations are limited to kubeconfig configuration, the two IRSA
ServiceAccounts, the Argo CD namespace/install, and the AWS Load Balancer
Controller Argo CD Application. Post-checks require the Argo CD core workloads
ready, exact Terraform-derived role annotations, the child Application
present, the Root Application absent, and Terraform state unchanged.

No Terraform plan/apply/destroy, Root Application, traffic, qualification,
promotion, teardown, retry or repair is authorized. Any failure preserves the
Terraform state and private evidence and stops.

## After merge

Run the repository validator first, then create a fresh private `verify` result
on the new protected-main SHA. Do not reuse a prior approval. The exact command
sequence and confirmation values are intentionally supplied only after the
post-merge SHA and remaining session time have been reviewed.
