## Budget and elapsed time

Historical aws-test spend cannot currently be separated from older AWS spend.
It is recorded as unknown, never zero. The operator accepts at most **USD 8
additional budget**, not a new USD 12 allowance or an assertion about the bill.
Twelve hours of operator availability is not twelve hours of authorized runtime.

The plan checker requires a documented conservative hourly upper estimate for
EKS, EC2, EBS, NAT/public IPv4, load balancing, backups/storage, logs/metrics,
DNS/other services and transfer. The estimate must cover both current idle
resources and the peak anticipated after Root reconciliation. Do not infer the
estimate solely from default Terraform variables or tag-matched inventory.
Document region, resource quantities/types, pricing basis and review time in
the private pricing reference; justify any zero component explicitly.

The additional cost estimate is:

```text
sum(hourly upper estimates)
  * hours(2026-09-13T00:27:58Z through cleanup completion)
  + fixed and uncertainty reserve
  <= USD 8
```

The accounting anchor conservatively includes all observed next-day idle time,
including time spent implementing and reviewing increments. Previous overnight
cost remains unknown and separate; this formula does not certify total spend.
Starting a new window must not reset that accounting anchor.

The new action window is at most eight hours and must finish before the stated
operator-availability bound, September 13 at 12:48:28 UTC. At least one hour
must be reserved for cleanup. These are plan limits, not preauthorized times.
The template deliberately has no invented rates or execution window. Missing,
non-finite, negative, over-budget, expired and incomplete plans fail closed.
The preflight can observe an expired session; it cannot authorize another one.
If the budget or day no longer fits, review a new recovery/cleanup plan rather
than editing timestamps to bypass this contract. There is no automatic billing
enforcement or automatic teardown.

## Why Root deployment needs a complete scope review

The tracked Root and same-repository children currently follow mutable `main`.
Root and child Applications enable automated reconciliation with prune and
self-heal. Creating Root may immediately begin child and controller writes;
it is not an inert registration step. No claim of an immutable deployment is
made here. The next executor design must choose and validate a consistent
Root/child revision policy, including any temporary Git freeze or pinned
rendering; pinning only Root does not pin children.

Review these connected parts before implementing deployment:

| Part | Resulting work and required review |
| --- | --- |
| Root and children | Render the exact test overlay, enumerate objects, review sync waves, prune scope, source revisions and chart versions. |
| Karpenter and storage | EC2NodeClasses/NodePools can create nodes; CNPG and monitoring can allocate volumes. Include capacity peaks and retention. |
| CNPG backups | Configure the exact state-derived backup role and ObjectStore destination; verify database readiness. |
| ESO and credentials | Configure IRSA and seed the application credential from CNPG into the intended AWS container; requires explicit value-transfer approval and protected output. |
| ALB and DNS | Preserve the live state-derived VPC override; separate the initial ALB controller from later application load balancers and DNS writes. |
| Monitoring | Account for monitoring resources and prerequisites; Root existence is not monitoring acceptance. |
| Failure and cleanup | Preserve state and partial outputs, stop foreground actions without automatic repair, and recognize controllers may continue reconciling. Plan teardown separately. |

The existing aws-dev wrapper also performs credential migration, ObjectStore
patching, readiness waits and DNS reconciliation. It cannot be used as a
Root-only test wrapper. This increment pins its source for review but never
invokes it. Existing Terraform, bootstrap and deploy wrappers are unchanged.

## Fresh read-only observation

Set `EXPECTED_MAIN` to the full post-merge main SHA, then run once:

```bash
python3 scripts/check-v0.11.9.3.6.7.5-aws-test-recovery-root-plan.py observe \
  --expected-main "$EXPECTED_MAIN" \
  --inputs "$ROOT_REVIEW_DIR/inputs.json" \
  --output-directory "$ROOT_REVIEW_DIR/preflight" \
  >"$ROOT_REVIEW_DIR/observe-result.json" \
  2>"$ROOT_REVIEW_DIR/observe-result.stderr"
```

The output directory must be new and have an owner-only persistent parent.
The preflight checks clean exact remote main, pinned repository inputs, local
state, recovery evidence, STS account, rehearsal EKS inventory, API CIDR/VPC,
metadata-container presence, isolated context and auth plugin, Kubernetes
readiness, Argo CD version/readiness, two IRSA annotations, ALB chart/target/
health and the absence of all other Applications including Root. It also
collects VPC EC2 and tag-matched volume inventories for private cost review.
Volume inventory is explicitly non-exhaustive and is not a billing audit.

All command stdout/stderr remain private. Only allowlisted aggregates and
hashes appear in the summary. Failure writes a sanitized stage marker and
stops; access denied or API failure never means a resource is absent. Neither
state nor kubeconfig is modified. No automatic retry or repair is performed.

  --plan "$ROOT_REVIEW_DIR/private-plan.json" \

  >"$ROOT_REVIEW_DIR/plan-check.json" \
  2>"$ROOT_REVIEW_DIR/plan-check.stderr"

`check-plan` is entirely offline and requires an observation no older than
15 minutes. Its result is design review only, not an execute token. Share the
sanitized results, exit codes and hashes; retain raw state, identifiers,
pricing evidence and logs privately. The future deployment executor must
recheck current main, live state, scope, budget and time immediately before
any separately approved mutation. A passed design checker alone is insufficient.
