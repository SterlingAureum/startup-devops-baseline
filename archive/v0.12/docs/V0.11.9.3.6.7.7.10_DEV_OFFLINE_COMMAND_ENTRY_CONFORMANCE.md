# v0.11.9.3.6.7.7.10 dev offline command-entry conformance

## Result

This increment adds a dev-only programmatic command-entry layer above the
v0.11.9.3.6.7.7.9 fixed fake transport and durable receipt store. It validates
the complete `verify` then separately confirmed `execute` control flow for all
eight phases without adding a CLI, environment reader, host clock, live private
file reader or real transport.

The implementation is bound to protected-main
`850720c1c15b6b26afa284a4e5c80ab0940318e9` and freezes the `.7.7.9` contract
and core byte hashes.

## Verify boundary

`verify` accepts one exact redacted request envelope. It reads only two canonical
JSON byte strings from a fixed in-memory reader: `approval` and `evidence`.
Their expected SHA-256 values, exact main, environment, phase, operation set,
receipt predecessor, proof clock and budget must all match.

The current UTC value comes from a concrete `FrozenClock`; no host clock is
consulted. Verify cannot receive a transport and writes no receipt. Its output
binds the reviewed input hashes, receipt predecessor, verify time, proof expiry
and execution end while keeping execution authority false.

## Execute boundary

`execute` requires three independently bound inputs: the same approval bytes,
the same evidence bytes and the canonical reviewed verify record. It requires
that record's exact SHA-256 and one phase-specific aws-dev offline confirmation.
It re-reads and revalidates every byte and the current receipt prefix before
the fixed fake transport can be called.

The command uses a second injected clock reading as completion time. Only after
all predecessor `.7.7.9` transport responses succeed can the inherited durable
store append one intent/receipt/completion triplet. A changed prefix, expired
verify, malformed input, response failure, late completion or pending receipt
store stops without automatic retry or repair.

## Closed dependency model

The command entry accepts only concrete instances of:

- `FrozenClock`, holding a fixed in-memory UTC sequence;
- `FixedPrivateInputReader`, holding canonical bytes under three closed names;
- `.7.7.9` `DevConformanceTransport`, the fixed fake only;
- `.7.7.9` `DurableReceiptStore`, the local append-only receipt store.

Subclasses and arbitrary path, endpoint or backend substitution are rejected.
No account ID, resource identity, credential, private path or payload is emitted
by success or failure reports.

## Offline evidence

Thirty-seven tests prove:

- the full eight-stage, 23-operation verify/execute/receipt chain;
- fresh clock, reader and store reconstruction at every stage;
- exact first and later predecessor receipts;
- strict request, approval, evidence, reviewed-verify and confirmation binding;
- expiry, byte drift, prefix drift, transport failure and pending-store stops;
- rejection of aws-test, aws-prod and dependency subclasses;
- absence of CLI, environment, host-clock, file-reader and network primitives.

The validator recursively replays `.7.7.9` and its complete predecessor chain.

## Authorization boundary and next step

This increment reads in-memory fixtures and writes only test receipt files. It
does not access live private evidence, AWS, Kubernetes or Terraform and does not
grant live execution authority to any environment.

The next increment may implement a separately reviewed dev-only local CLI
preflight prototype with strict real clock and private-file adapters while the
transport remains the fixed fake. Live transport integration and live mutation
would still require later, independently reviewed increments and approvals.
