# v0.11.9.3.6.7.7.7 三环境离线 Application freeze adapter

应用基线：`d9f9e96972a25f0a5894cd9c93ca018d27c28a96`。

本增量补齐 `.7.7.6` 明确记录的唯一离线阶段缺口：`freeze-applications`。
新增 adapter 使用 fixed fake transport 和 scripted clock，覆盖 aws-dev/aws-test/aws-prod，
不调用或修改任何 live executor。

## 精确两遍顺序

scope 必须包含一个 Root 和至少一个子 Application。Root 名称必须与显式环境匹配并位于
第一项，子 Application 名称唯一且按字典序排列。每个对象固定 namespace、UID、
resourceVersion、source/destination SHA-256、automated 状态、Argo finalizer、删除状态和
active operation 状态。

第一遍按 Root→子应用顺序，对每个对象重新观察并模拟移除 automated sync。全部对象
都已冻结后，第二遍按相同顺序：模拟移除一个已知 Argo Application finalizer，再模拟
删除该精确对象。这样先停止整棵应用树的持续协调，再移除 Application 对象，避免 Root
在子应用处理中重建对象。

以下情况全部 fail closed：

- active/terminating operation、deletion 已开始或 automated sync 已提前变化；
- Root/子应用缺失、额外、重复或顺序变化；
- UID、source/destination digest、相关对象或 resourceVersion 转换漂移；
- 未知或缺失的初始 Argo finalizer；
- identity、state、预算、proof、观察新鲜度、确认值或 journal 路径变化。

## intent、postcondition 与 receipt

每次 fake mutation 前都通过 `.7.7.3` journal 写入并 fsync intent，然后重新验证窗口与
观察年龄。明确失败写 terminal failure；未知响应、中断或后置条件不确定保留 pending。
已有 success/failed/pending journal 时不会再次调用 fake transport。

只有全部对象冻结、orphan、删除，最终 Application 数为零、active operation 为零且 state
不变后，才写 phase-complete 并生成 confirmed receipt。receipt 是仅含 step、environment、
confirmed 和 simulation_only 的 canonical synthetic JSON，不包含对象或私有标识。

新测试把该 receipt 依次交给 `.7.7.5` 五阶段和 `.7.7.4` 两阶段，按共同依赖顺序执行，
形成 dev/test/prod × 8 阶段的 24/24 成功矩阵。这证明离线 fixture receipt 链完整，不能
解释为 live 持久 handoff、真实 API 验证或执行授权。

## 保留边界

本版不实现 Kubernetes/AWS/Terraform transport、Secret value 读取、自动重试/修复或
prod live 操作。只模拟已审核的 Argo Application finalizer；ExternalSecret finalizer、
强制 Namespace/PV 清理和 backup/Secret 永久删除仍为 incident-only gap，不能从本版
推导通用权限。历史 aws-test teardown、scoped audit、批准、窗口和 marker 保持关闭。

下一步应先离线设计 versioned live transport、逐阶段批准命令和持久跨阶段 receipt
handoff，再决定是否迁移现有 dev/test executor。prod 仍需新的当前价格、预算、账户、
release、scope、proof 和人工批准。
