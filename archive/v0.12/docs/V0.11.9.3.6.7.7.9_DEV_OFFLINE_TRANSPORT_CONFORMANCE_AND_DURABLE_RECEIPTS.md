# v0.11.9.3.6.7.7.9 dev offline transport conformance and durable receipts

## Result

This increment implements the first executable migration-conformance slice for
`aws-dev`. It exercises all eight reviewed phases and all 23 closed operations
through one fixed fake transport, then persists terminal-success receipts with
real local Linux file operations. It does not implement or authorize a live
Kubernetes, AWS or Terraform backend.

The implementation is bound to protected-main
`2b117736fbc9152bc6f97a76783df90d0a727800` and reuses the exact transport,
approval and receipt schemas frozen by v0.11.9.3.6.7.7.8.

## Fixed transport boundary

The harness accepts only the concrete `DevConformanceTransport` class. Every
phase dispatches the predecessor's exact closed operation sequence and checks
canonical response bytes against an exact success envelope. Unknown operations,
missing or malformed responses, operation-set drift, wrong environment, stale
clocks and changed approval authority all stop before a receipt is appended.

The request envelope contains only schema, environment, phase, operation,
approval digest, predecessor receipt digest and a simulation marker. It does not
carry account IDs, resource IDs, credentials, endpoints or arbitrary commands.
`aws-test` and `aws-prod` are rejected by construction.

## Durable receipt protocol

Each ordered phase owns exactly three append-only files:

1. `intent` binds the environment, phase and future receipt digest.
2. `receipt` contains the canonical terminal-success receipt.
3. `completion` independently commits the receipt digest.

The containing directory must be an owned absolute directory with mode `0700`.
Every file must be owned, regular, single-linked and mode `0600`. Writes use
exclusive creation, canonical JSON, file `fsync` and directory `fsync`. Symbolic
links, hard links, unexpected files, gaps, noncanonical bytes, exact-main drift
and receipt-chain drift fail closed.

A partial triplet is a pending append. It blocks every subsequent run and is not
deleted, repaired or silently promoted. A complete triplet can be reloaded after
process restart, and its exact receipt SHA-256 becomes the next phase's required
predecessor.

## Failure and restart review

The offline suite injects one deterministic failure after each of twelve local
I/O boundaries spanning open, write, file-sync and directory-sync for the three
files. Every pre-completion failure preserves a blocked pending store. A valid
completion marker permits restart recovery, while any changed byte, mode, link,
phase, main or predecessor stops the chain.

Thirty-three tests cover the complete eight-stage/23-operation chain, restart at
every stage, exact approval and evidence binding, response failures, receipt
tampering and the twelve fault points. The predecessor `.7.7.8` validation chain
is replayed recursively.

## Authorization and effect boundary

This increment performs local private receipt-file writes only during tests. It:

- does not read live private evidence or the system clock;
- does not invoke a cloud, Kubernetes or Terraform transport;
- does not implement a live command entry point;
- does not read Secret values or grant retry/repair authority;
- does not modify historical live adapters or evidence;
- does not enable dev, test or prod live execution.

The next increment may design and test a dev-only offline command-entry layer
with injected clock and private-input readers. Any real transport integration,
live preflight, approval or execution remains a separate reviewed increment.
