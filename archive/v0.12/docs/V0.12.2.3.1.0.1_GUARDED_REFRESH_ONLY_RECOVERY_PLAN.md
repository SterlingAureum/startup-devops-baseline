# v0.12.2.3.1.0.1 Guarded Refresh-Only Recovery Plan

The v0.12.2.3.1 proof correctly stopped after Terraform reported seven
`resource_drift` entries. The real S3 lock contention succeeded, the holder
released its lock cleanly, and the saved ordinary plan returned detailed exit
code `0`. All 13 managed resource changes and every output change were
`no-op`, but the migrated state snapshot had not absorbed the first provider
refresh.

This recovery does not weaken the zero-drift proof gate and does not retry the
failed proof. It produces a separate `terraform plan -refresh-only` artifact
for human review. Applying that plan remains v0.12.2.3.1.0.2 scope.

## Exact reviewed incident

The command-free verifier binds the failed proof request, canonical state,
binary plan, JSON plan, text plan and exact resource-drift digest. It accepts
only these seven refresh entries:

- five `aws_iam_policy.root_state_access` instances: `tags`;
- `aws_kms_key.state`: `tags`;
- `aws_s3_bucket.state`: the reviewed legacy/computed policy, encryption,
  Bucket Key, versioning and tag fields.

For every entry, the refresh result must equal both sides of the corresponding
`no-op` resource change. The complete managed inventory must remain 13
addresses, outputs must remain no-op, and imports are forbidden. Raw drift
values remain private.

## Authority boundary

`verify` runs no AWS or Terraform command and writes no evidence. `execute`
requires a new protected-main-bound request, a fresh window, and:

```bash
export CONFIRM_BOOTSTRAP_REFRESH_ONLY_PLAN=produce-reviewed-bootstrap-refresh-only-plan
```

Execution may perform AWS identity and S3 reads, Terraform state pull/list,
one saved `terraform plan -refresh-only`, and `terraform show`. The plan must
return detailed exit code `2`, reproduce the exact seven-entry drift digest,
contain no `resource_changes`, retain the seven expected no-op output entries,
and leave canonical state bytes and the state-object history unchanged. One
temporary S3 lock version and one lock delete marker are expected. Unlike an
ordinary plan, a refresh-only plan represents the reviewed state updates in
`resource_drift`; an empty `resource_changes` array is therefore required.

Terraform init, apply, an ordinary plan, state push, destroy, IAM attachment,
direct lock writes, force unlock and automatic retry are prohibited.

## Private request and execution

Copy the example into the existing owner-readable private root, replace the
protected-main commit and AWS account placeholders, bind the exact failed
proof request/output paths, choose a new output path that does not exist, and
create an active approval interval no longer than one hour.

```bash
python3 scripts/execute-v0.12.2.3.1.0.1-bootstrap-refresh-only-plan.py verify \
  --private-refresh-plan-request "$REFRESH_PLAN_REQUEST_01"
```

After separate approval, use an isolated subshell with all prior proof,
migration, apply, destroy and state-push confirmations unset:

```bash
(
  unset CONFIRM_BOOTSTRAP_REMOTE_STATE_PROOF
  unset CONFIRM_STATE_BOOTSTRAP_PLAN
  unset CONFIRM_STATE_BOOTSTRAP_APPLY
  unset CONFIRM_STATE_BOOTSTRAP_RECOVERY
  unset CONFIRM_STATE_BOOTSTRAP_MIGRATION_PREFLIGHT
  unset CONFIRM_STATE_BOOTSTRAP_MIGRATION
  unset CONFIRM_STATE_BOOTSTRAP_IDENTITY_REBASE_RECOVERY
  unset CONFIRM_TERRAFORM_APPLY
  unset CONFIRM_TERRAFORM_DESTROY
  unset CONFIRM_STATE_PUSH

  export CONFIRM_BOOTSTRAP_REFRESH_ONLY_PLAN=produce-reviewed-bootstrap-refresh-only-plan

  python3 scripts/execute-v0.12.2.3.1.0.1-bootstrap-refresh-only-plan.py execute \
    --private-refresh-plan-request "$REFRESH_PLAN_REQUEST_01"
)
```

Human review must confirm the exact seven refresh entries, zero managed remote
actions, zero output changes, zero imports, unchanged canonical state and
clean lock release before v0.12.2.3.1.0.2 may authorize state reconciliation.
