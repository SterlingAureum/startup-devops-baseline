# v0.12.4.1.2 External Secrets Supportedness Repair Plan

## Outcome

This increment selects the exact three-hop External Secrets repair path and
defines the evidence required before any repository pin or live controller can
change. It is a static offline plan. It downloads no chart, changes no GitOps
declaration and grants no AWS, Kubernetes, Terraform or Argo CD authority.

The selected path is:

```text
2.8.0 -> 2.9.0 -> 2.10.0 -> 2.11.0
```

Each hop binds the matching application release (`v2.9.0`, `v2.10.0`,
`v2.11.0`) and Helm chart release (`helm-chart-2.9.0`,
`helm-chart-2.10.0`, `helm-chart-2.11.0`). Candidate selection is not version
mutation authority.

## Why the bridge releases remain necessary

The publisher supports only the current minor. As reviewed on 2026-09-29,
`2.11` is the supported line for Kubernetes 1.36. Lines `2.8`, `2.9` and `2.10`
are end-of-life, but the publisher strongly recommends upgrading one minor at
a time and validating outside production first.

Therefore `2.9.0` and `2.10.0` are required bridge releases, not acceptable
steady states. Each bridge must converge and pass its own evidence gate before
the next hop starts; it must not be skipped merely because it is already EOL.

| Line | Kubernetes review | Lifecycle on 2026-09-29 | Plan role |
| --- | --- | --- | --- |
| `2.8` | `1.35-1.36` | EOL 2026-08-07 | current repository source |
| `2.9` | `1.36` | EOL 2026-08-28 | required bridge |
| `2.10` | `1.36` | EOL 2026-09-18 | required bridge |
| `2.11` | `1.36` | supported until release of `2.12` | supported destination |

ESO and its Helm chart have separate release lifecycles. Matching version
numbers do not replace chart-package identity, digest and metadata proof.

## Frozen repository scope

The current GitOps application remains pinned to chart `2.8.0` with
`installCRDs: true`, server-side apply, namespace-scoped RBAC and
`scopedNamespace: startup-apps`. The chart does not create the service account;
the existing deployment flow injects the Terraform-derived IRSA annotation.

The repository contains exactly two namespaced `external-secrets.io/v1`
custom resources in this scope:

- one `SecretStore` using AWS Secrets Manager and IRSA; and
- one `ExternalSecret` that materializes only `DATABASE_URL` from
  `AWSCURRENT`.

ClusterSecretStore, ClusterExternalSecret, ClusterGenerator, ClusterPushSecret
and PushSecret processing remain disabled. No static AWS access key is stored
in the repository. Every render must preserve this least-privilege shape.

## Artifact and offline-render gate

Before a hop can change a GitOps pin, a separate artifact-proof increment must
obtain the publisher chart package and record, for all three candidates:

- the chart SHA-256;
- chart `name`, `version`, `appVersion` and `kubeVersion`;
- a deterministic render from the exact repository values and its SHA-256;
- the complete CRD inventory and hop-to-hop CRD diff;
- values/schema compatibility for every currently used value; and
- diffs for RBAC, webhook, deployments and service-account behavior.

Any missing value, new cluster-scoped permission, PushSecret capability,
unexpected service account, API removal, render warning or unexplained CRD
change blocks the hop. This increment intentionally captures no chart digest
and produces no render, because artifact acquisition and candidate selection
are separate review boundaries.

## Per-hop live qualification

Only after artifact proof and a separate GitOps change may a fresh live
approval cover one hop in one environment. The order is `aws-dev`, then
`aws-test`; aws-prod is not part of v0.12.4.1.2.

Each hop must verify:

1. server-side dry-run succeeds in the disposable environment;
2. Argo CD is Synced/Healthy and controller, webhook and cert-controller
   Deployments are ready;
3. IRSA and namespace-scoped RBAC remain exact;
4. SecretStore and ExternalSecret become Ready;
5. the `AWSCURRENT` refresh path works without reading or publishing secret
   values; and
6. logs, metrics, alerts and the rollback-or-forward-fix decision are recorded.

One hop is allowed per PR and per approval window. Progression is never
automatic and no EKS or other controller upgrade may share the window.

Rollback may target only the last qualified hop, requires fresh approval and
must remain compatible with the persisted APIs and CRDs. Direct Kubernetes
Secret mutation, automatic retry and automatic rollback remain forbidden.

## Gate and next checkpoint

Exact candidates are now selected, but the upgrade gate remains
`blocked-awaiting-artifact-and-render-proof`. The repository remains pinned to
`2.8.0`; no chart digest, render or CRD diff is claimed by this plan.
