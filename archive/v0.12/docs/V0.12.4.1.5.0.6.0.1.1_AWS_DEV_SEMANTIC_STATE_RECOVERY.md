# v0.12.4.1.5.0.6.0.1.1 AWS dev semantic-state recovery

The prior read-only recovery stopped because two `terraform state pull` JSON
documents had different raw SHA-256 values. Local evidence proves that serial,
lineage, 90 managed instances, 13 data instances, all 103 addresses, resource
instances, resource metadata and 39 outputs are identical. The only changed
top-level field is `check_results`.

Both documents contain 28 check-result entries and 56 `pass` statuses. After
recursively sorting the semantically unordered check collections, both produce
SHA-256 `cce879cf1dc7519f44b5a75d6802b9ef517712c1483688c0fc98184266ce11a1`.
No infrastructure or state drift was found.

## Recovery boundary

Command-free `verify` binds the stopped attempt-01 recovery request and output,
the original apply evidence, both raw state digests, exact state identity and
address inventory, and the normalized check-result digest and histograms.

After separate approval, `execute` may run only AWS identity, EKS status, S3
object-history and Terraform state/version reads. Live state must be exactly
equal after normalizing only `check_results`; all other state content retains
ordinary exact JSON equality. State list and state show must both match the
exact 103-address inventory, EKS must be `ACTIVE`, and state/lock history must
match the single successful apply lifecycle.

This checkpoint never executes Terraform init, plan, apply or destroy. It never
pushes or migrates state, mutates S3, force-unlocks, attaches IAM policy, runs a
Kubernetes command, reads secret values, retries, rolls back or cleans up.
