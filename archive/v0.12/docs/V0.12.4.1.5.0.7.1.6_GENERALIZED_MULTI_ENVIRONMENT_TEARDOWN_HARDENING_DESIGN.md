# v0.12.4.1.5.0.7.1.6 generalized multi-environment teardown hardening design

## Decision

The Terraform roots and modules are already structurally reusable across dev,
test and prod, but the completed aws-dev rehearsal proves only one live
environment. It does not certify the three-environment lifecycle.

The repository also contains two teardown generations that are not yet one
coherent path. The older dev/test shell entrypoint performs controller cleanup
and dependency convergence. The v0.12 guarded teardown applies a reviewed
saved plan but is aws-dev-specific. The final aws-dev cleanup required incident
recovery because the saved-plan path did not make post-cluster ENI and EKS
security-group convergence a planned lifecycle stage.

This checkpoint defines the future shared model. It is a design only: no
generalized executor is implemented and no live validation is claimed.

## Backend is outside environment teardown

The state-bootstrap root owns the versioned, KMS-encrypted S3 backend and
native lockfiles independently from every environment root. Normal environment
teardown must never delete the backend bucket, KMS key, state object, state
history, or persistent runtime-identity root.

A successful environment teardown writes an empty state. It does not delete
the state object. State-bootstrap already enforces `force_destroy = false` and
`prevent_destroy` on both the state bucket and KMS key. Backend retirement is a
separate future decommission operation with its own retention decision and
approval chain.

The environment state keys remain exact and independent:

| Environment | State key |
|---|---|
| aws-dev | `environments/dev/terraform.tfstate` |
| aws-test | `environments/test/terraform.tfstate` |
| aws-prod | `environments/prod/terraform.tfstate` |

These keys are declarations, not proof that every root has completed live
migration. Aws-dev has recorded S3 state and lock history. Aws-test must pass a
separately approved backend activation and migration checkpoint before its next
live create. Aws-prod keeps only its static key declaration in v0.12 and does
not require live backend activation.

The backend foundation and persistent runtime identities are intentional
shared control-plane resources. An environment residual-cost audit must report
them as protected exclusions, not delete them or misclassify them as leaked
environment resources.

## Environment policy matrix

| Environment | Live lifecycle target | Application backup policy | Required acceptance |
|---|---|---|---|
| aws-dev | Disposable after separate approval | Delete allowed | One clean create, qualify and teardown cycle |
| aws-test | Ephemeral after separate approval | Delete allowed | One dev-to-test promotion and test teardown cycle |
| aws-prod | Static/governance target in v0.12 | Delete rejected | Render, policy and command-free refusal only |

Shared Terraform structure is desirable. Governance must still differ. The
production root keeps backup deletion disabled and receives no live create or
destroy authority from this design.

## Two-wave teardown model

The implementation must replace the single opaque destroy attempt with an
ordered lifecycle:

1. Verify the private request without commands.
2. With separate approval, suspend reconciliation and remove controller-owned
   Kubernetes resources through their owning controllers.
3. Capture read-only Terraform, backend-history and cloud dependency evidence.
4. Create and review a saved first-wave plan that destroys non-network
   infrastructure while retaining the VPC network shell.
5. Apply only that exact plan under a separate approval.
6. After EKS is absent, inventory the retained VPC for ENIs, security groups,
   references, endpoints, gateways, load balancers and other dependencies.
7. If an exact safe orphan is present, require a new narrowly bound deletion
   approval. Unknown dependencies stop the flow.
8. Create a fresh network-only saved plan; never reuse the first-wave or a
   partially applied plan.
9. Review and separately approve application of that exact network plan.
10. Require empty state, environment absence and a separately scoped residual
    cost audit.

Terraform-managed resources remain Terraform-owned. Controller-owned resources
are removed through their controller. Only narrowly classified cloud-service
residue may receive direct deletion authority. Unknown identities never receive
automatic cleanup, retry or rollback.

## Validation strategy

The implementation checkpoint must first provide offline fixtures for all
three profiles and prove that environment identity, state key, backup policy,
plan scope and approval scope cannot cross environments.

Aws-test remote-state activation is a prerequisite to its live acceptance; it
cannot reuse the dev key, local state or a Terraform CLI workspace.

Before v0.12 closes, aws-dev must complete one clean end-to-end cycle without
an incident recovery package. Aws-test must then exercise the dev-to-test
promotion plus its own teardown. Aws-prod remains static or prod-like only; a
real production apply or destroy is not required to prove reusable modules.

If either live acceptance needs manual state editing, a reused partial plan,
an unknown dependency deletion or an incident recovery chain, generalized
acceptance has not passed.

## Audit and CI separation

Historical execution evidence remains a standalone, on-demand audit surface.
It is not a required CI check and private evidence is never loaded into CI.
After the shared teardown implementation exists, validators for active source
code may join normal quality gates because they protect current operational
behavior rather than replaying historical evidence.

This design validator itself is standalone and is not wired to a workflow or
the root CI validator. The checkpoint runs no AWS, Terraform or Kubernetes
command and grants no live authority.
