# v0.12.4.1.5.0.7.1 Guarded AWS dev teardown

This checkpoint skips the optional `.7` post-create qualification and provides
a short, fail-closed path for removing the disposable aws-dev environment. It
does not require `.7` to be rolled back: `.7` added only an offline/read-only
qualification entrypoint and did not alter Terraform infrastructure.

## Safety model

The executor has four phases. Both verification phases are command-free.

1. `verify-plan` binds clean protected `main`, the successful semantic recovery,
   the exact 103-address state (90 managed and 13 data), and a new private plan
   directory.
2. `plan` requires `CONFIRM_AWS_DEV_TEARDOWN_PLAN` and creates one saved
   `terraform plan -destroy`. It never runs `terraform init` or apply. The plan
   must delete exactly the 90 reviewed managed addresses, contain no drift or
   import, and complete one clean native lock lifecycle without changing state.
3. The operator reviews the private text/JSON plan and creates a separate
   destroy request containing every artifact digest and `humanReviewed: true`.
4. `verify-destroy` is command-free. `destroy` then requires
   `CONFIRM_AWS_DEV_TEARDOWN_DESTROY` and applies only the exact saved binary
   plan. It cannot create a replacement plan or use an unsaved destroy.

The plan approval lasts at most one hour, its review lifetime at most four
hours, and the separate destroy approval at most three hours without exceeding
the plan review deadline.

## Post-destroy boundary

Success requires Terraform to report exactly 90 destroyed, zero added, and
zero changed. The resulting state must contain zero managed instances; any
remaining data addresses must be a subset of the bound 13 data addresses.
The versioned S3 state object is preserved, no state delete marker is allowed,
and the Terraform lock must be cleanly released. Read-only checks must also
show that the EKS cluster and its VPC are absent.

If apply succeeds but any post-destroy check fails, preserve the private
evidence and do not retry automatically. A later recovery must be read-only;
rerunning the saved destroy plan is not authorized.

## Operator sequence

Create the private plan request from the example, using the new merged main
commit and current UTC windows, then run:

```bash
python3 scripts/execute-v0.12.4.1.5.0.7.1-guarded-aws-dev-teardown.py verify-plan \
  --private-teardown-plan-request "${TEARDOWN_PLAN_REQUEST}"

CONFIRM_AWS_DEV_TEARDOWN_PLAN=plan-reviewed-aws-dev-remote-state-teardown \
python3 scripts/execute-v0.12.4.1.5.0.7.1-guarded-aws-dev-teardown.py plan \
  --private-teardown-plan-request "${TEARDOWN_PLAN_REQUEST}"
```

Review `aws-dev-destroy-plan.txt`, copy the emitted hashes into a private
destroy request, keep `humanReviewed` true only after that review, and run:

```bash
python3 scripts/execute-v0.12.4.1.5.0.7.1-guarded-aws-dev-teardown.py verify-destroy \
  --private-destroy-request "${TEARDOWN_DESTROY_REQUEST}"

CONFIRM_AWS_DEV_TEARDOWN_DESTROY=destroy-reviewed-aws-dev-with-exact-saved-plan \
python3 scripts/execute-v0.12.4.1.5.0.7.1-guarded-aws-dev-teardown.py destroy \
  --private-destroy-request "${TEARDOWN_DESTROY_REQUEST}"
```

The first three commands cannot delete infrastructure. Only the final command
has destroy authority, and only for the reviewed saved plan.
