# v0.6.2 PostgreSQL High Availability

## Outcome

v0.6.2 moves PostgreSQL from the stable system Managed Node Group to dedicated
Karpenter On-Demand capacity and expands the existing CloudNativePG Cluster
from one instance to three.

## Capacity Contract

| Concern | Value |
|---|---|
| EC2NodeClass | `database` |
| NodePool | `database-ondemand` |
| Capacity type | On-Demand |
| Isolation | `dedicated=database:NoSchedule` |
| Architecture | Linux amd64 |
| Instance categories | c or m |
| Generation | 6 or newer |
| vCPU | 2 |
| Zones | `us-east-1a`, `us-east-1b` |
| Node ceiling | 3 |
| CPU ceiling | 6 |
| Memory ceiling | 24Gi |
| Consolidation | empty nodes only |
| Expiration | disabled |

The database EC2NodeClass reuses the existing Karpenter node IAM role, private
subnet discovery, cluster security group, and EKS access entry. No Terraform or
IAM change is required.

## PostgreSQL Contract

| Concern | Value |
|---|---|
| CloudNativePG | 1.30.0 |
| PostgreSQL | 17.10, pinned by immutable image digest |
| Instances | 3 |
| Roles | 1 primary and 2 replicas |
| Pod resources | 500m CPU and 1Gi memory, Guaranteed QoS |
| Data volume | one encrypted 20Gi gp3 EBS volume per instance |
| Node placement | three different database nodes |
| AZ placement | balanced `2+1` across two AZs |
| Synchronous method | `any` |
| Required acknowledgements | 1 standby |
| Data durability | `required` |

Required hostname anti-affinity prevents two PostgreSQL instances from sharing
one EC2 node. A `DoNotSchedule` topology spread constraint with `maxSkew: 1`
and `minDomains: 2` distributes the three instances across both development
Availability Zones. Required node affinity gives Karpenter the same two
eligible AZs declared by the database NodePool.

The VPC contains two private-subnet Availability Zones. Therefore three
instances cannot occupy three unique AZs; the intended cross-AZ layout is
`2+1`, with every instance still on a different node.

## Migration from v0.6.1

Argo CD first creates the database EC2NodeClass and NodePool. CloudNativePG then
creates two replicas, provisions their PVCs, and reconciles the original
primary onto database capacity. During convergence, inspect:

```bash
kubectl get application postgresql-baseline -n argocd
kubectl get nodepool database-ondemand
kubectl get nodeclaims
kubectl get cluster,pods,pvc -n data-platform -o wide
```

The migration may take several minutes while Karpenter launches three
On-Demand instances and EBS volumes attach. Do not delete the original Pod or
PVC to accelerate reconciliation.

## Validation

Run the normal, non-disruptive validation:

```bash
./scripts/validate-all.sh
```

For focused database diagnostics:

```bash
./scripts/validate-cloudnative-pg-persistence.sh
```

The database validator checks:

- three ready Pods with one primary and two replicas;
- three different `database-ondemand` nodes;
- coverage of both AZs with a maximum skew of one;
- three bound PVC/PV/EBS chains;
- encrypted gp3 type, size, IOPS, throughput, attachment state, and AZ;
- database services and generated credential Secret metadata;
- two streaming replicas and at least one synchronous standby.

Credential values are never decoded or printed.

## Controlled Replica Recreation

```bash
./scripts/run-cloudnative-pg-persistence-test.sh
```

After the operator types `restart-replica`, the script:

1. writes a marker through the current primary;
2. records one replica's Pod, PVC, PV, and EBS identities;
3. deletes only that replica Pod;
4. verifies that the primary Pod and role remain unchanged;
5. verifies reuse of the replica's PVC, PV, and EBS volume;
6. reads the replicated marker from the recreated replica.

The primary failover drill remains deferred to v0.6.5.

## Existing Karpenter Tests

The application On-Demand, Spot, and FIS tests now scope all NodeClaim checks
and cleanup operations to their selected NodePool. They do not require a
cluster-wide empty Karpenter baseline and cannot delete the persistent database
NodeClaims.

## Cost and Destruction

While deployed, v0.6.2 keeps three small On-Demand EC2 instances, three EC2
root volumes, and three 20Gi PostgreSQL data volumes. The database NodePool
does not consolidate active nodes.

The cleanup and destroy workflows delete the PostgreSQL Cluster and all data
PVCs before removing NodePools and EC2NodeClasses. The `gp3-cnpg` reclaim
policy is `Delete`, so all database EBS volumes are deleted. v0.6.2 has no
backup or restore path; export required data before confirming cleanup.

## Deferred

- restore and point-in-time recovery;
- primary failure and automated promotion drill;
- demo-api PostgreSQL integration.
