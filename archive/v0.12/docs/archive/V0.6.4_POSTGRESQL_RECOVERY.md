# v0.6.4 PostgreSQL Recovery and PITR

## Outcome

v0.6.4 proves that the v0.6.3 S3 base backups and WAL archive can restore
usable PostgreSQL data. Recovery is never performed in place: every drill
bootstraps a new CloudNativePG `Cluster`, validates its data, and deletes the
test-owned resources while the source cluster remains online.

## Recovery Contract

| Concern | Value |
|---|---|
| Source Cluster | `postgresql-baseline` |
| Recovery interface | Barman Cloud CNPG-I plugin `0.13.0` |
| Recovery source | `postgresql-baseline-backup` ObjectStore |
| Source server name | `postgresql-baseline` |
| Authentication | shared `postgresql-baseline` IRSA ServiceAccount |
| Latest recovery Cluster | `postgresql-recovery-latest` |
| PITR Cluster | `postgresql-recovery-pitr` |
| Recovery instances | one |
| Recovery storage | encrypted 20Gi `gp3-cnpg` PVC |
| Recovery capacity | one isolated On-Demand Karpenter node |
| Recovery NodePool | `database-recovery-ondemand` |
| Source impact | no deletion, restart, failover, or PVC replacement |

CloudNativePG recovery uses `bootstrap.recovery.source` and an
`externalClusters` plugin reference. PITR adds only
`bootstrap.recovery.recoveryTarget.targetTime`. Both clusters use
`serviceAccountName: postgresql-baseline`, a CloudNativePG 1.30 capability
that allows the existing IRSA identity to be shared without adding wildcard
subjects to the IAM trust policy.

## Data-integrity Scenario

The guarded test performs this sequence:

1. Record the source Cluster UID and three PVC/PV/EBS mappings.
2. Write a unique base marker and wait for its WAL segment in S3.
3. Create and complete a new plugin-based physical base backup.
4. Write a marker that PITR must preserve.
5. Capture a PostgreSQL UTC timestamp after that transaction commits.
6. Write a marker that PITR must exclude and wait for its WAL in S3.
7. Restore `postgresql-recovery-latest` and require all three markers.
8. Delete its Cluster, PVC, EBS volume, NodeClaim, and EC2 node.
9. Restore `postgresql-recovery-pitr` to the captured timestamp.
10. Require the base and preserved markers and reject the post-target marker.
11. Delete the second recovery stack.
12. Confirm the source UID, storage mappings, three ready instances, and source
    markers remain unchanged.

This distinguishes three independent claims:

- the base backup is readable;
- archived WAL can advance a restore to the latest state;
- WAL replay can stop at the requested timestamp without including a later
  committed transaction.

## Runtime Validation

Run the guarded recovery drill:

```bash
./scripts/run-cloudnative-pg-recovery-test.sh
```

Type:

```text
restore-and-cleanup
```

The test creates temporary On-Demand EC2 and EBS resources twice. It can take
several minutes for Karpenter to provision and consolidate the isolated
recovery node.

Expected final output:

```text
CloudNativePG latest recovery, PITR, data integrity, and cleanup validation passed.
```

Then confirm readiness and absence of residual recovery resources:

```bash
./scripts/validate-cloudnative-pg-recovery.sh
./scripts/validate-all.sh
```

Expected recovery validator output:

```text
CloudNativePG recovery and PITR readiness and cleanup validation passed.
```

## Safety Boundaries

- The test never deletes or patches `postgresql-baseline`.
- Recovery clusters do not enable WAL archiving into the source backup path.
- Cluster and NodePool names are fixed and checked before creation.
- Cleanup selectors are scoped to the two recovery cluster names and the
  recovery NodePool.
- A failure trap attempts to delete test-owned recovery resources.
- Source storage identity is compared before and after the drill.

The inserted validation rows remain in the source database as test evidence.
They are small and uniquely keyed by the UTC run identifier.
