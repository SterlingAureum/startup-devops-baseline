# v0.8.0 Security Supply Chain

## Scope

This increment completes the security-supply-chain half of v0.8.0. It extends
the runtime controls documented in `V0.8.0_WORKLOAD_HARDENING.md` without
introducing the Namespace, admission, network, secret-management, credential
rotation, or TLS controls assigned to later v0.8 increments.

## Security gates

The reusable quality-gate workflow now performs:

1. a full-history Gitleaks scan for committed credentials;
2. the existing shell, Helm, image-stage test, and workload-hardening
   validation; and
3. a Trivy HIGH/CRITICAL misconfiguration scan scoped to the demo-api Docker
   and Helm configuration.

The Trivy configuration gate is intentionally application-scoped in v0.8.0.
EKS endpoint, control-plane logging, and related Terraform hardening remain
part of v0.8.5, where the corresponding infrastructure findings can be fixed
and enabled as blocking controls rather than hidden by a broad ignore file.

## Safe image publication order

The image workflow uses the following order:

```text
reusable quality gates
  -> build and load local image candidate
  -> block fixable HIGH/CRITICAL image vulnerabilities
  -> generate SPDX JSON SBOM
  -> authenticate to GHCR
  -> push the scanned image tags
  -> resolve the registry digest
  -> publish image identity metadata
  -> upload the SBOM artifact
  -> attest build provenance
  -> attest the SBOM against the same digest
  -> allow the aws-dev Promotion PR job
```

The image scan sets `ignore-unfixed: true`. This means a HIGH/CRITICAL finding
blocks publication when the upstream package has a fix available. Findings
without an available fix remain visible without making the baseline
permanently unpublishable.

## Immutable workflow dependencies

Every external GitHub Action is pinned to a reviewed 40-character commit SHA.
The adjacent version comment preserves the human-readable release identity.
The security contract validator rejects:

- tag, branch, or short-SHA Action references;
- unreviewed Actions;
- unexpected revisions;
- pins without readable version comments; and
- unsafe build, scan, push, attestation, or promotion ordering.

## SBOM and attestations

Trivy generates an SPDX JSON document from the same locally loaded image that
passes the vulnerability gate. The workflow retains the document as an
artifact and uses `actions/attest` to bind it to the GHCR image digest.

The existing build-provenance attestation and the SBOM attestation therefore
share:

- the fully qualified image repository;
- the immutable registry digest;
- the source workflow identity; and
- short-lived OIDC-backed signing identity.

## Validation

Run:

```bash
./scripts/validate-demo-api-security-supply-chain.sh
./scripts/validate-ci-quality-gates.sh
```

The first command validates workflow pins and security ordering without
requiring network access or locally installed scanner binaries. The second
command includes that contract validation and the complete existing local
quality gates.

The Gitleaks and Trivy engines themselves execute in GitHub Actions. Before
marking v0.8.0 complete, both the pull-request `validate` workflow and the
feature-branch manual image-publish workflow must pass.
