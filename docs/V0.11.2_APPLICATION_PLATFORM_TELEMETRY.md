# v0.11.2 Application and Platform Telemetry

## Goal

v0.11.2 makes demo-api own its Prometheus discovery and exposes bounded
application signals that later dashboards, alerts, and SLOs can safely use. It
also defines release-correlation labels without changing the accepted v0.10
build, Promotion, rollback, or production-approval workflows.

This increment is offline implemented. Local and AWS live facts are not claimed
until the procedures below pass.

## Application-owned discovery

The active ServiceMonitor is rendered by:

```text
apps/demo-api/helm/templates/servicemonitor.yaml
```

The v0.11.1 `additionalServiceMonitors` compatibility entry has been removed
from the local and AWS monitoring Applications. kube-prometheus-stack owns the
metrics control plane and discovers ServiceMonitor resources; the application
owns its port, path, selector, limits, and correlation rules.

The following job names remain compatible with the existing Rollout query:

```text
demo-api
demo-api-stable
demo-api-canary
```

```promql
sum(up{job="demo-api-canary"})
```

## Bounded application metrics

| Metric | Labels | Purpose |
| --- | --- | --- |
| `demo_api_http_requests_total` | `method`, `route`, `status_class` | Traffic and errors |
| `demo_api_http_request_duration_seconds` | `method`, `route` | Request latency |
| `demo_api_dependency_checks_total` | `dependency`, `outcome` | PostgreSQL availability input |
| `demo_api_dependency_check_duration_seconds` | `dependency` | PostgreSQL check latency |

Methods are normalized to a fixed HTTP method set plus `OTHER`. Routes are
normalized to the six declared API routes plus `__unmatched__`. Status values
are grouped as HTTP classes. Dependency outcomes are `success`, `failure`, or
`disabled`.

Raw URLs, query strings, request bodies, Authorization values, database
parameters, user identifiers, and exception messages are never metric labels.

## Pod-derived release correlation

The authoritative release ID remains the v0.10 delivery contract value:

```text
demo-api-{sourceCommit12}-{imageDigest12}
```

The ServiceMonitor copies release metadata from the selected target Pod rather
than from the Service. This is required during a Canary: the stable Service can
still select an old ReplicaSet while the canary Service selects the new one.
Service metadata alone could incorrectly label both targets as the new release.

Every demo-api target receives:

```text
service_name
service_version
deployment_environment_name
platform_release_id
platform_source_commit
container_image_digest
```

AWS releases derive these values from the existing environment release file.
The disposable local profile uses `local-unavailable` and `local-unpinned`
sentinels and makes no production identity claim.

## Platform telemetry scope

v0.11.2 relies on the kube-prometheus-stack core targets introduced in
v0.11.1. The required platform inputs are:

```text
kube_pod_status_ready
kube_pod_container_resource_requests
node_cpu_seconds_total
node_memory_MemAvailable_bytes
prometheus_tsdb_head_series
```

Dedicated Argo CD, Argo Rollouts, CloudNativePG, and Karpenter controller
monitors are not added in this increment. Their exact endpoints are reviewed
with the v0.11.4 dashboards instead of enabling speculative third-party Chart
settings.

## Offline Validation

Run from the repository root:

```bash
./scripts/validate-v0.11.2-application-platform-telemetry.sh
./scripts/validate-ci-quality-gates.sh
```

The validator includes negative mutations for live-evidence claims, release-ID
drift, Service-derived Canary identity, unbounded labels, missing scrape limits,
and production automation expansion.

## Local Live Validation

Apply v0.11.1 and v0.11.2, sync the local root Application, and wait for
`monitoring` and `demo-api` to become Healthy. Then run:

```bash
./scripts/check-monitoring.sh
```

The check starts a temporary Prometheus port-forward when needed and validates:

- the application-owned ServiceMonitor;
- the stable and canary jobs;
- HTTP and dependency metric families;
- all six release-correlation target labels;
- the required core platform metric families.

Local live validation is required before a v0.11.2 tag.

## AWS Validation Boundary

AWS live validation may share one bounded aws-dev window with the pending
v0.11.1 metrics-foundation validation. It must prove:

- Prometheus remains private and scheduled on system capacity;
- the encrypted bounded gp3 PVC is Bound;
- demo-api stable and canary targets are Up;
- target labels match the aws-dev release file and running Pod identity;
- PostgreSQL success and controlled failure signals are present;
- EBS and other cost-bearing resources are absent after teardown.

aws-test and aws-prod qualification remain v0.11.8 work. The clean-room
dev/test/prod-live automated release and failure drill remains v0.11.9 work.

## Deferred

v0.11.2 does not enable Grafana, recording rules, Alertmanager, Loki, Alloy,
Tempo, OpenTelemetry SDKs, service SLOs, burn-rate alerts, or new Rollout SLI
gates. These remain v0.11.4 through v0.11.7 work. v0.11.3 adds only the local
feature-revision validation path needed to prove this increment safely.
