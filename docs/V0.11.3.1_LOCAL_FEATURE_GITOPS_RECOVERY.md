# v0.11.3.1 Local Feature GitOps Recovery

## Outcome

The local rollout recovered at revision 15. `Rollout/demo-api` became Healthy
with three ready replicas, and `AnalysisRun/demo-api-5b98fb8f59-15-2` completed
successfully with two measurements. Failed revision 14 was scaled down and may
remain in history; that is evidence, not an active fault.

The attempted command below did not cause the recovery because the Argo
Rollouts CLI requires the resource type:

```bash
# Invalid
kubectl argo rollouts retry demo-api -n startup-apps

# Valid, only when an aborted Rollout really needs retrying
kubectl argo rollouts retry rollout demo-api -n startup-apps
```

Revision 15 was created and reconciled after the feature configuration was
corrected. Do not attribute that recovery to the rejected retry command.

## What Failed

Three independent state relationships overlapped:

1. A historical live Helm parameter could keep
   `analysis.prometheus.address` different from the value in Git. Syncing a
   parent Application is not a reliable deletion mechanism for a child field
   that the parent manifest never declared.
2. `deploy-root-app.sh` previously applied an automated Root and disabled
   automation immediately afterward. Creation or apply could start an
   automatic operation before the manual sync, producing `another operation
   is already in progress`.
3. The feature branch intentionally keeps child Application manifests at
   `HEAD`. Syncing the Root after live child revisions are pinned therefore
   resets those children toward `HEAD`.

## Repair

- Manual Root mode is rendered without `spec.syncPolicy.automated` before the
  Application is created or applied.
- Every scripted Argo CD mutation waits for the prior Application operation to
  become idle; a sync is issued only when the Application is OutOfSync.
- Child automation is paused while revisions and local-image parameters are
  changed.
- Feature validation explicitly removes every unexpected `demo-api` Helm
  parameter and then asserts this exact allowlist:
  `image.pullPolicy`, `image.repository`, `image.tag`, and
  `release.applicationVersion`.
- HEAD restoration explicitly unsets every live Helm parameter, asserts the
  set is empty, and restores Root automation last.

## demo-api Configuration Dependency Map

| Layer | Source | Produces or controls | Depends on |
| --- | --- | --- | --- |
| Root GitOps | `clusters/local/root-app.yaml` | `startup-devops-root` | repository URL, Root revision, `clusters/local/platform` |
| Child GitOps | `clusters/local/platform/demo-api.yaml` | `Application/demo-api` | child revision, Helm path, destination namespace |
| Metrics platform | `clusters/local/platform/monitoring.yaml` | kube-prometheus-stack and Prometheus Service | `observability` namespace, chart release name |
| Chart defaults | `apps/demo-api/helm/values.yaml` | image, Rollout steps, services, analysis and telemetry settings | feature or HEAD revision selected by child Application |
| Local validation overrides | `deploy-local-feature-gitops.sh` | local image identity only | image already loaded into kind; exact Helm allowlist |
| Workload | `templates/rollout.yaml` | Rollout, ReplicaSets and Pods | image values, stable/canary Services, AnalysisTemplate |
| Traffic | `templates/service.yaml`, `templates/ingress.yaml` | stable/canary endpoints and ingress routing | selectors managed by Argo Rollouts |
| Metrics discovery | `templates/servicemonitor.yaml` | Prometheus scrape targets/jobs | Service labels, `/metrics`, Prometheus Operator |
| Canary gate | `templates/analysis-template.yaml` | AnalysisRun Prometheus query | Prometheus Service address and `demo-api-canary` target |

The critical runtime chain is:

```text
Git revision -> child Application -> Helm render -> Rollout/Services/ServiceMonitor
ServiceMonitor -> Prometheus scrape -> AnalysisRun query -> Rollout gate
```

The Root owns the child Application object, but the feature workflow
temporarily changes that live child. Therefore Root `OutOfSync / Healthy` is
expected until `restore-local-gitops-head.sh` returns every Application and
Helm parameter to the stable declaration.

## Acceptance

revision 22. v0.11.3.2 supersedes this acceptance checkpoint with a bounded
metric delay and fail-closed `len(result) > 0` guard. See
`docs/V0.11.3.2_PROMETHEUS_NO_DATA_HARDENING.md`.

Run the offline checks, then replay the feature workflow once from a clean
HEAD-restored state. Complete the retained manual Canary pause, run
`validate.sh` and `check-monitoring.sh`, and finally run
`restore-local-gitops-head.sh`. The patch changes no telemetry schema, Canary
strategy, AWS state, or production boundary.
