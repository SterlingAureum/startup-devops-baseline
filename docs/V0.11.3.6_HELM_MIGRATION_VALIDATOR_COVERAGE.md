# v0.11.3.6 Helm Migration Validator Coverage

## Finding

The complete quality gate exposed a stale path in
`scripts/validate-namespace-guardrails.sh`:

```text
clusters/local/platform/namespace-guardrails.yaml
```

v0.11.3.4 deliberately moved that Application into the local platform Helm
Chart:

```text
clusters/local/platform/templates/namespace-guardrails.yaml
```

The namespace guardrail resource was present. The failure was a validator
migration defect, not a missing runtime declaration. Reintroducing the old raw
file would create two declaration models and is explicitly rejected.

## Namespace Guardrail Contract

The validator now separates template ownership from stable values:

- the template must use `.Values.git.repoURL` and
  `.Values.git.targetRevision`;
- `clusters/local/platform/values.yaml` must keep the stable revision at
  `HEAD`;
- the old raw local Application must remain absent;
- AWS guardrail, demo-api, and PostgreSQL Applications must retain `main`.

This reflects the rendered Helm model instead of looking for a literal `HEAD`
inside a template.

## Recursive Admission Boundary

The application admission-policy validator previously scanned only YAML files
directly under `clusters/local/platform`. After the Helm migration, that scan
would not detect a forbidden local admission-policy Application placed under
`templates/`.

The scan is now recursive. A nested
`application-admission-policies.yaml` remains forbidden because local kind
acceptance uses tag-loaded images while the AWS policy requires immutable image
digests.

## Regression Tests

The v0.11.3.6 validator runs both corrected historical contracts and executes
two negative fixtures:

1. a reintroduced raw local namespace guardrail Application must fail;
2. a nested local admission-policy Application must fail.

Run:

```bash
./scripts/validate-v0.11.3.6-helm-migration-validator-coverage.sh
./scripts/validate-ci-quality-gates.sh
```

The complete quality gate remains mandatory in an environment with Docker,
Helm, and the repository's full CI toolchain.

## Application Sequence

This increment is designed to be applied directly on top of the already
applied but uncommitted v0.11.3.5 increment. Validate both increments, then
commit and push them together before running the v0.11.3.5 live recovery
sequence.

## Boundary

This repair changes validation logic and documentation only. It changes no
namespace resource, admission policy, platform Chart, demo-api workload,
telemetry, Canary behavior, AWS desired state, release orchestrator, or
production automation.
