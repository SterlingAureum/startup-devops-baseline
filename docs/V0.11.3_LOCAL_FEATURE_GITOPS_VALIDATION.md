# v0.11.3 Local Feature GitOps Validation

## Purpose and Successor Repairs

v0.11.3 introduced a reversible local feature-revision workflow after the
v0.11.2 live check exposed a split state: Root read the feature branch while
`demo-api` still read `HEAD`. The original workflow temporarily patched child
Applications and accepted Root `OutOfSync` as a bounded state.

Subsequent live replay produced three focused repairs:

- v0.11.3.1 removed stale child Helm parameters and serialized operations;
- v0.11.3.2 hardened the Prometheus Canary gate against empty vectors;
- v0.11.3.3 added bounded retry for the Argo CD server-side operation lock;
- v0.11.3.4 replaced live child overrides with one declarative Root-rendered
  revision and local-image configuration.
- v0.11.3.5 added remote source-content preflight and separated pre-merge
  feature baseline restoration from post-merge HEAD restoration.

This document describes the current v0.11.3.5 execution model while retaining
the original v0.11.3 validation objective.

## Stable Mode

The Root and same-repository child Applications use `HEAD`. The local platform
Helm Chart renders `demo-api` parameters as an explicit empty list. Root and
child automation are enabled and Argo CD owns the complete desired state.

Tracked active values never contain a feature branch or SHA.

## Feature-Validation Mode

The operator supplies:

```text
TARGET_REVISION=feature/v0.11-observability-sre-baseline
```

The workflow:

1. resolves the remote branch once to a full commit SHA;
2. requires the local checkout to be that commit with no tracked changes;
3. renders the Root source revision and `git.targetRevision` with that SHA;
4. renders the exact four local-image parameters into `Application/demo-api`;
5. applies the Root in manual mode and syncs it;
6. synchronizes the two same-repository children;
7. asserts Root and both children declare and resolve the same SHA;
8. verifies Chart, ServiceMonitor, Prometheus address, and Root ownership.

The Root remains manual but must be `Synced`. A Root resync is safe because the
Root desired state already contains the feature SHA and local-image values. It
no longer resets children to `HEAD`.

No telemetry source configuration is overridden. The Chart version,
ServiceMonitor, AnalysisTemplate, and Prometheus address continue to come from
the selected Git commit.

## Prerequisites

Commit and push the exact feature source before deployment:

```bash
git status --short
git push origin feature/v0.11-observability-sre-baseline

IMAGE_TAG=v0.11.3-local \
  ./scripts/build-load-demo-api-image.sh
```

The working tree must contain no tracked changes, and the `argocd` CLI must be
authenticated to the local API.

## Deploy and Verify

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_TAG=v0.11.3-local \
  ./scripts/deploy-local-feature-gitops.sh
```

Expected output includes the requested branch, resolved commit SHA, Chart
`demo-api-0.5.1`, local image, and Root `Synced` status.

Inspect source identity directly:

```bash
kubectl -n argocd get applications \
  startup-devops-root namespace-guardrails demo-api \
  -o custom-columns='NAME:.metadata.name,TARGET:.spec.source.targetRevision,RESOLVED:.status.sync.revision,SYNC:.status.sync.status,HEALTH:.status.health.status'
```

All three target and resolved revisions must be the same full commit SHA.

During a retained manual Canary pause, `demo-api` and possibly the Root may
report `Suspended`; source sync must remain `Synced`.

## Manual Canary Completion

Confirm the latest AnalysisRun is `Successful`:

```bash
kubectl -n startup-apps get analysisrun \
  --sort-by=.metadata.creationTimestamp

kubectl argo rollouts get rollout demo-api \
  -n startup-apps
```

Then perform the retained human-controlled promotion:

```bash
kubectl argo rollouts promote demo-api \
  -n startup-apps
```

Do not use `promote --full`. For an actually aborted Rollout, the valid retry
syntax is:

```bash
kubectl argo rollouts retry rollout demo-api -n startup-apps
```

Complete local acceptance with:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
```

## Restore Before Merge

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
  ./scripts/restore-local-feature-baseline.sh
```

Pre-merge restoration resolves the remote feature branch to one full SHA,
renders Root and children at that SHA, disables local-image mode, renders the
demo-api parameter list explicitly empty, synchronizes Root and children, and
restores Root automation last. It performs no direct child `set` or `unset`
operation.

Required restored state:

```text
startup-devops-root    <feature-sha>  Synced
namespace-guardrails   <feature-sha>  Synced
demo-api               <feature-sha>  Synced
demo-api parameters          empty
Root prune/selfHeal           true/true
```

After the platform Helm Chart reaches remote HEAD, run
`./scripts/restore-local-gitops-head.sh` and require the same state with `HEAD`
as the declared revision.

## Acceptance Boundary

Acceptance requires offline validators, Helm lint/render in the quality gate,
one live feature deployment, successful Canary analysis and manual completion,
runtime and monitoring checks, pre-merge feature baseline restoration, and
post-merge HEAD restoration. It requires no AWS
environment and changes no release-orchestration or production boundary.

See `docs/V0.11.3.5_PRE_MERGE_BASELINE_RESTORATION.md` for the revision content
preflight and exact restoration boundary.
