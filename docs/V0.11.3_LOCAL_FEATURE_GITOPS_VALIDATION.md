# v0.11.3 Local Feature GitOps Validation

## Purpose

v0.11.3 makes local feature-branch acceptance reproducible without committing
a feature revision into an active Argo CD declaration. It was added after the
v0.11.2 live check exposed a split state:

- the Root Application read `feature/v0.11-observability-sre-baseline`;
- the `demo-api` child Application still read `HEAD`;
- syncing the Root restored a temporary child override to `HEAD`;
- the cluster therefore remained on Chart `0.4.0` and had no application-owned
  ServiceMonitor even though the local checkout contained Chart `0.5.0`.

The fix is an explicit, reversible runtime validation mode. The tracked local
manifests remain `HEAD` so the repository does not retain a stale feature name.

## State Model

### Stable mode

The Root and same-repository child Applications use `HEAD`, automated sync and
self-heal are enabled, and Argo CD owns the complete desired state.

### Feature-validation mode

The Root is set to the requested feature revision and changed to manual sync.
It is synced once to create the child Applications. The same-repository child
Applications are then set to that feature revision, and `demo-api` receives
only the local image identity overrides.

The telemetry source configuration is not overridden. Chart version,
ServiceMonitor creation and the AnalysisTemplate Prometheus address must come
from Git and are checked after sync.

After the child revisions are overridden, the Root Application becomes
OutOfSync while remaining Healthy. This is expected: the feature branch keeps
the child declarations at `HEAD`, while the live child Applications temporarily
use the feature revision. Do not sync the Root Application again during this
mode.

## Prerequisites

The feature branch must be pushed, the kind cluster and Argo CD must be
available, and the local image must already be loaded:

```bash
git push origin feature/v0.11-observability-sre-baseline

IMAGE_TAG=v0.11.3-local \
  ./scripts/build-load-demo-api-image.sh
```

The `argocd` CLI must be authenticated to the local Argo CD API.

## Deploy and Verify the Feature Revision

Run from the repository root:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_TAG=v0.11.3-local \
  ./scripts/deploy-local-feature-gitops.sh
```

The script:

1. deploys the Root at `TARGET_REVISION` with manual sync;
2. syncs the Root exactly once;
3. pins `namespace-guardrails` and `demo-api` to the same revision;
4. injects the already-loaded local image with `pullPolicy=Never`;
5. checks all Application revisions and disabled Root automation;
6. checks the deployed Chart against the local `Chart.yaml`;
7. checks that `ServiceMonitor/demo-api` exists;
8. checks the Git-sourced Prometheus address.

It does not change tracked YAML, publish an image, contact AWS, progress the
Canary, use full promotion, or change a release-orchestration workflow.

## Manual Canary Completion

`demo-api` may show `Synced / Suspended` at the indefinite 50 percent pause.
Confirm that the latest AnalysisRun is `Successful`:

```bash
kubectl -n startup-apps get analysisrun \
  --sort-by=.metadata.creationTimestamp

kubectl argo rollouts get rollout demo-api \
  -n startup-apps
```

Then perform the retained human-controlled promotion:

```bash
kubectl argo rollouts promote demo-api \
  -n startup-apps
```

Do not use `promote --full`; that would bypass the remaining step sequence.

Complete local acceptance with:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
```

## Expected Argo CD State

During feature validation:

```text
startup-devops-root  OutOfSync  Healthy
demo-api             Synced     Suspended or Healthy
monitoring           Synced     Healthy
```

The Root OutOfSync condition is deliberate and bounded. A synced and healthy
feature child plus the exact Git revision, Chart, ServiceMonitor and metrics
checks are the acceptance facts.

## Restore the Stable Declaration

After testing, restore `HEAD`, automated sync and Root self-heal:

```bash
./scripts/restore-local-gitops-head.sh
```

This Root sync also removes the live feature revision and local Helm image
parameters from the child Applications. The restored workload then follows the
image identity declared by `HEAD`.

## Acceptance Boundary

The v0.11.3 tag requires an offline validator pass and one live local execution
of deploy, manual Canary completion, telemetry checks and HEAD restoration.
This increment requires no AWS environment and claims no production evidence.
