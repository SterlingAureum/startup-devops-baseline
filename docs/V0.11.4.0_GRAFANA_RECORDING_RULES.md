# v0.11.4.0 Grafana and Recording Rules

## Goal

v0.11.4.0 converts the bounded demo-api telemetry delivered in v0.11.2 into
the first stable operator query and visualization layer. It enables a private,
GitOps-managed Grafana instance, adds version-controlled recording rules, and
provisions one service overview Dashboard without changing the release,
Canary, alerting, or production-approval model.

The machine-readable contract is:

```text
delivery/contracts/v0.11.4.0-grafana-recording-rules.json
```

## Ownership Model

The pinned `kube-prometheus-stack` release continues to own Prometheus and now
owns the Grafana runtime. Repository-owned views are deployed by a separate
Helm Chart:

```text
platform/observability/helm
```

The `observability-views` Argo CD Application installs Dashboard ConfigMaps and
PrometheusRule resources in the `observability` Namespace. This prevents large
Dashboard JSON documents from being copied into the external Chart values.

Local feature validation treats `observability-views` as a same-repository
child. Root, namespace guardrails, demo-api, and observability views must use
the same resolved full commit SHA. Stable local declarations remain `HEAD` and
AWS declarations remain `main`.

## Grafana Profile

Grafana is enabled in local and AWS manifests with:

- no public Ingress, LoadBalancer, or NodePort;
- a ClusterIP Service;
- anonymous access and self-sign-up disabled;
- generated administrator credentials stored in a Kubernetes Secret;
- no committed plaintext administrator password;
- default bundled Dashboards disabled;
- Dashboard sidecar discovery restricted to labeled ConfigMaps in the
  `observability` Namespace;
- a stable Prometheus datasource UID of `prometheus`;
- bounded CPU and memory resources;
- no persistent Grafana database, because accepted Dashboards are recreated
  from Git;
- system-capacity placement in AWS;
- an explicit cluster-only NetworkPolicy.

Operators access local Grafana through port-forwarding rather than a public
endpoint.

## Service Overview Dashboard

The first Dashboard is:

```text
platform/observability/helm/dashboards/service-overview.json
```

Its immutable UID is:

```text
startup-devops-service-overview
```

It displays:

- HTTP request rate;
- HTTP success ratio;
- P50, P95, and P99 request latency;
- PostgreSQL dependency success ratio;
- active environment, service version, and release identity.

The only first-increment variables are `environment` and `release`. Pod names,
Pod UIDs, container IDs, trace IDs, raw URLs, request IDs, and other unbounded
dimensions are not service aggregation controls.

## Recording Rules

Nine `demo_api:` recording rules provide the query layer used by the
Dashboard. They retain the bounded environment, service, service version, and
release dimensions already provided by application-owned discovery.

Missing raw metrics remain missing. Rules do not use `or vector(0)` to convert
absence into a healthy value. The dependency success denominator excludes the
`disabled` outcome so disabled checks do not appear successful.

This increment contains only `record:` rules. It contains no `alert:` rules,
SLO target, error budget, or burn-rate calculation.

## Offline Validation

Run:

```bash
./scripts/validate-v0.11.4.0-grafana-recording-rules.sh
./scripts/validate-ci-quality-gates.sh
```

The focused validator checks the Chart, Dashboard JSON, recording-rule names,
Grafana security and resource settings, local/AWS Application sources, AWS
overlay identities, same-repository feature inheritance, CODEOWNERS, and
negative contract mutations.

The complete quality gate additionally requires the repository's pinned Helm
and Docker validation toolchain.

## Local Live Acceptance

Commit and push the feature branch, deploy the immutable feature revision, and
complete the normal demo-api Canary validation. Then run:

```bash
./scripts/check-observability-views.sh
```

The script:

1. requires `monitoring` and `observability-views` to be Healthy and Synced;
2. verifies Grafana, the PrometheusRule, and Dashboard ConfigMap;
3. generates bounded `/health` and `/ready` traffic;
4. waits for scrape and rule evaluation;
5. verifies all nine rules are loaded;
6. requires the core service rules to return data;
7. verifies the Grafana datasource and immutable Dashboard through the Grafana
   API.

If the cluster or rule group was just created, increase the bounded warm-up:

```bash
RULE_WARMUP_SECONDS=90 ./scripts/check-observability-views.sh
```

After acceptance, restore the neutral feature baseline:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
  ./scripts/restore-local-feature-baseline.sh
```

The restored Root, namespace guardrails, demo-api, and observability views must
all declare and resolve the same feature commit.

## Deferred

v0.11.4.0 does not add Alertmanager, actionable alerts, controller-specific
monitors, centralized logs, tracing, SLOs, burn-rate alerts, Kubecost, AWS
Billing integration, real currency cost claims, or a new Rollout analysis
gate. Delivery/data/platform/capacity views continue in v0.11.4.1 and resource
efficiency plus no-data hardening continue in v0.11.4.2. Formal AWS
observability evidence remains v0.11.8 work.
