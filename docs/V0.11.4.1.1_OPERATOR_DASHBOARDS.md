# v0.11.4.1.1 Operator Dashboards

## Goal

Turn the accepted Delivery, Data, and Platform recording rules into immutable,
Git-provisioned operator views without expanding the telemetry, alerting, or
automation boundary.

## Dashboard inventory

The observability views Chart now provisions four Dashboard ConfigMaps:

| Dashboard | UID | Purpose |
| --- | --- | --- |
| Service Overview | `startup-devops-service-overview` | Existing application traffic, latency, dependency, and release view |
| Delivery Overview | `startup-devops-delivery-overview` | Argo CD and Argo Rollouts reconciliation and readiness |
| Data Overview | `startup-devops-data-overview` | demo-api dependency checks and conditional CloudNativePG health |
| Platform Overview | `startup-devops-platform-overview` | Deployment readiness, restarts, and Prometheus target health |

All Dashboard JSON is stored under
`platform/observability/helm/dashboards`, labeled for Grafana sidecar discovery,
uses datasource UID `prometheus`, and sets `editable=false`.

## Query ownership

The three new Dashboards query only the twenty-one recording rules accepted in
v0.11.4.1.0. They do not query raw Argo CD, Argo Rollouts, CloudNativePG,
kube-state-metrics, or Prometheus target metrics directly.

This separation keeps component-specific names and aggregation policy in the
recording-rule layer. A future component upgrade can update one rule contract
without rewriting every panel.

## Local and AWS Data behavior

The Data Overview always requires the demo-api dependency rule. CloudNativePG
panels are present in every profile, but their descriptions state that runtime
data is conditional on the AWS PodMonitor profile.

Local acceptance permits those four CloudNativePG panels to show no-data. It
does not synthesize zero and does not enable local CloudNativePG monitoring to
make the Dashboard appear healthy. AWS profile acceptance requires the four
CloudNativePG rules to return data; formal environment evidence remains in
v0.11.8.

## Live acceptance

After committing, pushing, and deploying the exact feature revision, run:

```bash
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-controller-metrics.sh
PROFILE=local ./scripts/check-operator-dashboards.sh
```

The operator Dashboard check:

1. verifies the monitoring and observability Applications are Synced and
   Healthy;
2. verifies all four labeled Dashboard ConfigMaps;
3. generates bounded demo-api dependency traffic;
4. checks required Delivery, Data, and Platform rule results;
5. treats local CloudNativePG no-data as an explicit informational condition;
6. verifies every Dashboard through the Grafana API and rejects editable UI
   state.

The Grafana sidecar watches Dashboard ConfigMaps, so this increment does not
require a Grafana Deployment restart. A zero-replica historical Grafana
ReplicaSet remains normal rollback history.

## AWS profile

When an AWS environment is running, use:

```bash
PROFILE=aws AWS_ENVIRONMENT=aws-dev \
  ./scripts/check-operator-dashboards.sh
```

The AWS profile requires the CloudNativePG recording-rule results. This script
does not create an environment, change a Rollout, or write to production.

## Boundary

This increment adds three Dashboards and Chart metadata only. It adds no raw
metric query, recording rule, monitor, alert, Alertmanager route, log backend,
trace backend, SLO, capacity or cost panel, Grafana exposure, persistence,
Canary change, AWS desired-state mutation, or production automation.

Capacity and resource-efficiency views plus broader conditional no-data
hardening remain v0.11.4.2.
