# v0.11.4.2.1 Capacity and Resource Efficiency Dashboard

## Goal

Turn the twenty capacity and efficiency recording rules accepted in
v0.11.4.2.0 into one immutable, Git-provisioned operator Dashboard without
changing the signal, monitoring, alerting, scaling, cost, or release boundary.

## Dashboard identity

```text
File: platform/observability/helm/dashboards/capacity-overview.json
UID: startup-devops-capacity-overview
Title: Startup DevOps / Capacity & Efficiency Overview
```

The observability views Chart now provisions five Dashboard ConfigMaps. The
Service, Delivery, Data, and Platform Dashboard UIDs and panel inventories are
preserved. The new Dashboard sets `editable=false`, uses datasource UID
`prometheus`, refreshes every thirty seconds, and defaults to the last hour.

## Panel inventory

| Panel | Operator question |
| --- | --- |
| CPU Allocatable | How much node CPU is allocatable? |
| Memory Allocatable | How much node memory is allocatable? |
| Pod Capacity Utilization | What fraction of Pod capacity is running? |
| CPU Requested / Allocatable | How much allocatable CPU is reserved by active containers? |
| Memory Requested / Allocatable | How much allocatable memory is reserved? |
| Active Containers | How many active containers are in the selected namespaces? |
| Cluster CPU Reservation Proxy | How do CPU requests and limits compare with allocatable CPU? |
| Cluster Memory Reservation Proxy | How do memory requests and limits compare with allocatable memory? |
| Running Pods and Pod Capacity | How does running Pod count compare with allocatable Pod capacity? |
| Namespace CPU Efficiency | How do CPU usage, requests, and their ratio compare by namespace? |
| Namespace Memory Efficiency | How do memory working set, requests, and their ratio compare by namespace? |
| Namespace Request Coverage | Which active containers omit positive CPU or memory requests? |

The `namespace` variable is derived from
`efficiency:namespace_active_containers:count` and supports one, multiple, or
all observed namespaces.

## Query ownership

Every Dashboard expression and variable query uses only the twenty
`capacity:*` and `efficiency:*` recording rules accepted in v0.11.4.2.0. All
twenty accepted rules are consumed. The Dashboard does not query raw `kube_*`,
`container_*`, or `node_*` metrics.

This boundary keeps kube-state-metrics and cAdvisor labels, active Pod
semantics, aggregation, and missing-data policy in the recording-rule layer.

## Interpretation boundary

Requests and limits are container reservation proxies. They are not exact
scheduler headroom and do not include every scheduling constraint, Pod
overhead, init-container maximum, topology rule, taint, fragmentation effect,
or instance launch delay.

Usage-to-request ratios are efficiency indicators, not recommendations to
change requests automatically. A ratio exists only when the namespace has a
positive request total.

Missing-request zeroes are scoped to observed active containers. Absent source
inventory remains no-data; the Dashboard adds no global `or vector(0)`.

Allocatable resources, requests, limits, and usage are not currency cost. The
Dashboard contains no price, chargeback, saving, or spend claim.

## Live acceptance

After committing, pushing, and deploying the exact feature revision, run:

```bash
./scripts/check-monitoring.sh
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-capacity-signals.sh
PROFILE=local ./scripts/check-capacity-dashboard.sh
```

The Dashboard check verifies:

1. the monitoring and observability Applications are Synced and Healthy;
2. all five labeled Dashboard ConfigMaps exist;
3. the capacity PrometheusRule exists and representative rule-backed data is
   finite;
4. all five Dashboard UIDs are available through the Grafana API;
5. every Dashboard remains immutable with its accepted panel count;
6. the Capacity Dashboard keeps exactly one `namespace` variable and its
   capacity and efficiency tags.

For an already-running AWS environment:

```bash
PROFILE=aws AWS_ENVIRONMENT=aws-dev \
  ./scripts/check-capacity-dashboard.sh
```

The script creates no environment and performs no production write. Formal
AWS evidence remains v0.11.8 work.

## Clean local replay

After this increment passes normal local acceptance, v0.11.4.2 closes with one
clean feature-revision replay from the neutral pre-merge baseline. The replay
must verify all monitoring, operator Dashboard, capacity signal, and Capacity
Dashboard checks before restoring the feature baseline again.

A new repair version is required only if that replay exposes a real contract,
script, or reproducibility defect.

## Boundary

This increment adds one Dashboard and Chart metadata only. It adds no recording
rule, monitor, exporter, alert, Alertmanager route, automatic scaling, Karpenter
policy, Kubecost, AWS Billing integration, currency-cost claim, Canary change,
AWS desired-state mutation, or production automation.
