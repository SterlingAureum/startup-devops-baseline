# v0.11.5.0 Alertmanager and Alerting Policy Foundation

## Purpose

Enable one environment-local Alertmanager for every existing monitoring
profile and establish the routing, inhibition, storage, security, and
acceptance contracts required before repository-owned actionable alert rules
are added.

This increment separates Alertmanager runtime acceptance from alert-expression
acceptance. v0.11.5.0 proves the Prometheus-to-Alertmanager control path.
v0.11.5.1 will add actionable rules and version-controlled Runbooks, and
v0.11.5.2 will exercise firing, routing, inhibition, recovery, and the
environment-owned notification integration boundary.

## Architecture and ownership

Each environment owns an independent runtime:

```text
local Prometheus    -> local Alertmanager
aws-dev Prometheus  -> aws-dev Alertmanager
aws-test Prometheus -> aws-test Alertmanager
aws-prod Prometheus -> aws-prod Alertmanager
```

The `monitoring` Application and its pinned kube-prometheus-stack `88.5.0`
values own the Alertmanager runtime and global configuration. The
`platform/observability/helm` Chart remains the owner of repository
PrometheusRule resources and is intentionally unchanged in this increment.

No central Alertmanager or cross-environment silence state is introduced.
Configuration is shared through Git, while active alerts, silences,
notification logs, and storage remain environment-local.

The global route is configured directly in kube-prometheus-stack values.
`AlertmanagerConfig` custom resources are not added because the current
baseline has one platform owner and does not need namespace-tenant route
merging.

## Routing contract

The root route uses:

```text
default receiver: platform-observation
group_by: environment, cluster, component, alert_family
group_wait: 30s
group_interval: 5m
repeat_interval: 4h
```

Two child routes select the only accepted initial severities:

```text
severity="critical" -> critical-observation
severity="warning"  -> warning-observation
```

All three receivers are observation-only in v0.11.5.0. They contain no Slack,
email, PagerDuty, SNS, webhook, or other external delivery configuration. The
repository therefore claims routing visibility, not external notification
delivery.

Future alert rules must provide these labels:

```text
severity
environment
cluster
component
alert_family
promotion_blocking
```

The first five are routing and inhibition inputs. `promotion_blocking` is a
reviewed policy label for later qualification and Rollout integration; it does
not change a delivery gate in v0.11.5.0.

## Inhibition policy

A critical alert inhibits a warning alert only when both alerts have equal:

```text
environment
cluster
component
alert_family
```

The explicit `alert_family` label prevents an unrelated critical alert from
silencing every warning in one Namespace or component. Default
kube-prometheus-stack rules remain disabled, and all future repository alerts
must satisfy the label contract before the inhibition drill is accepted.

## Runtime profiles

| Environment | Replicas | Retention | Storage | Claim |
| --- | ---: | ---: | --- | --- |
| local | 1 | 6h | bounded 512Mi emptyDir | functional development |
| aws-dev | 1 | 24h | encrypted 2Gi gp3 PVC | cost-aware development |
| aws-test | 1 | 48h | encrypted 2Gi gp3 PVC | controlled SRE validation |
| aws-prod | 1 | 168h | encrypted 5Gi gp3 PVC | declared production profile, not HA |

The AWS volumes use the dedicated
`gp3-observability-alertmanager` StorageClass with environment-specific tags
and `Component=observability-alertmanager`. This avoids assigning the existing
Prometheus component tag to Alertmanager volumes.

Alertmanager persists silences and notification-log state. Prometheus
continues to resend firing alerts, so the small bounded profile does not claim
long-term metric retention.

All profiles use one replica. High availability, multi-replica gossip
evidence, topology spread, and production disruption testing remain part of
the later production-readiness review.

## Security and cost boundary

- The Alertmanager Service is `ClusterIP` and no Ingress is created.
- Alertmanager Pods do not automount a Kubernetes API token.
- Requests are `50m` CPU and `64Mi` memory.
- Limits are `200m` CPU and `256Mi` memory.
- AWS placement remains `workload=system`.
- `alertmanager-cluster-only` permits port `9093` from Prometheus in the
  `observability` Namespace.
- Alertmanager peer traffic is restricted to Alertmanager Pods on TCP and UDP
  port `9094`.
- DNS is restricted to the `kube-system` Namespace.
- No external receiver credential, endpoint, or unrestricted notification
  egress is committed.

The NetworkPolicy contains the future single-cluster peer path even though
v0.11.5.0 deploys one replica. This does not claim Alertmanager HA.

## Offline validation

Run:

```bash
./scripts/validate-v0.11.5.0-alertmanager-foundation.sh
./scripts/validate-ci-quality-gates.sh
```

The focused validator checks:

1. the pinned Chart and direct configuration ownership;
2. exact local, aws-dev, aws-test, and aws-prod profiles;
3. route grouping, severity receivers, and bounded inhibition equality;
4. private exposure, resource limits, token, placement, and NetworkPolicy;
5. dedicated encrypted AWS storage and environment tag patches;
6. the absence of external notification integrations and plaintext secrets;
7. the absence of alert rules before v0.11.5.1;
8. historical validator successor compatibility.

## Local live acceptance

Commit and push the increment to the feature branch, then deploy the exact
feature revision:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
  ./scripts/deploy-local-feature-gitops.sh
```

If the local feature workflow is currently at the neutral baseline, preserve
the v0.11.4.2.2 requirement to build and load a fresh uniquely tagged demo-api
image before deployment. This Alertmanager-only increment does not otherwise
require a new application image.

After the monitoring Application is Synced and Healthy, run:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
REQUIRE_NO_ALERT_RULES=true ./scripts/check-alertmanager.sh
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-controller-metrics.sh
PROFILE=local ./scripts/check-operator-dashboards.sh
PROFILE=local ./scripts/check-capacity-signals.sh
PROFILE=local ./scripts/check-capacity-dashboard.sh
```

The Alertmanager check requires:

1. a Ready Alertmanager Pod and private Service;
2. a successful `/-/ready` response;
3. the exact route and inhibition markers in `/api/v2/status`;
4. no active external notification configuration;
5. an active Alertmanager endpoint in Prometheus `/api/v1/alertmanagers`;
6. a scraped `alertmanager_build_info` series;
7. no alert rules while `REQUIRE_NO_ALERT_RULES=true`.

The first live run proved the active routes and inhibition but exposed an
acceptance-only formatting defect: Alertmanager returned
`severity="critical"` instead of the declaration's spaced form. The
v0.11.5.0.1 repair validates optional matcher whitespace while retaining
exactly two critical and two warning occurrences. Apply that repair and rerun
the same command directly; no GitOps redeployment is required.

The script chooses an available local port within a bounded range, records
port-forward diagnostics, and removes both port-forward processes on exit.

## Acceptance and next increment

v0.11.5.0 is accepted locally when both offline validators pass, the exact
feature deployment passes the complete live sequence, and the existing five
Grafana Dashboards and all accepted recording rules remain healthy.

Formal live AWS evidence remains v0.11.8 work. Do not claim production
Alertmanager HA or external notification delivery from local acceptance.

After acceptance, v0.11.5.1 may add the bounded first alert inventory and one
reviewed Runbook per alert without changing the routing ownership established
here.

That successor is now implemented as eight recording-rule-backed alerts with
one English Runbook each. Run `scripts/check-alertmanager.sh` without
`REQUIRE_NO_ALERT_RULES=true` after applying v0.11.5.1, then run
`PROFILE=local scripts/check-actionable-alerts.sh`.

v0.11.5.1.1 subsequently repairs the target-down recording-rule semantics and
adds the ninth alert without changing this Alertmanager routing foundation.

## Explicit exclusions

This increment adds no alert rule, Runbook, Dashboard, recording rule,
ServiceMonitor, application metric, external receiver, notification Secret,
central Alertmanager, remote write, log backend, tracing backend, SLO,
burn-rate expression, Rollout gate, release-orchestrator behavior, automatic
AWS mutation, or production write.
