# v0.11.5.1.1.1 Local Acceptance Path Repair

## Purpose

v0.11.5.1.1.1 repairs two validation-path defects found during the first local
live attempt for the Prometheus target-down semantic repair. The observed
runtime confirms that the new application metrics are present after a fresh
build and that the repository-owned diagnostic PrometheusRule exists.

This patch changes no Kubernetes desired state. It does not alter the repaired
recording-rule expression, the nine-alert inventory, a Dashboard, a monitor,
Alertmanager, or demo-api source code.

## Observed failures

The neutral feature baseline deployed `sha-3e50802`. It was Healthy and exposed
the historical metric `demo_api_requests_total`, but it did not contain the
accepted v0.11 application metrics:

```text
demo_api_http_requests_total
demo_api_dependency_checks_total
```

The shared telemetry preflight correctly rejected that image. Building the
current feature source under a unique local tag and redeploying restored both
required metrics.

The target-count check also queried the nonexistent resource name
`operator-recording-rules`. The Chart has always declared the resource as:

```text
operator-diagnostic-recording-rules
```

The live cluster confirmed that the correctly named PrometheusRule was
present. The check now derives its default from that declared identity and
allows an explicit `OPERATOR_RECORDING_RULE_NAME` override for controlled
non-default release layouts.

## Required local replay

Start from a committed and pushed feature revision. A neutral-baseline image
must not be reused merely because its Rollout is Healthy or its image tag and
application version agree.

Build and load one unique image from the exact current revision:

```bash
IMAGE_REPOSITORY="startup-devops-baseline/demo-api"
IMAGE_TAG="v0.11.5.1.1.1-$(git rev-parse --short=12 HEAD)-local"

IMAGE_NAME="${IMAGE_REPOSITORY}" \
IMAGE_TAG="${IMAGE_TAG}" \
  ./scripts/build-load-demo-api-image.sh
```

Deploy that image through the exact feature revision:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_REPOSITORY="${IMAGE_REPOSITORY}" \
IMAGE_TAG="${IMAGE_TAG}" \
APPLICATION_VERSION="${IMAGE_TAG}" \
  ./scripts/deploy-local-feature-gitops.sh
```

Complete any intentional Canary pause. Then run the live suite in this order:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
./scripts/check-alertmanager.sh
PROFILE=local ./scripts/check-prometheus-target-counts.sh
PROFILE=local ./scripts/check-actionable-alerts.sh
./scripts/check-observability-views.sh
PROFILE=local ./scripts/check-controller-metrics.sh
PROFILE=local ./scripts/check-operator-dashboards.sh
PROFILE=local ./scripts/check-capacity-signals.sh
PROFILE=local ./scripts/check-capacity-dashboard.sh
```

The shared telemetry preflight must observe populated HTTP and dependency
metrics. The target-count check must find
`operator-diagnostic-recording-rules`, compare its recorded vector with the
direct Boolean query, and report zero down targets on the clean baseline. The
actionable-alert check must load exactly nine healthy, inactive alerts.

## Completion boundary

Successful local replay accepts the v0.11.5.1.1 semantic repair and this
validation repair. It does not prove intentional firing, severity routing,
critical-over-warning inhibition, resolution, or external notification
delivery. Those drills remain v0.11.5.2 work. Formal AWS evidence remains
v0.11.8 work.

After collecting evidence, restore the neutral pre-merge feature baseline:

```bash

  ./scripts/restore-local-feature-baseline.sh
```

Do not run `restore-local-gitops-head.sh` before this feature reaches the
stable branch.
