# v0.11.5.1.1 Prometheus Target-Down Semantics Repair

## Goal

v0.11.5.1.1 repairs the existing Prometheus target-down recording rule before
it becomes an actionable alert source. The previous filter comparison retained
the value `0` for every down target, so summing the result could incorrectly
report zero down targets.

The repaired expression uses a Boolean comparison:

```promql
sum by (namespace, job) (
  up == bool 0
)
```

Each up target now contributes `0`; each down target contributes `1`. An absent
target group remains no-data and is not converted into a fabricated healthy or
failing series.

## Semantic contract

| Input for one namespace and job | Recorded value |
| --- | ---: |
| all targets up | `0` |
| one target down | `1` |
| two targets down | `2` |
| target group absent | no-data |

The aggregation preserves the `namespace` and `job` labels. Both the Platform
Overview Dashboard and the new alert consume the repaired recording rule.

## Alert inventory change

`PrometheusTargetDown` is added as the ninth repository-owned alert. It is
critical after the repaired count remains above zero for 10 minutes in the
required platform, application, delivery, and data namespaces. The alert uses
`component=prometheus` and `alert_family=monitoring-target-health` and links to
its dedicated Runbook.

The eight v0.11.5.1 alerts, their thresholds, durations, labels, annotations,
and Runbooks remain unchanged. The complete inventory is now two warning and
seven critical alerts.

## Offline acceptance

Run:

```bash
./scripts/validate-v0.11.5.1.1-prometheus-target-down-semantics-repair.sh
./scripts/validate-ci-quality-gates.sh
```

The focused validator rejects the former `up == 0` filter form, requires the
Boolean expression, evaluates all-up, one-down, two-down, and absent fixtures,
and validates the ninth alert and Runbook contract.

## Local live acceptance

The neutral pre-merge feature baseline is only a replay start state. Its
default demo-api image may expose the historical metric schema even when the
Rollout is Healthy. After committing and pushing the exact feature revision,
build and load one unique local image from that revision and deploy it through
the Root Application:

```bash
IMAGE_REPOSITORY="startup-devops-baseline/demo-api"
IMAGE_TAG="v0.11.5.1.1-$(git rev-parse --short=12 HEAD)-local"

IMAGE_NAME="${IMAGE_REPOSITORY}" \
IMAGE_TAG="${IMAGE_TAG}" \
  ./scripts/build-load-demo-api-image.sh

TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_REPOSITORY="${IMAGE_REPOSITORY}" \
IMAGE_TAG="${IMAGE_TAG}" \
APPLICATION_VERSION="${IMAGE_TAG}" \
  ./scripts/deploy-local-feature-gitops.sh
```

Do not derive acceptance image suitability from an existing Application Helm
parameter. A neutral baseline intentionally removes the four local-image
parameters. Prove the deployed image instead by requiring both
`demo_api_http_requests_total` and `demo_api_dependency_checks_total` during
the shared telemetry preflight.

After reconciliation, run:

```bash
PROFILE=local ./scripts/check-prometheus-target-counts.sh
PROFILE=local ./scripts/check-actionable-alerts.sh
```

The first script compares the recorded vector with a direct live evaluation of
`sum by (namespace, job) (up == bool 0)`. It retries within the bounded rule
evaluation window, requires an exact namespace/job/value match, and requires
the clean baseline to contain no down target. The second script validates the
exact nine-alert inventory and requires every alert to remain inactive.

The target-count check verifies the repository-owned rule through
`PrometheusRule/operator-diagnostic-recording-rules`, which is the metadata
name declared by the observability views Chart.

## Acceptance-path repair

The first live attempt found two validation-path defects while confirming the
runtime design:

- the neutral baseline image `sha-3e50802` exposed the historical
  `demo_api_requests_total` metric instead of the accepted HTTP and dependency
  telemetry;
- the target-count script looked for a nonexistent
  `PrometheusRule/operator-recording-rules` even though the real
  `operator-diagnostic-recording-rules` resource was present.

v0.11.5.1.1.1 corrects both acceptance paths without changing the repaired
recording rule, its alert, or any Kubernetes desired state.

## Explicit exclusions

This repair changes no Dashboard, monitor, scrape configuration, Alertmanager
route, external receiver, credential, application image, Rollout Analysis,
SLO, burn-rate expression, AWS resource, or production automation. It does not
deliberately break a real target. Firing, routing, inhibition, resolution, and
notification-path drills remain v0.11.5.2 work.
