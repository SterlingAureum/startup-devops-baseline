# v0.11.5.2.0.3 Prometheus Rule Cleanup Synchronization Repair

## Outcome

The repaired v0.11.5.2.0.2 drill completed all four lifecycle phases. Its final
formal-baseline check then observed the exact nine healthy inactive formal
alerts plus two healthy inactive temporary drill alerts. The temporary alerts
were no longer firing, but Prometheus still exposed their rule definitions in
`/api/v1/rules` immediately after Kubernetes deletion.

This is a cleanup synchronization defect. `kubectl delete --wait=true` waits
for Kubernetes object deletion; it does not prove that Prometheus Operator has
regenerated rule files or that Prometheus has reloaded the resulting inventory.

## Repair

The drill now treats cleanup as two distinct convergence boundaries:

1. delete the temporary PrometheusRule from Kubernetes;
2. poll Prometheus until neither `AlertLifecycleDrillWarning` nor
   `AlertLifecycleDrillCritical` exists in the active alert-rule inventory.

The bounded Prometheus wait runs after every phase deletion and once more
before the final exact nine-alert assertion. A timeout prints only the matching
temporary rule names, health, state, and last error.

The normal final cleanup is strict: a Kubernetes deletion failure terminates
the drill instead of being hidden. The EXIT trap remains best-effort because it
must attempt all cleanup operations while preserving the original failure.

## Correct final sequence

```text
resolved webhook observed
no current drill alert in Prometheus or Alertmanager
strict Kubernetes PrometheusRule deletion
temporary rules absent from Prometheus rule inventory
strict labeled sink-resource deletion
zero labeled Kubernetes resources
zero active drill alerts
exact nine healthy inactive formal alerts
```

The rule-inventory wait has a default timeout of 120 seconds and polls at the
existing bounded interval. It may be overridden for unusually slow local
systems with `RULE_REMOVAL_TIMEOUT_SECONDS`, but increasing the timeout must not
replace diagnosis of a persistent reload failure.

## Incident interpretation

The observed eleven-rule diagnostic does not invalidate the earlier lifecycle
evidence:

- all four phases completed;
- the two temporary alerts were healthy and inactive;
- the nine formal alerts were healthy and inactive;
- no route, receiver, notification, inhibition, or inactive-transition failure
  was reported.

The incident output alone did not prove whether the Kubernetes object had been
deleted. The strict deletion path and separate Prometheus convergence check now
make those failure classes distinguishable.

## Unchanged runtime

This repair changes the guarded drill script, contracts, and documentation
only. It changes no monitoring Application, Helm Chart, Alertmanager
configuration, route, receiver, NetworkPolicy, permanent PrometheusRule,
formal alert, webhook sink, demo-api image, AWS declaration, or production
workflow.

No monitoring redeployment or image rebuild is required.
