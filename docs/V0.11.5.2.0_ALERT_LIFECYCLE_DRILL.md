## Outcome

v0.11.5.2.0 proves the local alert lifecycle without deliberately failing a
real application, controller, database, or scrape target. A guarded script
creates synthetic Prometheus alerts and a restricted in-cluster webhook sink,
checks routing and inhibition through the live Alertmanager API, observes both
firing and resolved webhook payloads, and removes every temporary object.

The nine repository-owned operational alerts remain unchanged. This increment
does not claim delivery to Slack, email, PagerDuty, or another external
provider.

## Permanent desired state

Each environment-owned Alertmanager receives two narrowly matched drill routes:

| Severity | Drill receiver | Webhook path | Normal route also checked |
| --- | --- | --- | --- |
| critical | `critical-drill-webhook` | `/critical` | `critical-observation` |
| warning | `warning-drill-webhook` | `/warning` | `warning-observation` |

Both drill routes require `drill="true"`,
`alert_family="alert-lifecycle-drill"`, and the expected severity. They set
`continue: true`, so Alertmanager also evaluates the existing severity route.
Only drill routes use the short `1s` group wait and `2s` group interval. Normal
production-oriented route timing remains `30s`, `5m`, and `4h`.

Both webhook receivers set `send_resolved: true` and point only to:

```text
alert-lifecycle-drill-sink.observability.svc.cluster.local:8080
```

The permanent Alertmanager NetworkPolicy adds only TCP 8080 egress to Pods
carrying `app.kubernetes.io/name=alert-lifecycle-drill-sink` in the
`observability` Namespace. No public endpoint or credential is added.

## Temporary drill resources

`scripts/check-alert-lifecycle-drill.sh` creates these resources only for the
duration of an explicitly confirmed run:

- `PrometheusRule/alert-lifecycle-drill`;
- `ConfigMap/alert-lifecycle-drill-sink`;
- `Deployment/alert-lifecycle-drill-sink`;
- `Service/alert-lifecycle-drill-sink`;
- `NetworkPolicy/alert-lifecycle-drill-sink`.

The sink reuses the currently deployed demo-api image because that image
already contains Python. It overrides the command with the repository fixture
at `scripts/fixtures/alert-webhook-sink.py`. It runs without a ServiceAccount
token, as a non-root UID, with a read-only root filesystem and all Linux
capabilities dropped. Its Service is ClusterIP. Its NetworkPolicy allows
ingress only from Alertmanager Pods and allows no egress.

The sink keeps at most 500 events in memory and exposes `/health`, `/events`,
and `/reset` for the drill process. It is not a notification service and must
not remain deployed after acceptance.

## Drill phases

1. Preflight proves that the monitoring and views Applications are Synced and
   Healthy, the exact nine formal alerts are healthy and inactive, and no
   stale drill resource exists.
2. Warning lifecycle proves Prometheus firing, both warning receiver
   assignments, a firing webhook, rule removal, and a resolved webhook.
3. Critical lifecycle proves the equivalent critical path.
4. Positive inhibition creates critical and warning alerts with equal
   environment, cluster, component, and alert-family labels. Critical remains
   active and is delivered; warning becomes suppressed with a non-empty
   `inhibitedBy` set and produces no firing webhook.
5. Negative inhibition uses different component labels. Both alerts remain
   active and both webhook paths receive firing payloads.
6. Cleanup removes the temporary resources, waits until Prometheus and
   Alertmanager contain no drill alert, and rechecks the exact nine-alert clean
   baseline.

Every run uses a unique `drill_id` and component label. Fixed Kubernetes names
also make concurrent execution fail safely during preflight instead of mixing
evidence from two drills.

Run from the repository root:

```bash

./scripts/validate-ci-quality-gates.sh
```

The validator checks exact route and receiver cardinality, internal-only URLs,
resolved delivery, NetworkPolicy scope, the unchanged nine-alert inventory,

fixture behavior, and negative public-URL rejection.

## Live acceptance

Start from the accepted local feature deployment with a unique image built
from the current feature commit. Do not run the drill against the neutral
feature baseline image.

First verify the normal runtime:

```bash
./scripts/validate.sh
./scripts/check-monitoring.sh
./scripts/check-alertmanager.sh
./scripts/check-actionable-alerts.sh
./scripts/check-prometheus-target-counts.sh
```

Run the guarded drill:

```bash
CONFIRM_ALERT_DRILL=true \
  ./scripts/check-alert-lifecycle-drill.sh
```

The final success line must be:

```text
v0.11.5.2.0 local firing, routing, inhibition, resolved delivery, isolation, and zero-residual cleanup acceptance passed.
```

Confirm zero residual independently:

```bash
kubectl -n observability get prometheusrule,networkpolicy,service,deployment,configmap \
  -l platform.startup.dev/alert-lifecycle-drill=true

./scripts/check-actionable-alerts.sh
./scripts/check-alertmanager.sh
```

The labeled resource query must return no resources. The two follow-up checks
must pass with the formal alert inventory clean and inactive.

If a run is interrupted, the EXIT trap attempts cleanup. If the shell or
machine is terminated before that trap runs, remove the labeled objects and
wait for drill alerts to clear before retrying:

```bash
kubectl -n observability delete prometheusrule,networkpolicy,service,deployment,configmap \
  -l platform.startup.dev/alert-lifecycle-drill=true \
  --ignore-not-found --wait=true
```

## Environment boundary

The same tightly scoped, inert-until-used routes are declared in local and AWS
profiles so configuration ownership stays consistent. v0.11.5.2.0 executes
the mutating drill only on local kind. Formal AWS execution, environment-owned
external provider endpoints and secret delivery remain v0.11.8 or v0.12 work.

This increment does not add a business alert, change any formal threshold or
duration, create a real outage, create a Silence, mutate AWS, add an external
credential, change release automation, or add logging, tracing, SLO, or
burn-rate behavior.
