# v0.11.6.1.0 Structured demo-api Logging Runtime

## Outcome

v0.11.6.1.0 implements the application side of the centralized logging path.
Every demo-api process record is one JSON object on one stdout line, request
logs use bounded route templates, and release identity is projected from the
existing Pod annotations through the Kubernetes Downward API.

This increment deliberately stops before Loki, Alloy, Kubernetes Event
collection, or Grafana log data sources. The application log contract can be
validated independently before a collector and backend make debugging more
complex.

## Runtime identity

The Helm chart already owns the canonical delivery annotations. The container
does not recalculate them. Deployment and Rollout Pod templates project:

| Environment variable | Pod annotation |
| --- | --- |
| `PLATFORM_RELEASE_ID` | `platform.startup.dev/release-id` |
| `PLATFORM_SOURCE_COMMIT` | `platform.startup.dev/source-commit` |
| `CONTAINER_IMAGE_DIGEST` | `platform.startup.dev/image-digest` |

`APP_NAME`, `APP_VERSION`, and `APP_ENV` remain the service, version, and
environment sources. A local process that does not run under Kubernetes uses
explicit `local-unavailable` and `local-unpinned` fallback values.

## JSON Lines contract

Every record includes:

```text
timestamp
severity
message
service.name
service.version
deployment.environment.name
platform.release.id
platform.source.commit
container.image.digest
```

Completed HTTP requests may also include:

```text
http.request.method
http.route
http.response.status_code
duration_ms
outcome
```

The middleware records a normalized method and a route template. An unknown
route becomes `__unmatched__`; the raw path and query string are never copied
to the record. Successful `/health`, `/ready`, and `/metrics` requests are
quiet to prevent probe and scrape noise. A failed request to any of those
routes is still recorded.

The process entrypoint is `python -m src.server`. It installs the same JSON
formatter for application and Uvicorn process logs and disables Uvicorn's
second access-log stream. If a Python log record carries exception data, the
formatter emits the bounded `unhandled_exception` message rather than the
exception text or connection details.

## Security boundary

The application does not add request or response bodies, raw URLs, query
strings, Authorization or Cookie headers, user identifiers, raw SQL, database
parameters, credentials, or Secrets to records. Structured fields cannot
override the required runtime identity.

This application boundary does not replace collector filtering. Alloy receives
an independent filtering and label-cardinality contract in v0.11.6.1.1.

## Offline validation

Run from the repository root:

```bash
./scripts/validate-v0.11.6.1.0-structured-demo-api-logging-runtime.sh
./scripts/validate-v0.11.6.0-centralized-logging-minimal-tracing-foundation.sh
./scripts/validate-ci-quality-gates.sh
docker build --target test \
  --tag startup-devops-baseline/demo-api:v0.11.6.1.0-test \
  apps/demo-api
```

## Local image and GitOps validation

Build and load a unique image. Replace the example tag with a tag that is not
already present in the kind node:

```bash
IMAGE_TAG=v0.11.6.1.0-local-1
IMAGE_TAG="${IMAGE_TAG}" ./scripts/build-load-demo-api-image.sh
```

The helper defaults to the repository's `startup-devops-baseline` kind cluster.
Set the same `CLUSTER_NAME` used by `bootstrap-kind.sh` when the cluster has a
different name.

Deploy the feature baseline with the same tag and application version:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
LOCAL_IMAGE_ENABLED=true \
IMAGE_TAG="${IMAGE_TAG}" \
APPLICATION_VERSION="${IMAGE_TAG}" \
  ./scripts/deploy-root-app.sh
```

`GIT_TARGET_REVISION` defaults to `TARGET_REVISION`, so this command points the
Root Application and every same-repository child Application at the same
feature branch. Set `GIT_TARGET_REVISION` explicitly only when intentionally
testing different Root and child revisions.

Wait for the demo-api Rollout to finish before checking logs. If the Rollout is
paused at a manual step, inspect it and promote only after the current Canary
analysis is successful:

```bash
kubectl argo rollouts get rollout demo-api -n startup-apps --watch
kubectl argo rollouts promote demo-api -n startup-apps
```

Then run:

```bash
./scripts/check-demo-api-structured-logs.sh
```

The live check executes requests inside the selected demo-api Pod, validates
that every returned process line is JSON, compares the log identity to Pod
annotations, proves that successful probe logs are suppressed, and rejects raw
secret-bearing paths and query strings.

## Acceptance boundary

v0.11.6.1.0 is accepted when the offline validator, complete quality gate,
Docker test stage, unique-image local redeployment, completed Rollout, and live
structured-log check all pass.

No Loki or Alloy resource should exist because of this increment. No
monitoring redeployment, AWS mutation, external credential, public endpoint,
tracing runtime, AI infrastructure, AIOps, or OpenClaw integration is included.

The next increment is v0.11.6.1.1: local Loki Monolithic and the Alloy Pod-log
collector.
