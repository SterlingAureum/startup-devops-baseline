# v0.11.6.1.1.2 Alloy Non-Root and Loki Rules-Sidecar Runtime Repair

## Purpose

The v0.11.6.1.1.1 repair allowed the pinned Alloy Chart to render, exposing two
independent runtime configuration failures. Alloy could not start because the
Pod required non-root execution while the image metadata still resolved to
root. Loki itself and its private gateway became ready, but the Loki Pod stayed
unready because an unused rules-discovery sidecar repeatedly failed.

This repair resolves both blockers without changing the logging architecture,
memberlist topology, application image, or index-label contract.

## Incident Evidence

Kubernetes rejected the Alloy container with:

```text
container has runAsNonRoot and image will run as root
```

The Alloy image provides a dedicated `alloy` identity with UID/GID `473`, but
the prior values enabled `runAsNonRoot` without selecting that identity.

The Loki main container reached Ready and the gateway reached two Ready
containers. The `observability-logs-memberlist` headless Service also acquired
an EndpointSlice address on port `7946`; the earlier DNS messages were startup
convergence, not evidence of a missing memberlist topology.

The remaining Loki Pod failure was `loki-sc-rules`. The Chart enables rule
discovery by default, while this increment intentionally deploys no ruler
ConfigMaps or Secrets and disables ServiceAccount token automounting. Granting
the unused sidecar a token or adding RBAC would expand authority without adding
required behavior.

## Repair

Alloy retains its restricted container security settings and now explicitly
uses:

```yaml
runAsNonRoot: true
runAsUser: 473
runAsGroup: 473
```

The Pod security context adds `fsGroup: 473` for its writable temporary storage.

Loki retains `defaults.automountServiceAccountToken: false` and adds:

```yaml
sidecar:
  rules:
    enabled: false
```

The resulting Monolithic Pod contains only the `loki` application container.
The gateway remains a separate two-container Deployment.

## Unchanged Boundary

This repair does not change:

- local platform Chart `0.5.0` / application version `v0.11.6.1.1`;
- Loki Chart `18.11.3`, Loki `3.7.6`, Monolithic storage, or memberlist;
- Alloy Chart `1.11.0`, Alloy `1.18.0`, RBAC, or Pod-log pipeline;
- the six indexed labels or Pod structured metadata;
- demo-api Chart `0.6.0`, application version `0.4.0`, code, or image;
- Grafana data sources, Kubernetes Events, tracing, or AWS state;
- public endpoints, credentials, or production automation.

## Acceptance

Run the focused repair and predecessor validators, followed by the complete
quality gate:

```bash
./scripts/validate-v0.11.6.1.1.2-alloy-nonroot-loki-rules-sidecar-runtime-repair.sh
./scripts/validate-v0.11.6.1.1-local-loki-alloy-pod-logs.sh
./scripts/validate-ci-quality-gates.sh
```

The pinned Alloy render must contain UID/GID `473` and Pod `fsGroup` `473`.
The pinned Loki render must contain no `loki-sc-rules` container and must keep
ServiceAccount token automounting disabled.

After committing and pushing the repair, reconcile the two logging
Applications and run:

```bash
./scripts/validate.sh
./scripts/check-local-logging-runtime.sh
```

The live checker requires the Alloy DaemonSet, one-container Loki StatefulSet,
and two-container gateway to be Ready. It also verifies the memberlist
EndpointSlice and observes that the Loki main-container restart count remains
stable before continuing with the existing LogQL and Pod-replacement checks.

No demo-api image rebuild or deliberate logging Pod deletion is required.
