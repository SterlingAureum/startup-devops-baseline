# v0.11.6.1.2.1 Events PVC Sync-Wave Troubleshooting

This document is specific to the `v0.11.6.1.2` Kubernetes Events rollout and
its `v0.11.6.1.2.1` repair. It records the observed deadlock, the exact
diagnostic signature, and a non-destructive recovery procedure. It is not a
generic storage or Argo CD troubleshooting guide.

## Incident Signature

The local cluster used this default StorageClass:

```text
NAME                 PROVISIONER             VOLUMEBINDINGMODE
standard (default)   rancher.io/local-path   WaitForFirstConsumer
```

The original Root Chart placed the Event-position PVC at sync wave `8` and the
`logging-alloy-events` child Application at wave `9`. A Root sync then remained
at:

```text
Application/startup-devops-root                  OutOfSync  Progressing
PersistentVolumeClaim/observability-events-collector-storage  Synced  Progressing
Application/logging-alloy-events                 OutOfSync  Missing
```

No `observability-events-collector` Pod existed. Existing Loki, Pod-log Alloy,
Grafana, Prometheus, and demo-api workloads remained available.

## Causal Chain

`WaitForFirstConsumer` intentionally delays volume binding until Kubernetes can
schedule a Pod that references the claim. Argo CD sync waves wait for resources
in the current wave to become Healthy before applying the next wave.

The original ordering therefore formed a cycle:

1. wave `8` created the PVC;
2. the PVC waited for an Event collector Pod before binding;
3. Argo CD waited for the PVC to become Healthy before entering wave `9`;
4. wave `9` therefore never created `logging-alloy-events`;
5. the child Application could not create the consumer Pod; and
6. the PVC remained unbound indefinitely.

More waiting cannot resolve this state. The repair keeps Loki at wave `7` and
places both the claim and `logging-alloy-events` at wave `8`. Argo CD can then
create both resources, the child Application can create its Deployment, and
the scheduler can bind the claim.

## Why PermissionDenied Was Misleading

Before the child Application existed, this command could return
`PermissionDenied`:

```bash
argocd app get logging-alloy-events
```

That response was not evidence that the Event collector lacked Kubernetes Event
RBAC. Argo CD can conceal an absent or inaccessible Application behind the same
authorization response. The Root resource view already showed the decisive
state: `logging-alloy-events` was `Missing`.

`observability-events-collector-storage` is a PVC, not an Argo CD Application.
Inspect it with Kubernetes commands in the `observability` namespace:

```bash
kubectl -n observability get pvc observability-events-collector-storage
kubectl -n observability describe pvc observability-events-collector-storage
```

Inspect child Applications in the `argocd` namespace:

```bash
kubectl -n argocd get application logging-alloy-events
```

## Confirm the Deadlock Before Recovery

These read-only commands preserve evidence:

```bash
kubectl get storageclass \
  -o custom-columns=NAME:.metadata.name,PROVISIONER:.provisioner,MODE:.volumeBindingMode

kubectl -n argocd get application startup-devops-root \
  -o custom-columns=NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status,OPERATION:.status.operationState.phase

kubectl -n observability get pvc observability-events-collector-storage

kubectl -n argocd get application logging-alloy-events \
  -o custom-columns=NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status \
  2>/dev/null || true
```

The original defect is confirmed when the StorageClass uses
`WaitForFirstConsumer`, the PVC is Pending or Progressing, the Events
Application is absent, and the Root operation remains Running or Progressing.

## Safe Recovery

If the old `argocd app sync` process is still attached to the terminal, stop
only the local client with `Ctrl+C`. Then inspect the operation:

```bash
kubectl -n argocd get application startup-devops-root \
  -o jsonpath='{.status.operationState.phase}{"\n"}'
```

If the phase is `Running`, terminate that stale Root operation explicitly:

```bash
argocd app terminate-op startup-devops-root
argocd app wait startup-devops-root --operation --timeout 180
```

Apply, validate, commit, and push `v0.11.6.1.2.1`. Reconcile the same accepted
demo-api image identity:

```bash
TARGET_REVISION=feature/v0.11-observability-sre-baseline \
IMAGE_TAG=<accepted-v0.11.6.1.0-local-tag> \
APPLICATION_VERSION=<accepted-v0.11.6.1.0-application-version> \
  ./scripts/deploy-local-feature-gitops.sh
```

The repaired command has a bounded Argo CD CLI timeout. A future stalled sync
returns an error and Application diagnostics instead of waiting indefinitely.

Do not manually create `logging-alloy-events`, change the StorageClass to
`Immediate`, remove Argo CD health checks, or delete Loki. The existing Pending
claim does not need to be deleted; once its consumer becomes schedulable it can
bind normally.

## Expected Convergence

Verify the repaired topology:

```bash
kubectl -n argocd get application \
  startup-devops-root logging-loki logging-alloy logging-alloy-events monitoring

kubectl -n observability get pvc observability-events-collector-storage

kubectl -n observability rollout status \
  deployment/observability-events-collector --timeout=300s
```

Required result:

- the Root and `logging-alloy-events` Applications are `Synced/Healthy`;
- the positions claim is `Bound`;
- the singleton Event Deployment is available; and
- existing Loki and Pod-log workloads remain healthy.

Finish both live paths:

```bash
./scripts/check-local-logging-runtime.sh
./scripts/check-local-events-grafana.sh
```

## Prevention Invariant

For a Root-managed PVC backed by `WaitForFirstConsumer`, the first workload
that consumes the claim must be creatable in the same Argo CD sync wave. A
later-wave consumer behind the PVC's health gate is invalid even if the YAML,
Helm render, and individual resource contracts are otherwise correct.

Historical render validators must compare complete resource names. Substring
checks such as `name: logging-alloy` cannot distinguish `logging-alloy` from
`logging-alloy-events`. Commands that stream an Argo CD operation must also
carry a real CLI timeout; a timeout used only before or after the command does
not bound the command itself.
