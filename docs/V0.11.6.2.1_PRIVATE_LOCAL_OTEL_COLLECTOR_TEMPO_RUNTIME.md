# v0.11.6.2.1 Private Local OTel Collector and Tempo Runtime

## Outcome

This increment creates the private local tracing transport and store without
enabling application export. A single OpenTelemetry Collector Deployment
accepts OTLP/HTTP traces on port 4318, applies memory limiting and batching,
and forwards them to a single Tempo 3.0.3 process. Tempo stores traces in a
bounded `emptyDir` for 24 hours and exposes only private ClusterIP Services.

The accepted v0.11.6.2.0 demo-api image and Helm tracing configuration remain
unchanged. `TRACING_ENABLED=false` is still the required application state.
Grafana integration and real demo-api request traces begin in later increments.

## Version and ownership decision

The OpenTelemetry Collector uses the official `opentelemetry-collector` Chart
0.172.0 and Collector 0.159.0. Tempo uses a repository-owned minimal Chart
0.1.0 pinned to Tempo 3.0.3. The previously considered external Tempo Chart
1.24.4 is deprecated and targets Tempo 2.9.0, so it is intentionally rejected.
The local Chart contains only the five resources required by this checkpoint:
ServiceAccount, ConfigMap, Service, Deployment, and NetworkPolicy.

## Topology

| Application | Wave | Workload | Private ports |
| --- | ---: | --- | --- |
| `tracing-tempo` | 7 | one `observability-tempo` Deployment | 3200 query, 4318 OTLP/HTTP |
| `tracing-otel-collector` | 8 | one `observability-otel-collector` Deployment | 4318 OTLP/HTTP |

The Collector has one traces pipeline only:

```text
OTLP/HTTP receiver -> memory_limiter -> batch -> OTLP/HTTP Tempo exporter
```

There is no logs pipeline, metrics pipeline, Jaeger or Zipkin receiver,
application-side sampling, Collector sampling, public route, Ingress, or
LoadBalancer. Neither workload needs Kubernetes API RBAC or a mounted service
account token.

## Storage and availability boundary

Tempo local filesystem storage is deliberately disposable. Replacing the
Collector Pod must preserve an accepted trace because Tempo owns the history.
Replacing the Tempo Pod or rebuilding the kind cluster may lose all traces.
This is a deterministic local acceptance runtime, not a production durability
claim. Distributed storage, object storage, multi-replica Tempo, multi-AZ
availability, and disaster recovery remain production-qualification work.

## Security boundary

- Both Services are private `ClusterIP` resources.
- Collector ingress is limited to `startup-apps`; its egress is limited to DNS
  and the Tempo OTLP/HTTP port.
- Tempo OTLP ingress is limited to the Collector and its query endpoint to the
  `observability` namespace.
- Both workloads run non-root with a read-only root filesystem, RuntimeDefault
  seccomp, no privilege escalation, and all Linux capabilities dropped.
- No host network, host PID, hostPath, cloud credential, or public endpoint is
  introduced.

## Acceptance

Run the focused offline validator, then reconcile the local Root Application.
No demo-api image rebuild is required. Run the live checker twice:

```bash
./scripts/validate-v0.11.6.2.1-private-local-otel-collector-tempo-runtime.sh
./scripts/validate-ci-quality-gates.sh
./scripts/check-local-tracing-runtime.sh
./scripts/check-local-tracing-runtime.sh
```

The live checker posts one uniquely identified synthetic OTLP trace through a
Ready demo-api Pod to the Collector, queries the trace from Tempo, replaces the
Collector Pod, and proves the same trace remains queryable. It also proves the
demo-api still has tracing disabled. This does not claim an HTTP-to-PostgreSQL
application trace; that boundary remains v0.11.6.2.2 and later.
