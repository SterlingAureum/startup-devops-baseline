# v0.11.6.2.2.4 Loki Gateway stale upstream troubleshooting

## Classic incident

The real trace-log correlation check reached the Loki Gateway but received
`HTTP 502`. Loki remained Running and Healthy, so pod health alone obscured the
fault. The decisive evidence was:

```text
current Loki Service ClusterIP: 10.96.150.207
NGINX upstream in the 502 log:  198.18.0.195:3100
direct Loki API response:       HTTP 200
Gateway Loki API response:      HTTP 502
```

Alloy pushes failed through the same old upstream. The incident therefore sat
between the Gateway and the current Loki Service, not in Alloy, Loki storage,
Tempo, the application, or the NetworkPolicy.

## Root cause

The Loki Helm Gateway is an NGINX reverse proxy. Its generated `proxy_pass`
targets are hostnames resolved when NGINX loads its configuration. A local
GitOps recovery replaced the Loki Service and assigned a new ClusterIP while
the existing Gateway process retained the old resolved address. Kubernetes
reported both resources Healthy because the Gateway root endpoint and the Loki
pod probes did not exercise the stale proxied route.

The Service ClusterIP and Endpoint Pod IP normally differ. That difference is
not evidence of this incident. The fault is proven only when the current
Service ClusterIP differs from the address in a current NGINX upstream error
and a direct Loki request succeeds.

## Immediate recovery

```bash
kubectl -n observability rollout restart \
  deployment/observability-logs-gateway
kubectl -n observability rollout status \
  deployment/observability-logs-gateway --timeout=180s
```

Restarting the Gateway reloads NGINX and resolves the current Service address.
This is safe for the local single-replica acceptance environment but is not a
general production availability strategy.

## Declarative prevention

`restore-local-gitops-baseline.sh` records the Loki Service ClusterIP before
restoration. After the Loki Application is synchronized, it restarts and waits
for the Gateway only when the Service existed on both sides and its ClusterIP
changed. The read-only live checker never restarts resources.

This bounded repair covers the repository path that caused the incident. A
manual Service replacement outside that path still requires the immediate
recovery command above. Production designs should instead evaluate redundant
gateways, disruption budgets, and dynamically resolved upstream configuration.

## Related Tempo identifier trap

After the Gateway recovered, Loki correlation succeeded but the checker could
not find the hexadecimal log `span_id` as a literal string in Tempo's query
JSON. These interfaces use different JSON conventions:

- OTLP/JSON ingestion requires hexadecimal `traceId` and `spanId` values;
- Tempo's protobuf-JSON query representation may return those byte fields as
  Base64 strings.

The checker now normalizes either valid query representation to lowercase
hexadecimal before comparing it with the Loki log. This does not relax the
v0.11.6.2.1.1 OTLP/JSON ingestion contract.
