# v0.11.7.2.2 Canary Endpoint Identity and Scrape-window Troubleshooting

## Incident signature

The Rollout and AnalysisRun carried the new application/release identity, and
the checker reported that it generated canary traffic. Both stable-budget
queries and `up{job="demo-api-canary"}` succeeded, while all three candidate
queries with the exact new `platform_release_id` returned an empty vector.

Prometheus target evidence showed that relabeling was correct but the canary
Service still selected the previous ReplicaSet hash. Its Endpoints therefore
carried the previous release ID. The checker sent every request to those old
Pods before Argo Rollouts updated the Service selector.

## Why metadata was insufficient

GitOps updates labels on the Service object and annotations on the Rollout
before the Rollouts controller completes traffic-target reconciliation. A new
`app.kubernetes.io/version` label on the Service does not prove that its
selector or Endpoints point to the new ReplicaSet.

The authoritative local precondition is the complete chain:

1. Rollout annotation equals the expected application version.
2. Canary Service has a non-empty `rollouts-pod-template-hash` selector.
3. That selector resolves at least one Ready Pod.
4. Every selected Pod has the exact expected release-ID annotation.

## Scrape-window requirement

A one-time request burst can occur before Prometheus' first scrape of a new
target. In that case, later counter samples contain no observed increase. The
checker now sends bounded request pairs for at least 45 seconds, crossing
multiple 15-second scrape intervals, and the SLO metrics begin after 90
seconds. This preserves the 20-request minimum without weakening no-data
behavior.

## Diagnostics

On identity timeout or AnalysisRun failure, the checker prints the Rollout,
canary Service, selector hash, selected Pod names, readiness, application
version, and release ID. A stale selected Pod is an orchestration precondition
failure, not a Prometheus relabel failure.

Do not delete failed AnalysisRuns. Start the repaired checker before a fresh
release reconciliation and use one new application version in both terminals,
as documented in the package `APPLY.md`.
