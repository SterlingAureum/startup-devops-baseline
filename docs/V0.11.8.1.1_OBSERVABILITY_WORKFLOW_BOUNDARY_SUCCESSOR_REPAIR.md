# v0.11.8.1.1 Observability Workflow Boundary Successor Repair

## Incident

After v0.11.8.1 was applied, the complete local quality gate stopped during release-orchestration contract validation:

```text
Workflow gained AWS/EKS runtime access: aws-dev-observability-qualification.yaml
```

The workflow was already constrained by the v0.11.8.1 validator, but the older repository-wide workflow scanner recognized only `demo-api-runtime-qualification.yaml` as an approved AWS/EKS runtime boundary.

This was a validator compatibility defect. It was not evidence that the new workflow had obtained an unintended permission, and it was unrelated to the current Git branch or AWS connectivity.

## Repair

The historical scanner now constructs its approved runtime-workflow set from repository successors:

- `demo-api-runtime-qualification.yaml` remains approved;
- `aws-dev-observability-qualification.yaml` is approved only when the v0.11.8.1 contract exists;
- every other workflow remains forbidden from containing kubectl, EKS kubeconfig, or AWS credential configuration.

The historical scanner also checks the observability workflow's trusted runner, `aws-dev-runtime` Environment, and checker entry point, and rejects aws-prod, pull-request triggers, `kubectl apply`, `terraform apply`, and `git push`.

An internal negative fixture creates a hypothetical third workflow with `kubectl get pods` and requires rejection. The v0.11.8.1 specialized validator remains responsible for the complete workflow, evidence, and read-only runtime contract.

## Boundary

This repair changes no workflow, RBAC, checker, AWS environment, application, image, or live evidence. It does not require checkout or merge of main.

## Acceptance

Run from the active v0.11 feature branch:

```bash
./scripts/validate-release-orchestration-contract.sh
./scripts/validate-v0.11.8.1-aws-dev-live-observability-qualification.sh
./scripts/validate-v0.11.8.1.1-observability-workflow-boundary-successor-repair.sh
./scripts/validate-ci-quality-gates.sh
```

The final command still requires the repository's normal Docker, Helm, kubectl, and kustomize toolchain.
