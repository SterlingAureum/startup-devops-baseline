# v0.11.8.1.2 aws-dev Pre-Merge Feature Revision Qualification

## Purpose

The aws-dev Root Application can be deployed from the long-lived v0.11 feature branch, but the child Applications previously retained `targetRevision: main`. That split source made a pre-merge live result ambiguous: the checker came from feature while the runtime could come from main.

This increment adds a dev-only Kustomize patch for the nine same-repository child Applications. aws-test, aws-prod, and all external Helm Chart versions remain unchanged.

## Revision model

During aws-dev feature qualification:

```text
Root source                       feature/v0.11-observability-sre-baseline
aws-dev same-repository children feature/v0.11-observability-sre-baseline
aws-dev external Charts          pinned Chart versions
aws-test same-repository sources main
aws-prod same-repository sources main
```

The logical branch is desired state, not final evidence. The live checker requires every aws-dev Git Application to report the exact supplied 40-character commit in `.status.sync.revision`. The evidence `targetRevision` remains that immutable SHA.

## Offline revision-boundary check

```bash
EXPECTED_DEV_GIT_TARGET_REVISION=feature/v0.11-observability-sre-baseline \
EXPECTED_TEST_GIT_TARGET_REVISION=main \
EXPECTED_PROD_GIT_TARGET_REVISION=main \
  ./scripts/check-aws-gitops-revision-boundary.sh
```

The command renders all three overlays, counts same-repository Applications, verifies their environment-specific revisions, and verifies every external Chart version independently.

## Feature deployment

Commit and push the increment to the feature branch first. Resolve the exact remote commit, then deploy the aws-dev Root from the same branch:

```bash
git fetch origin feature/v0.11-observability-sre-baseline
FEATURE_REVISION=feature/v0.11-observability-sre-baseline
FEATURE_SHA="$(git rev-parse origin/${FEATURE_REVISION})"

TARGET_REVISION="${FEATURE_REVISION}" \
  ./scripts/deploy-aws-dev-root-app.sh
```

Wait until the nine Git-sourced Applications are Synced and Healthy at `FEATURE_SHA`. External Chart Applications retain their repository versions.

## Direct live qualification before main merge

The GitHub manual workflow remains protected-main-oriented. Pre-merge feature qualification runs the same read-only checker from the trusted local management host:

```bash
APPLICATION_VERSION="$(kubectl -n startup-apps get deployment demo-api \
  -o jsonpath='{.metadata.annotations.platform\.startup\.dev/application-version}')"

EXPECTED_GIT_TARGET_REVISION="${FEATURE_REVISION}" \
EXPECTED_CONTROL_PLANE_SHA="${FEATURE_SHA}" \
EXPECTED_AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)" \
EXPECTED_APPLICATION_VERSION="${APPLICATION_VERSION}" \
AWS_REGION="${AWS_REGION:-us-east-1}" \
  ./scripts/check-aws-dev-observability-qualification.sh
```

Only `qualified` accepts the feature runtime. `waiting-runtime` still means aws-dev is absent and exits 2.

## Pre-merge restoration

The dev-only feature patch must not enter main. Before opening the final v0.11 merge PR:

1. remove the `patches` block that sets the feature revision from `clusters/aws/overlays/dev/kustomization.yaml`;
2. run the boundary checker with all three expected revisions set to `main`;
3. run the complete quality gate;
4. commit the restoration separately;
5. verify no active GitOps manifest contains the v0.11 feature branch.

```bash
EXPECTED_DEV_GIT_TARGET_REVISION=main \
EXPECTED_TEST_GIT_TARGET_REVISION=main \
EXPECTED_PROD_GIT_TARGET_REVISION=main \
  ./scripts/check-aws-gitops-revision-boundary.sh

rg -n 'feature/v0\.11-observability-sre-baseline' clusters/aws
```

The final `rg` command must return no active AWS manifest match. Documentation and archived incident references may remain outside `clusters/aws`.

## Safety boundary

This increment changes only declarative source selection for aws-dev same-repository child Applications and read-only validation. It does not create AWS infrastructure, alter external Chart versions, send traffic, promote a Rollout, write live resources from the checker, or grant production access.
