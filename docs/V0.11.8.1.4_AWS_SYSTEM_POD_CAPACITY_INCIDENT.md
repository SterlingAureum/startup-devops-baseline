# AWS system Pod-capacity incident and controlled recovery

Project: startup-devops-baseline
Affected checkpoint: v0.11.8.1, repaired through v0.11.8.1.4
Environment: aws-dev only
Incident date: 2026-09-01 (UTC, from supplied logs)
Evidence: operator-provided info58.txt through info65.txt
Status: monitoring runtime recovered; strict per-node reserve remains unmet

## Executive summary

The complete monitoring stack exceeded the Pod-slot capacity of two t3.medium
system nodes. Both nodes had 17 non-terminated Pods against 17 allocatable Pod
slots. Prometheus Operator and two node-exporter Pods could not schedule.
Separately, Grafana's Helm-managed generated credentials produced Secret and
Deployment differences in Argo CD.

Expanding the system managed node group to four nodes allowed Operator,
Prometheus and Alertmanager to run, but did not move existing Pods away from
the full old nodes. Two sequential, operator-reviewed ALB Controller Pod
evictions allowed the old nodes' node-exporters to start. Monitoring then
completed synchronization, including the independent Grafana Secret migration.

The final supplied snapshot shows monitoring Synced/Healthy, sync Succeeded,
all eight node-exporters Ready, and no unassigned relevant Pods. A separate
capacity script still exits nonzero because one old node has zero spare slots.
This is a reserve-policy failure, not evidence of continued monitoring outage.

## Root cause and contributing factors

### Scheduling failure

The system tier's effective capacity was 34 Pods, including cluster agents,
platform controllers and monitoring. Operator required workload=system. The
application/database pools could not provide interchangeable capacity under
the existing placement and taint policies.

The old-node node-exporter instances were bound by DaemonSet scheduling to
their target nodes. Adding nodes created capacity elsewhere but did not free
those specific targets. Deleting and recreating the exporters alone would not
resolve this constraint.

CPU and memory percentages in describe-node were requests, not measured usage.
Several controllers declared zero requests, so those percentages were not a
complete resource budget. The incident proves a Pod-slot shortage, not that
CPU/memory or CNI capacity can be ignored in subsequent sizing.

An earlier aws-cni IP assignment warning for kube-state-metrics was followed by
successful startup. The supplied evidence does not prove subnet-wide IP
exhaustion or justify changing CNI/maxPods.

### Independent Grafana drift

The dev overlay was changed to reference observability-grafana-admin, prepared
outside Chart ownership. Preparation preserved existing target credentials,
otherwise copied the existing source keys or generated initial credentials.
The new Secret was required before pushing the auto-reconciled overlay.

Pinned Chart 88.5.0 was rendered twice during package preparation: the old
Chart-owned Grafana Secret was absent, the Deployment referenced the independent
Secret, and the Grafana Deployment was deterministic. In info62 the desired
reference had changed but the live Deployment still used the old Secret.
In info65 the new Grafana Pod was Ready and Argo CD had pruned the old Secret.

## Recovery performed

1. Add the dev-only four-node capacity profile and apply a reviewed, in-place
   managed-node-group expansion; no instance replacement, taint changes or
   CNI modification was intended.
2. Wait for the new system nodes to register Ready. Confirm both aggregate
   capacity and per-node occupancy, not just total cluster node count.
3. Inspect ALB Controller replicas and current PDBs. Confirm two healthy replicas.
4. Cordon old node A, submit one targeted Pod Eviction, wait for the replacement
   on another node and controller availability 2/2, then uncordon A.
5. Confirm exporter readiness improved to 7/8. Only then repeat on old node B.
6. Confirm controller availability 2/2 and exporters 8/8. Observe the monitoring
   synchronization complete, Grafana rollout and old Secret pruning.
7. Continue read-only qualification without repeating expansion or arbitrarily
   evicting additional workloads just to make the reserve check green.

These steps record this incident, not an unattended replay procedure. Historical
Pod names must never be reused without inspecting the current inventory.
Eviction respects matching PDBs; it does not invent a PDB when one is absent.
If eviction is denied or replacement does not recover, stop, diagnose and
restore the node's schedulable state as appropriate. Do not bypass with force
deletion or drain both system nodes together.

Unassigned relevant Pods: 0. The strict checker requires at least one free
slot on every eligible node, so it correctly fails its coded predicate for
old system B. Its undifferentiated FAIL message is misleading when interpreted
as current runtime failure. Per-node spare capacity is a project policy, not
a universal requirement for all workloads to be healthy.

## Acceptance and evidence limits

- Supplied logs prove component readiness and successful Argo CD synchronization.
- The user subsequently reported completion of the remaining workflow; the
  final qualification JSON and exact accepted commit were not supplied with
  that report. Preserve those artifacts separately rather than inventing IDs.
- Long-term Grafana stability should be supported by repeated refresh/diff.
- No claim is made for test/prod, single-node-loss HA, CPU/memory stress,
  guaranteed disruption-free upgrades, or persistent Grafana user data.
- Grafana storage was ephemeral: rollout can discard manual dashboards/users;
  Git-provisioned dashboards can be recreated. Credential migration is not a
  production secret rotation or backup design.

## Follow-up proposal: v0.11.8.1.5

Separate observation categories in capacity reporting:

- Actual blockers: missing required capacity/identity, relevant unschedulable
  Pods or unavailable required DaemonSet instances; fail.
- Low per-node reserve with healthy runtime and adequate aggregate reserve:
  explicit warning in operational mode; fail in opt-in strict reserve mode.
- API failures, unknown state and unreadable inventory: fail closed.

Do not silently weaken the historical contract: update contract, documentation,
fixtures and callers together. Retain the strict policy and its evidence.

Add a bounded post-expansion wait for the exact node group, four Ready system
nodes and timeout diagnostics. Node readiness must not be reported as complete
monitoring acceptance. Keep relocation operator-reviewed; do not add automatic
drains, forced evictions or blanket tolerations.

Required regression cases include the original 2x17/17 state, new-node startup
delay, four nodes with old-node Pending exporters, the recovered 8/8 state
with one zero-reserve node, strict reserve failure, and forbidden API access.
