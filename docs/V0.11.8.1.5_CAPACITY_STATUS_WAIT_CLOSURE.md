## Status semantics

| Entry point / mode | Checks | Result |
| --- | --- | --- |
| Capacity CLI, default operational | Four eligible system nodes, total Pod reserve, no unassigned relevant Pods, required monitoring workloads ready | PASS or explicit WARN, exit 0 |
| Operational, only individual-node reserve missing | Same runtime checks pass; at least one node has zero free slots | WARN: per_node_reserve_low, exit 0 |
| Operational runtime/capacity blocker | Missing/unready workload, relevant Pod not Ready, inadequate total reserve or system-node count | FAIL, exit 1 |
| Capacity CLI --mode strict | Historical Pod-slot budget, including at least one free slot per eligible node | FAIL if reserve unmet; this is not a runtime readiness check |
| API/identity/parse failure | State is unknown, not healthy | FAIL, exit 1 |

The Python evaluate() default remains strict for historical callers. The CLI
explicitly defaults to operational and performs runtime checks before evaluating
the warning. The .8.1.4 contract is retained as the historical strict policy;
the .8.1.5 contract specifies the new operational interpretation.

Operational readiness covers Operator, Grafana, kube-state-metrics,
node-exporter, Prometheus and Alertmanager plus non-completed observability
Pods. This is not a replacement for exact-release qualification, target scrape,
Dashboard/SLO checks, CPU/memory sizing or HA analysis. WARN is a recorded risk,
not a claim that the strict reserve policy passed.

```bash
./scripts/check-aws-dev-system-capacity.py
./scripts/check-aws-dev-system-capacity.py --mode strict
```

For the info65 snapshot, expect operational WARN/exit 0 and strict FAIL/exit 1.
Do not add `|| true` to quality gates or perform arbitrary eviction to hide it.
Future state can differ; a new Pending/unready Pod must fail operational mode.

## Wait without reapplying Terraform

```bash
export EXPECTED_AWS_ACCOUNT_ID='<intended-12-digit-account>'
export AWS_REGION=us-east-1
./scripts/wait-aws-dev-system-nodes.py
```

The waiter checks the exact dev ARN context and selects only nodes from
startup-devops-baseline-dev-general with workload=system. It requires at least
four Ready, schedulable nodes without NoSchedule/NoExecute taints. Other node
groups do not count. Default timeout is 900 seconds with 10-second polling;
explicit --timeout and --interval arguments allow bounded overrides.

The expansion script checks context before Terraform and invokes this waiter
after apply. A later timeout does not roll back expansion or mean that Terraform
failed. Inspect diagnostics and rerun the read-only waiter, not the apply script.
The wait deadline bounds polling; timeout diagnostics have separate short
command bounds. Permission/API failures fail immediately, rather than being
silently retried as missing capacity. Node readiness does not imply balanced
Pods or completed monitoring synchronization.
