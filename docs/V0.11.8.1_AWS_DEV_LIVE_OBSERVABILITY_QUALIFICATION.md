# v0.11.8.1 aws-dev Live Observability Qualification

## Outcome

This increment implements a read-only, exact-identity qualification for the existing aws-dev observability profile. It does not create or restore EKS, reconcile Argo CD, generate application traffic, trigger alerts, promote a release, or add a logging or tracing backend.

The live result is one of:

- `qualified`: every mandatory aws-dev control-plane and runtime check passed;
- `waiting-runtime`: the named EKS cluster is absent; the command exits 2;
- `failed`: the runtime exists but identity, health, capability, or safety checks failed.

Only `qualified` is acceptance.

## Declared capability profile

| Capability | aws-dev declaration | Live interpretation |
| --- | --- | --- |
| Metrics | supported | Prometheus ready, demo-api target up, rules available |
| Dashboards | supported | six exact GitOps-managed Dashboard ConfigMaps present |
| Alerts | supported | formal alert rules present and Alertmanager ready |
| SLO | supported | rule/query semantics verified; organic series optional |
| Logs | not deployed | Loki and Alloy runtime must remain absent |
| Traces | not deployed | Collector and Tempo runtime must remain absent |
| Progressive-delivery telemetry | not applicable | aws-dev uses a Deployment, not an Argo Rollout |

The checker does not inherit the accepted local Loki/Tempo result.

## Read-only RBAC

The existing `demo-api-runtime-qualification` group gains a namespaced `observability-runtime-qualification` Role. It permits get/list/watch for bounded runtime resources and create only on `pods/portforward`.

Kubernetes represents port-forward establishment as a create operation on the non-persistent `pods/portforward` subresource. This permission opens a temporary read transport to private Prometheus and Alertmanager Services; it does not create or mutate a Pod. Secret reads, Pod exec, ordinary resource create, patch, and delete remain denied.

The live checker verifies both the allowed and denied RBAC boundaries before querying telemetry.

## Identity model

The operator supplies:

- exact 12-digit aws-dev account ID;
- AWS region;
- exact protected-main 40-character commit;
- exact deployed demo-api application version.

`demo-api-aws-dev` and `observability-views-aws-dev` retain `targetRevision: main`, but their observed `.status.sync.revision` must equal the supplied immutable commit. `monitoring-aws-dev` is an external Helm source and is locked separately to kube-prometheus-stack `88.5.0`.

The checker itself must be checked out at the same protected-main commit. Therefore the live workflow is run after the reviewed increment reaches protected main and that exact revision has reconciled. A feature-branch script cannot qualify an older main runtime.

## Environment preparation boundary

If aws-dev was removed for cost control, restore it through the existing operator-controlled AWS lifecycle before qualification. The checker deliberately does not call Terraform, bootstrap Argo CD, deploy the Root Application, create a trusted runner, or alter DNS.

An absent cluster produces a Schema-compatible evidence record with:

```json
{
  "status": "waiting-runtime"
}
```

and exits 2. Keep that historical artifact, restore the environment independently, and start a new qualification run.

## Live workflow

Prerequisites:

- the exact `.8.1` commit is on protected main;
- aws-dev is reconciled to the same commit;
- the `aws-dev-runtime` GitHub Environment and OIDC role remain configured;
- an ephemeral self-hosted runner has labels `self-hosted`, `linux`, `x64`, `trusted-runtime`, `aws-dev`.

Determine the inputs:

```bash
CONTROL_PLANE_SHA="$(git rev-parse origin/main)"
APPLICATION_VERSION="$(kubectl -n startup-apps get deployment demo-api \
  -o jsonpath='{.metadata.annotations.platform\.startup\.dev/application-version}')"
AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
```

Dispatch:

```bash
gh workflow run aws-dev-observability-qualification.yaml \
  --ref main \
  -f control_plane_sha="${CONTROL_PLANE_SHA}" \
  -f expected_aws_account_id="${AWS_ACCOUNT_ID}" \
  -f expected_application_version="${APPLICATION_VERSION}"
```

The workflow uploads one seven-day runtime artifact and succeeds only when its evidence status is `qualified`. It does not commit evidence or create a pull request; reviewed append-only evidence remains v0.11.8.4 work.

## Direct operator execution

The same checker may run from a trusted host with equivalent AWS and Kubernetes identity:

```bash
EXPECTED_CONTROL_PLANE_SHA="$(git rev-parse HEAD)" \
EXPECTED_AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)" \
EXPECTED_APPLICATION_VERSION="${APPLICATION_VERSION}" \
AWS_REGION="${AWS_REGION:-us-east-1}" \
  ./scripts/check-aws-dev-observability-qualification.sh
```

## Idle SLO behavior

The checker never calls demo-api. It verifies Prometheus readiness, an up demo-api target, required SLO/Burn-rate rules, and a valid read-only SLO query. If organic `/version` traffic produced a current series, SLO becomes `supported-verified`; otherwise it remains `supported-not-verified` without failing the control-plane qualification.

Traffic-backed SLO and Canary behavior belongs to v0.11.9.

## Troubleshooting

On failure, inspect the uploaded evidence reason first. Then check the exact Application identities:

```bash
kubectl -n argocd get application \
  demo-api-aws-dev observability-views-aws-dev monitoring-aws-dev \
  -o custom-columns=NAME:.metadata.name,SOURCE:.spec.source.targetRevision,SYNC:.status.sync.status,REVISION:.status.sync.revision,HEALTH:.status.health.status
```

Do not repair a failed qualification by patching live Applications or granting broad cluster-admin access. Correct repository desired state or the trusted runtime role through a reviewed change, reconcile normally, and create a new evidence artifact.
