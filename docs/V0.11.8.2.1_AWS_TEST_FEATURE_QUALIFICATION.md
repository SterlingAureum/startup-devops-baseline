# v0.11.8.2.1 — AWS test feature deployment and observation

Baseline: validated v0.11.8.2.0.1. This enables a separate feature-mode test
workflow. Existing clean-main `apply-aws-test.sh` and `bootstrap-aws-test.sh`
remain unchanged. The `.8.2.0` preview manifest remains an offline artifact;
the new bootstrap creates a temporary operational root from the stable test
template, retaining its runtime VPC ignore rule and automated reconciliation.

## Boundaries

- Fixed account input, region `us-east-1`, cluster
  `startup-devops-baseline-test`, independent default local test state.
- Clean feature branch and exact pushed SHA are required by every live entry.
  Do not push concurrently during an operation; a moved branch fails checks.
- The plan profile is explicitly loaded: system node min/desired/max 4/4/4.
  As of .8.2.1.2, an existing test `terraform.tfvars` is preserved and fingerprinted.
  Additional automatic variable files and redirected/non-default state are rejected.
- A one-hour saved plan is reviewed before a separate confirmed apply.
  Deletion/replacement is rejected. No automatic imports or adoption.
- Bootstrap creates independent test Grafana credentials, never copies dev,
  preserves a valid existing Secret and never rotates it automatically.
- No automatic release promotion, Canary promotion, traffic generation,
  fault injection, AWS logging/tracing installation, or prod operation.
- Node Pod slots are a readiness preflight, not proof of CPU/memory sizing.

## 1. Offline validation and commit

The .8.2.1.1 repair registers the exact offline preview with the historical
active GitOps gate. Run `validate-v0.11.8.2.1.1-active-gitops-preview-registration.sh`
under `scripts/` as well. A failing full gate is not fixed by committing:
finish validation before commit/push. Negative fixtures intentionally print
rejection messages; their surrounding test must report `ok`/passed. The final
`CI quality gates passed.` line confirms completion of the full gate.

Prerequisites: Bash, Git, Python 3.10+ with PyYAML, Kustomize or kubectl.
The normal full quality gate also requires the repository's Docker/Helm/jq
toolchain. Live preparation additionally needs AWS CLI and Terraform; existing
bootstrap helpers also use kubectl and jq.

```bash
./scripts/validate-v0.11.8.2.1-aws-test-feature-qualification.sh
./scripts/check-aws-test-qualification-preview.sh
./scripts/check-aws-gitops-revision-boundary.sh
./scripts/validate-ci-quality-gates.sh
git diff --check
```

A renderer SKIP is not a render pass. Complete both standalone render checks
locally. Review, commit and push this increment to
`feature/v0.11-observability-sre-baseline` before any live command. See the
package APPLY guide for exact staging paths. Do not switch to main.

## 2. Set identity and review current test release

Use your existing configured AWS operator profile for plan/apply/bootstrap.
Verify its account against your intended AWS account, not just against itself.

```bash
aws sts get-caller-identity
read -r -p 'Reviewed target AWS account (12 digits): ' EXPECTED_AWS_ACCOUNT_ID
export EXPECTED_AWS_ACCOUNT_ID
export EXPECTED_CONTROL_PLANE_SHA="$(git rev-parse HEAD)"
git status --short
git ls-remote origin refs/heads/feature/v0.11-observability-sre-baseline
```

The scripts check the canonical repository directly, not only a possibly stale
remote-tracking ref. They sanitize inherited environment target overrides;
configured AWS authentication remains in use. They do not print credentials.

Inspect the already governed test release. This package does not change it:

```bash
sed -n '1,80p' apps/demo-api/helm/values/releases/aws-test.yaml
export EXPECTED_APPLICATION_VERSION="$(python3 -c 'import yaml; print(yaml.safe_load(open("apps/demo-api/helm/values/releases/aws-test.yaml"))["release"]["applicationVersion"])')"
```

This is the declared test application version, not this infrastructure version
and not automatically the dev release. The checker also verifies the declared
image digest. If the intended test release has not been governed/promoted yet,
stop and follow the existing release workflow separately. An old release that
lacks the required metrics may deploy but will not pass observability checks.

## 3. Create or resume infrastructure

An existing `infra/terraform/aws/environments/test/terraform.tfvars` is supported
by .8.2.1.2. Keep your Owner tags and valid persistent test runtime Role settings.
The file is optional; do not recreate it from the example over your own settings.
The example's commented Role ARN remains a placeholder, not a real credential.
Terraform resolves the HCL; the explicit profile overrides capacity to 4/4/4,
and CLI values pin test/project/region and the current management IPv4 /32.
All remaining resource changes still require human review. `.auto.tfvars`,
`.auto.tfvars.json` and `terraform.tfvars.json` are rejected, not removed.
When runtime identity is enabled, the exact account's
`startup-devops-baseline-test-github-runtime-read-role` must already exist;
the operator needs `iam:GetRole` for its read-only existence check. This does
not verify its trust/policies and does not create or change IAM roles.
See `V0.11.8.2.1.2_TEST_VARIABLE_INPUT_REPAIR.md` for the incident and recovery.
Do not move/delete Terraform state or `.terraform` to bypass a guard.

```bash
read -r -p 'Current public management IPv4 (not a private/VPN interface IP): ' TEST_MANAGEMENT_IP
export TEST_PLAN_DIR="/tmp/aws-test-plan-$(date -u +%Y%m%dT%H%M%SZ)"
./scripts/prepare-aws-test-feature.py plan \
  --mode create --management-ip "$TEST_MANAGEMENT_IP" --bundle "$TEST_PLAN_DIR"
```

`create` requires empty test state and no existing cluster. For an interrupted
deployment whose test state contains resources, use `--mode resume` and a new
bundle path. A partial apply may have state before the EKS cluster exists;
resume accepts that case but never treats a permission/API failure as absence.
An existing cluster without its state is not automatically adopted.

The displayed Terraform plan must be reviewed for account, test naming,
resources, four-node capacity, current endpoint /32 and cost. The bundle is
private (umask 077), contains sensitive infrastructure data, and must stay
outside Git. Proceed only after `Plan saved:`; a failed plan is not an applyable
bundle. Never manufacture `review.json`. Old pre-.8.2.1.2 plans and any added,
removed or changed `terraform.tfvars` require a new plan and review.
Apply exactly that saved plan within one hour:

```bash
./scripts/prepare-aws-test-feature.py apply \
  --bundle "$TEST_PLAN_DIR" --confirm apply-reviewed-aws-test
```

Do not rerun an old plan after a partial apply or endpoint/IP change. Generate
a fresh resume plan and review it. A requested deletion/replacement requires
separate diagnosis/review; this entrypoint intentionally stops.

## 4. Bootstrap test

Select a reviewed exact Argo CD release (`vX.Y.Z`), normally the release already
validated for your dev environment; `stable` and `latest` are rejected.
Do not upgrade Argo CD incidentally while qualifying test.
An existing argocd-server image must match that exact tag; a different version
or digest-pinned image stops for separate review instead of being overwritten.

```bash
read -r -p 'Reviewed exact Argo CD release (vX.Y.Z): ' TEST_ARGOCD_VERSION
./scripts/prepare-aws-test-feature.py bootstrap \
  --argocd-version "$TEST_ARGOCD_VERSION" \
  --confirm bootstrap-reviewed-aws-test
```

This waits up to 15 minutes for four schedulable system nodes and Pod-slot
reserves, prepares the independent Grafana Secret, then runs the existing
IRSA/Argo CD/ALB and database/ESO/DNS bootstrap helpers with fixed test targets.
Their existing waits remain active. A private temporary kubeconfig is used and
removed afterwards; your current context is not changed by this entrypoint.

An existing stable-main or foreign root causes a stop before bootstrap writes.
Do not patch it around the guard. Mode migration of an existing stable test
cluster needs separate review; this workflow supports fresh test and resuming
the same feature-mode root.

Bootstrap completion is not qualification. If it times out, inspect the named
component and rerun bootstrap with the same reviewed version/SHA after recovery.
No need to recreate healthy infrastructure. A valid existing Grafana Secret is
preserved. Credentials created for a fresh test cluster are independently random.

## 5. Review application rollout separately

For manual inspection configure a dedicated kubeconfig in your operator shell:

```bash
export KUBECONFIG="$(mktemp)"
aws eks update-kubeconfig --region us-east-1 \
  --name startup-devops-baseline-test --kubeconfig "$KUBECONFIG"
kubectl config current-context
kubectl argo rollouts get rollout demo-api -n startup-apps
kubectl -n startup-apps get analysisruns
```

Verify the context ARN's account and exact test cluster before any manual
mutation. At the reviewed indefinite pause, if you approve continuing:

```bash
kubectl argo rollouts promote demo-api -n startup-apps
kubectl argo rollouts status demo-api -n startup-apps
```

This is a separate operator approval, not an automatic step of the checker.
Do not promote a failing/aborted analysis just to obtain a pass. A first stable
deployment might not exercise a new canary at all; the evidence does not claim
a traffic-backed Canary experiment from a Healthy state alone.

## 6. Read-only observation and fresh evidence

The default checker requires the bounded runtime read/port-forward permissions
already declared by the repository. If you are using an existing trusted local
operator/admin profile instead, explicitly select `--operator-observation`.
This does not grant privileges: it records that the code is read-only while
least privilege of the actor is not verified. Do not claim it as the restricted
runtime-role test. No new GitHub workflow or IAM trust change is included.

```bash
./scripts/check-aws-test-observability-qualification.py \
  --application-version "$EXPECTED_APPLICATION_VERSION" \
  --operator-observation \
  --output "/tmp/aws-test-observability-$(date -u +%Y%m%dT%H%M%SZ).json"
```

Omit `--operator-observation` when using the bounded runtime identity. It uses
its own temporary kubeconfig regardless of your shell's active context.
Exit 0 means `qualified`, 2 means absent environment (`waiting-runtime`), and
1 means failure. Invalid preflight input stops before evidence construction.
Evidence is never overwritten; every attempt requires a new output name.

Checks cover root/all nine same-repository resolved SHAs, external Chart pins,
Healthy Rollout and stable hash, exact version/image digest, ready application
Pods and monitoring workloads, Prometheus target/rules, six dashboard ConfigMaps,
Alertmanager readiness, and absence of undeclared logging/tracing components.
Dashboard ConfigMap presence does not prove browser rendering. Idle SLO series
remain `supported-not-verified`, and Healthy Rollout state does not prove a
new SLO-aware Canary drill. No application traffic is generated by the checker.

Evidence uses the existing v0.11.8.0 schema and `qualificationVersion` v0.11.8.2
(the stage version), with aws-test identity. The implementation increment is
v0.11.8.2.1. It is not dev evidence relabeled as test evidence.

## 7. Preserve evidence and clean up

Review/copy the fresh evidence to your approved evidence location. Do not
commit plan files, kubeconfigs, Terraform state or credentials. When finished,
review the existing test cleanup runbook and run cleanup only from the intended
AWS account with the same independent test state:

```bash
AWS_REGION=us-east-1 CLUSTER_NAME=startup-devops-baseline-test \
TF_DIR="$PWD/infra/terraform/aws/environments/test" \
  ./scripts/destroy-aws-test.sh
AWS_ENVIRONMENT=aws-test AWS_REGION=us-east-1 \
CLUSTER_NAME=startup-devops-baseline-test \
TF_DIR="$PWD/infra/terraform/aws/environments/test" \
  ./scripts/validate-aws-cost-cleanup.sh
```

The destroy command has its own destructive confirmation and removes test
backups as documented by the existing flow. It is never invoked by preparation
or qualification. Keep the state until cleanup is verified; securely remove
your temporary plan/kubeconfig files afterwards. Prod remains out of scope.
