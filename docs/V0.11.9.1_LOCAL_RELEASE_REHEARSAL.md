# v0.11.9.1.1 Local successful release rehearsal

## Safety boundary

This runbook performs a real deployment and bounded stable/canary traffic on one
loopback-only kind cluster. It never promotes, retries or rolls back automatically.
It does not deploy AWS, inject failures or qualify production. Keep the evidence
bundle outside Git. Use only `feature/v0.11-observability-sre-baseline` with a
clean, pushed HEAD and a healthy v0.11.7.3-profile local cluster.

Required tools: bash, Python 3.10+, git, kubectl, Argo CD CLI, the kubectl Argo
Rollouts plugin, curl and jq. The context must be `kind-<cluster-name>` and its
API endpoint must resolve to loopback.

## Operator map

| Order | Terminal | Command phase | Wait for this visible result | Next action |
| --- | --- | --- | --- | --- |
| 1 | 1 | `prepare` | `prepare passed` and printed bundle path | Copy the raw path to terminal 2 |
| 2 | 2 | `first-analysis` | `Waiting for Rollout application version` or traffic output | Start `deploy` in terminal 1 |
| 3 | 1 | `deploy` | `deploy passed` | Wait for terminal 2 to report `first-analysis passed` |
| 4 | 1 | `human-review` | `human-review passed` and Rollout is at the 50% pause | Start `second-analysis` in terminal 2 |
| 5 | 2 | `second-analysis` | Traffic/waiting output is visible | Run the one manual promote in terminal 1 |
| 6 | 2 | — | `second-analysis passed` | Run `final` in terminal 1 |
| 7 | 1 | `final` | `final passed` and `runtime_qualified: true` | Preserve and review evidence |

Do not promote before human review passes. Do not promote a second time. Do not
start `final` while `second-analysis` is still running or failed.

## 1. Prepare — terminal 1

```bash
cd ~/startup-devops-baseline
kubectl config get-contexts
read -r -p 'Exact local kind context: ' LOCAL_CONTEXT
kubectl --context "$LOCAL_CONTEXT" get nodes
read -r -p 'Review/ticket reference: ' REVIEW_REF
read -r -p 'Recovery owner: ' RECOVERY_OWNER
RELEASE_VERSION="v0.11.9.1.1-$(date -u +%Y%m%d%H%M%S)"
REHEARSAL_PARENT=$(mktemp -d /tmp/local-release-rehearsal.XXXXXX)
REHEARSAL_DIR="$REHEARSAL_PARENT/run"

python3 scripts/local-release-rehearsal.py prepare \
  --bundle "$REHEARSAL_DIR" \
  --context "$LOCAL_CONTEXT" \
  --version "$RELEASE_VERSION" \
  --review "$REVIEW_REF" \
  --recovery-owner "$RECOVERY_OWNER" \
  --confirm observe-local

printf 'Bundle path for all terminals: %s\n' "$REHEARSAL_DIR"
```

The `run` directory must not already exist. The plan expires after four hours.
Preparation records the cluster UID, API server, exact source commit, baseline
version and the baseline image tag plus Ready Pod runtime `imageID`. The candidate
reuses that same known-good binary; a runtime imageID is not presented as a
registry digest.

## 2. Enter the bundle path correctly — terminal 2

Shell variables are not shared between terminals. At this prompt, enter only the
literal path printed by terminal 1:

```text
Existing bundle path from terminal 1: /tmp/local-release-rehearsal.ABC123/run
```

Do not enter this assignment form:

```text
REHEARSAL_DIR=/tmp/local-release-rehearsal.ABC123/run
```

Run:

```bash
cd ~/startup-devops-baseline
read -r -p 'Existing bundle path from terminal 1: ' REHEARSAL_DIR
python3 scripts/local-release-rehearsal.py first-analysis \
  --bundle "$REHEARSAL_DIR" \
  --confirm generate-local-traffic
```

The runner now mirrors child output live to the terminal and retains the same
output in `command.log`. When it says to start deploy, continue immediately in
terminal 1; do not wait for `first-analysis` to exit.

## 3. Deploy — terminal 1

```bash
python3 scripts/local-release-rehearsal.py deploy \
  --bundle "$REHEARSAL_DIR" \
  --confirm deploy-reviewed-local
```

Wait for both `deploy passed` in terminal 1 and `first-analysis passed` in
terminal 2. A deployment attempt is never replayable automatically. If deploy
fails or its outcome is ambiguous, stop and inspect; do not delete
`deploy.started.json`.

## 4. Review the 50% pause — terminal 1

```bash
python3 scripts/local-release-rehearsal.py human-review \
  --bundle "$REHEARSAL_DIR" \
  --review "$REVIEW_REF" \
  --confirm observe-local

kubectl argo rollouts get rollout demo-api \
  -n startup-apps --context "$LOCAL_CONTEXT"
```

Confirm the first AnalysisRun succeeded, the Rollout is at the 50% indefinite
pause, SLO/Grafana/alerts are acceptable, and the recovery identity is known.
If review is not approved, stop. The review reference is an operator record,
not cryptographic authorization.

## 5. Arm second analysis, then promote once

In terminal 2:

```bash
python3 scripts/local-release-rehearsal.py second-analysis \
  --bundle "$REHEARSAL_DIR" \
  --confirm generate-local-traffic
```

Wait until terminal 2 prints traffic generation or that it is waiting for the
successful second AnalysisRun. Only then, in terminal 1, run:

```bash
kubectl argo rollouts promote demo-api \
  -n startup-apps --context "$LOCAL_CONTEXT"
```

The runner never issues that command. Keep watching terminal 2 until it prints
`second-analysis passed`.

## 6. Final acceptance — terminal 1

```bash
python3 scripts/local-release-rehearsal.py final \
  --bundle "$REHEARSAL_DIR" \
  --confirm observe-local
```

Only `final.passed.json` with `runtime_qualified: true` qualifies this local
successful-release rehearsal. Final verifies Healthy convergence, stable
endpoint coverage, two distinct fresh release-bound six-metric AnalysisRuns,
image/version identity and exact Root/demo-api GitOps commit/sync state.

## Logs and diagnosis

The active attempt path is printed when every command starts. To rediscover the
newest command log from a separate observation terminal:

```bash
ATTEMPT_DIR=$(find "$REHEARSAL_DIR" -mindepth 1 -maxdepth 1 -type d \
  -name '*-*' -printf '%T@ %p\n' | sort -n | tail -1 | cut -d' ' -f2-)
printf 'Newest attempt: %s\n' "$ATTEMPT_DIR"
tail -n 100 -f "$ATTEMPT_DIR/command.log"
```

Inspect rollout and analyses without changing them:

```bash
kubectl argo rollouts get rollout demo-api \
  -n startup-apps --context "$LOCAL_CONTEXT"
kubectl get analysisruns -n startup-apps --context "$LOCAL_CONTEXT" \
  --sort-by=.metadata.creationTimestamp
kubectl get pods -n startup-apps --context "$LOCAL_CONTEXT" \
  -l app=demo-api -o wide
```

After a successful phase command, the runner waits up to 120 seconds for all
matching release Pods to become Ready with a consistent runtime imageID. The
message about waiting during Canary replica scaling is informational. If the
bound expires, preserve the new failure attempt and inspect the commands above.

## Retry decision table

| Situation | Allowed action | Prohibited action |
| --- | --- | --- |
| `prepare passed` | Continue with the same bundle | Replay prepare or create a second plan for this run |
| `deploy` failed/ambiguous | Stop, inspect current GitOps/Rollout state and obtain explicit recovery approval | Blind deploy retry, marker deletion or automatic rollback |
| `first-analysis` failed | Diagnose logs and AnalysisRuns; retry the phase only if deploy state is known and no failed candidate AnalysisRun makes the candidate invalid | Promote while unresolved |
| `human-review passed` | Arm second analysis | Replay review or promote before second analysis is armed |
| `second-analysis` timed out before promotion and Rollout is still safely at 50% with no failed candidate AnalysisRun | Diagnose, then explicitly retry `second-analysis`; promote once after its visible signal | Automatic retry or repeated promote |
| Any candidate AnalysisRun is `Failed`, `Error` or `Inconclusive` | Preserve evidence and stop for separately authorized recovery | Retry until green or treat old analyses as evidence |
| A phase already has `*.passed.json` | Continue to its documented successor | Replay the successful phase |

Every attempt is append-only and retains `before.json`, `command.log`, an
`after.json` on command success, or `failure.json` plus best-effort
`failure-state.json`. Do not delete markers to force replay and do not reuse an
old bundle for a new rehearsal. Failure/recovery automation remains v0.11.9.2
work and this increment makes no recovery attestation.
