# v0.11.9.1 Local successful release rehearsal

## Scope and prerequisites

This runbook performs a real **local** deployment and bounded stable/canary
traffic. It does not deploy AWS, promote automatically, inject failures, or
roll back automatically. Prod remains deferred to the v0.11 tail.

First apply this increment, run offline quality gates, review, commit and push
the feature branch. Live phases require a clean worktree and exact HEAD equal
to the canonical remote feature branch. Do not switch to main.

Use an existing healthy local kind cluster with the v0.11.7.3 SLO/Canary profile,
observability components and a previously validated tracing-capable demo-api
image loaded on its nodes. No active analysis or incomplete rollout is allowed.
Install the existing toolchain: kubectl, Argo CD CLI with Rollouts plugin,
bash, Python 3.10+, curl, jq, git and the tools required by the existing local
deployment scripts. These are not installed by this increment.

The API endpoint must be loopback and the context must be `kind-<cluster-name>`.
Remote kind endpoints, sidecar-containing application pods and AWS contexts
are deliberately unsupported by this bounded profile.

## Image identity: do not invent a digest

This is a new application-version rollout of the **same known-good binary**.
Preparation reads the current Rollout image tag, `Never` pull policy and Ready
Pod runtime `imageID`; the candidate reuses that image. Each analysis/final
phase checks the candidate's image reference and imageID against that baseline.
There is no image build, image publish or different-binary acceptance in .9.1.

This local evidence is explicitly `local-tag-plus-runtime-image-id`; a runtime
imageID is not re-labelled a registry digest. The strict .9.0 offline plan
format remains unchanged and is not an input to this local runner. The runner
creates its own observed `plan.json`; do not fill or pass the .9.0 template here.

## 1. Prepare in terminal 1 (read-only cluster checks)

List contexts and select your local context, not a dev/test shell default:

```bash
cd ~/startup-devops-baseline
kubectl config get-contexts
read -r -p 'Exact local kind context: ' LOCAL_CONTEXT
kubectl --context "$LOCAL_CONTEXT" get nodes
read -r -p 'Review/ticket reference: ' REVIEW_REF
read -r -p 'Recovery owner: ' RECOVERY_OWNER
RELEASE_VERSION="v0.11.9.1-$(date -u +%Y%m%d%H%M%S)"
REHEARSAL_PARENT=$(mktemp -d /tmp/local-release-rehearsal.XXXXXX)
REHEARSAL_DIR="$REHEARSAL_PARENT/run"
python3 scripts/local-release-rehearsal.py prepare \
  --bundle "$REHEARSAL_DIR" --context "$LOCAL_CONTEXT" \
  --version "$RELEASE_VERSION" --review "$REVIEW_REF" \
  --recovery-owner "$RECOVERY_OWNER" --confirm observe-local
printf 'Bundle path for BOTH terminals: %s\n' "$REHEARSAL_DIR"
```

The `run` directory must not exist before prepare. Review `plan.json` and the
prepare snapshot: baseline version/image, target cluster and recovery owner.
Preparation pins kube-system UID and API server; every later phase rechecks
them and source HEAD. Plans expire after four hours. Credentials are only in
a private temporary kubeconfig during each command, never in bundle evidence.

## 2. Start first analysis in terminal 2 BEFORE deployment

Copy the **literal bundle path printed above** into this terminal. Shell
variables are not shared automatically.

```bash
cd ~/startup-devops-baseline
read -r -p 'Existing bundle path from terminal 1: ' REHEARSAL_DIR
python3 scripts/local-release-rehearsal.py first-analysis \
  --bundle "$REHEARSAL_DIR" --confirm generate-local-traffic
```

This waits for the candidate version, then sends bounded traffic to the local
stable/canary services and verifies the first six-metric SLO AnalysisRun.
Immediately continue step 3 in terminal 1; do not wait for step 2 to finish.
Candidate wait is bounded by the predecessor script (normally five minutes).
Command output is retained under `first-analysis-*/command.log`; use `tail -f`
on that file from another terminal if needed. Each command has a 15-minute
outer bound; timeout stops only its own process group/port-forwards.

## 3. Deploy in terminal 1 (explicit mutation)

```bash
python3 scripts/local-release-rehearsal.py deploy \
  --bundle "$REHEARSAL_DIR" --confirm deploy-reviewed-local
```

This uses `deploy-local-feature-gitops.sh` with the pinned commit, observed
image and new version. It can reconcile the local Root and its child
Applications, not only demo-api. Argo CD is forced into core mode against the
isolated local kubeconfig; an unrelated saved cloud Argo CD login is not used.
Do not run another deployment concurrently. A deployment attempt is never
automatically replayed, including after partial failure.

Wait for BOTH deploy and first-analysis to report passed.

## 4. Human review at 50% (read-only), then explicit promote

```bash
python3 scripts/local-release-rehearsal.py human-review \
  --bundle "$REHEARSAL_DIR" --review "$REVIEW_REF" --confirm observe-local
kubectl argo rollouts get rollout demo-api -n startup-apps --context "$LOCAL_CONTEXT"
```

Review the first analysis, SLO/Grafana/alerts, stable availability and the
prepared recovery identity. A review reference is an operator record, not a
cryptographically authenticated approval. If you decide not to proceed, stop.

If approved, first start step 5 in terminal 2, then explicitly promote in
terminal 1:

```bash
kubectl argo rollouts promote demo-api -n startup-apps --context "$LOCAL_CONTEXT"
```

The script never issues this command. Keep the current human-governed policy;
this is not a claim that every team must use the same approval design.

## 5. Second analysis in terminal 2

```bash
python3 scripts/local-release-rehearsal.py second-analysis \
  --bundle "$REHEARSAL_DIR" --confirm generate-local-traffic
```

It must identify two distinct, fresh, release-bound successful AnalysisRuns,
owned by this Rollout, each containing all six successful SLO metrics. Old
analyses, provider failures and absent traffic cannot substitute for a pass.

## 6. Final acceptance in terminal 1

After step 5 passes:

```bash
python3 scripts/local-release-rehearsal.py final \
  --bundle "$REHEARSAL_DIR" --confirm observe-local
```

Final reuses the .7.3.1 bounded convergence wait and .7.3 SLO observability
checks. It also verifies image/version, fresh analyses, stable endpoint
coverage and the Root/demo-api GitOps commit/sync state. Only
`final.passed.json` marks this local successful-release rehearsal qualified.
It does not qualify AWS, fault recovery, different-image delivery or prod.

## Failure, recovery and retained evidence

Every command attempt preserves before/after snapshots, command logs and any
failure record. Failed attempts do not produce a passed marker; read-only or
traffic phases can be explicitly retried after diagnosis, with a new attempt
directory. Successful phases refuse replay. Do not delete markers to force
another deployment. Never use an old bundle to represent a new rehearsal.

On failure: stop promotion, retain the bundle, inspect Rollout/AnalysisRun
states with the explicit context, and review `plan.json` for the known-good
baseline version/image. Do not interpret a partially applied deployment as
unapplied. Recovery is separately authorized: use the existing
`deploy-local-feature-gitops.sh` only after reviewing its pinned source,
baseline image/version and current Argo CD target. Do not run an implicit
context rollback or blindly reapply the candidate. A full controlled failure
and recovery runner is .9.2 work; this increment cannot attest recovery.

Keep the private bundle outside Git. It contains internal resource metadata,
not a sanitized public report or tamper-proof audit ledger. Restrict access
and redact before sharing. It is not the .8 observability evidence schema;
do not register it with that archive command. Retain failed AnalysisRuns and
runtime history. No cluster/PVC deletion or cost cleanup occurs here.
