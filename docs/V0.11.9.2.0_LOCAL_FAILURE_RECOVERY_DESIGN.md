# v0.11.9.2.0 Local candidate rejection and recovery design

## Boundary

This checkpoint defines and validates the next local failure/recovery rehearsal
offline. It does not implement a fault endpoint, build an image, contact GitHub,
run kubectl, generate traffic, abort a Rollout, restore GitOps state or qualify
runtime recovery. Do not rerun or disturb the already successful v0.11.9.1
Rollout to accept this increment.

The only planned environment is one loopback kind cluster on
`feature/v0.11-observability-sre-baseline`. AWS and production remain out of
scope. v0.11.9.2.1 must undergo separate code review before any live approval.

## Why the failure mechanism must be explicit

The current Canary availability query selects `GET /version`, status class
`5xx`, the Canary Prometheus job and the exact candidate release ID. Requests
to an unknown path therefore cannot prove the intended SLO rejection. Pod
deletion, database damage, Prometheus outages and no-data results also fail to
isolate the candidate availability signal.

The reviewed v0.11.9.2.1 implementation target is a test-only application
capability with these properties:

- default state is disabled and ordinary requests are unchanged;
- only candidate Pods explicitly configured with `availability-503` can fault;
- `/version` returns HTTP 503 only when a per-run runtime token is also supplied
  in `X-Rehearsal-Fault`;
- the raw token is generated at runtime, never committed or stored in shareable
  evidence; only a one-way fingerprint may be retained;
- fault traffic goes directly to `demo-api-canary`, while independent control
  traffic continuously checks `demo-api-stable`;
- at most 80 fault requests and 180 seconds are allowed, followed by bounded
  process/fixture cleanup;
- the qualifying failure must be the
  `canary-availability-error-budget-burn-rate` metric and AnalysisRun `Failed`;
  provider errors, no data and wrong-target failures are rejected.

## Two-stage same-binary isolation

The fault-capable image cannot be introduced for the first time as the failing
candidate. That would mix a new binary with the injected configuration. The
future live rehearsal must first deploy that binary with fault mode disabled,
complete a successful local release, and record it as the new known-good
baseline. The rejection candidate then uses a distinct application version and
release ID but the exact same image reference and runtime imageID, with fault
mode enabled only on its new Pod template.

This creates a controlled comparison:

| Identity/property | Healthy baseline | Rejection candidate |
| --- | --- | --- |
| Image reference and runtime imageID | Recorded | Must be identical |
| Application version/release ID | Known good | Fresh and distinct |
| Fault mode | `disabled` | `availability-503` |
| Fault token header | No effect | Required for 503 |
| Traffic target | Stable control | Canary fault traffic |

If the binary identity differs, stable control traffic degrades, or the baseline
is not Healthy before candidate creation, stop without fault traffic.

## Required future state order

1. `prepared`: exact pushed source, loopback context, Healthy baseline identity,
   reviewer, recovery owner, deadlines and private evidence directory are pinned.
2. `fault-armed`: candidate-only mode and runtime token fingerprint are observed;
   stable Pods remain fault-disabled.
3. `traffic-active`: bounded Canary fault traffic and stable control traffic run;
   every child process is owned by this attempt.
4. `analysis-failed`: the exact release-bound AnalysisRun fails the availability
   burn-rate metric with real samples—not provider error or no data.
5. `abort-confirmed`: candidate did not become stable, no promotion occurred and
   stable availability remained acceptable. Abort remains an explicit reviewed
   action unless Rollout's existing analysis semantics already produced it; the
   runner must observe, never silently manufacture, the claimed state.
6. `recovery-approved`: evidence is preserved before a separately recorded human
   recovery decision.
7. `desired-baseline-restored`: GitOps desired version, fault-disabled mode and
   exact known-good binary are restored together; a runtime-only undo is not enough.
8. `healthy-verified`: current/stable ReplicaSet, Ready Pods, Service/Endpoints,
   GitOps sync, stable metrics and absence of active fault fixtures converge.

Failure, abort and restoration are separate facts. A failed AnalysisRun alone
does not prove the stable service survived, and an aborted Rollout alone does not
prove Git desired state or runtime health was restored.

## Offline plan preflight

Copy the template outside the repository. The unedited tracked example is
supposed to fail:

```bash
PLAN_PARENT=$(mktemp -d /tmp/local-failure-recovery-plan.XXXXXX)
PLAN_FILE="$PLAN_PARENT/plan.json"
cp delivery/examples/v0.11.9.2.0-local-failure-recovery-plan.json "$PLAN_FILE"
chmod 600 "$PLAN_FILE"
```

Fill every `REPLACE` field from a future freshly observed baseline. For example,
the values must look like:

```json
{

  "context": "kind-startup-devops",
  "evidence_directory": "/tmp/local-failure-recovery.ABC123/run",

```

Keep all other required fields from the template, then validate:

```bash
python3 scripts/check-v0.11.9.2.0-failure-recovery-plan.py \

```

Expected output includes:

```text
"status": "failure_recovery_plan_validated_offline"

"execution_authorized": false

```

The checker performs JSON and safety-contract validation only. It makes no Git,
network, Kubernetes, process or filesystem mutation. A passing plan is not a
command to begin the rehearsal. No execution is authorized by this checkpoint.

## Stop and recovery decision matrix for v0.11.9.2.1

| Observation | Required decision | Forbidden interpretation/action |
| --- | --- | --- |
| Baseline not Healthy or identity changed | Stop before arming | Continue because the previous run once passed |
| Stable control traffic fails | Stop fault traffic, preserve evidence, assess incident | Claim candidate-only isolation |
| Prometheus provider error or no data | Stop as invalid experiment | Count it as SLO rejection |
| Wrong metric fails | Stop as invalid experiment | Retry until the desired metric fails |
| Exact availability metric and AnalysisRun fail | Preserve evidence and verify stable/abort state | Promote or delete the AnalysisRun |
| Candidate unexpectedly becomes stable | Stop and escalate; do not start scripted recovery | Relabel it as successful rejection |
| Recovery identity/approval is missing | Retain current state and stop | Guess a baseline or run automatic rollback |
| Desired baseline restored but runtime not Healthy | Continue bounded observation, then stop on deadline | Claim recovery from Git sync alone |
| Runtime Healthy but Git desired state differs | Stop as incomplete restoration | Claim recovery from runtime alone |

No successful or failed phase may be replayed by deleting evidence markers.
Retries require a new attempt record and are never automatic. Do not remove
failed AnalysisRuns or rollout history before the evidence review closes.
