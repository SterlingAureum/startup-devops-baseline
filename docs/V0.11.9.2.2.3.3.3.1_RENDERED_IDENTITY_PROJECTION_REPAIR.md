# v0.11.9.2.2.3.3.3.1 rendered identity projection repair

## Finding

The inherited v0.11.6.1.0 validator rejected the current Rollout render with:

```text
platform.startup.dev/source-commit is not rendered exactly once
```

The rendered Rollout was not invalid. The annotation is deliberately consumed
by two independent mechanisms: the demo-api container receives it through the
Kubernetes Downward API, and each SLO-aware AnalysisRun step receives it as a
release identity argument. With two analysis steps, a global text count sees
three valid `source-commit` field references. The historical validator had
already special-cased this successor behavior for `release-id`, but not for
`source-commit` or `image-digest`.

## Repair

The rendered-manifest check now validates the container projection as an exact
named `valueFrom.fieldRef` binding. Rollout analysis arguments are checked
separately. Their required count is derived from the rendered
`expected-release-id` bindings, so every analysis step must carry matching
`source-commit` and `image-digest` bindings. A Deployment must have exactly one
container binding for each identity field and no AnalysisRun bindings.

The focused regression covers the accepted two-analysis-step Rollout and rejects
a duplicate container projection, a missing AnalysisRun source binding, and an
AnalysisRun binding added to a Deployment.

This increment does not change the Helm chart, immutable image identity,
application version, release ID, workload annotations, or Rollout strategy.
Validation is offline and performs no Kubernetes, Argo CD, traffic, image,
Rollout, or AWS operation. Consequently, applying this repair must not create a
new Rollout revision or AnalysisRun.
