# v0.11.9.3.6.4.1 aws-dev monitoring convergence repair

## Outcome

The `.3.6.4` Root deployment completed its GitOps, database, External Secrets,
demo-api and DNS scope, but live evidence found `monitoring-aws-dev` in
`Synced / Degraded`. The aws-dev demo workload itself was healthy and correctly
used a Deployment; aws-dev intentionally does not require a Rollout or an
AnalysisRun.

The blocking Grafana Pod was in `CreateContainerConfigError` because the
independent `observability-grafana-admin` runtime Secret did not exist. Waiting
alone cannot create that Secret. This repair adds a separate resumable boundary
between Root deployment and runtime qualification.

## Safety boundary

`verify` performs only reads and accepts exactly two states:

1. the reviewed incomplete state: monitoring is `Synced / Degraded`, the
   Grafana Secret is absent and the Grafana Deployment is unavailable;
2. the idempotent final state: monitoring is `Synced / Healthy`, the Secret is
   present and the Grafana Deployment is fully Ready.

Any Degraded state with an existing Secret is treated as an unrelated failure
and is rejected. The operator must diagnose that state instead of overwriting
credentials or retrying this repair.

`execute` repeats verification and requires a separate confirmation. When the
Secret is absent, it invokes the existing create-only
`prepare-aws-dev-grafana-secret.py` entrypoint, waits up to ten minutes for the
Grafana Deployment and monitoring Application, then repeats exact-main and live
postcondition checks. When the reviewed state is already converged, execution
performs no write and returns `grafana_secret_action=preserved`.

The executor never prints or writes credential values to an evidence file. It
does not redeploy Root, sync Argo CD manually, generate traffic, qualify the
runtime, promote progressive delivery or destroy aws-dev.

missing-Secret state or the already-converged state.

## Eight-hour timebox and continuation

The planned eight hours are an operational review and cost timebox, not an AWS
automatic expiry. The cluster continues to incur cost until teardown even if
the testing window ends.

Do not edit an already reviewed or executed plan to extend its end time. At the
end of the approved window:

1. stop initiating new writes, traffic, promotion or qualification phases;
2. record the current commit, phase result, live application health and private
   log hashes;
3. decide explicitly whether to keep the stable cluster running or perform the
   separately reviewed teardown;
4. for a later continuation, create a new time-window plan referencing the
   preserved evidence, rerun exact-main and live-state preflight, and obtain a
   new phase approval.

If the pause is only minutes and the current approval is still valid, finish the
active bounded command. If testing will continue beyond the reviewed end time,
start no new command under the old approval. For an overnight or uncertain
pause, teardown is normally preferred because EKS, EC2, NAT, load balancers and
storage continue billing; preserve evidence before teardown and recreate from
the reviewed checkpoint later.
