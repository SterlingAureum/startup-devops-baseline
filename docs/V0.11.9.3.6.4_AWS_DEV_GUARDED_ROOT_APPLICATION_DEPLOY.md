# v0.11.9.3.6.4 aws-dev guarded Root Application deploy

## Outcome

This checkpoint implements, but does not execute, the first aws-dev Root-tree
deployment after the successful `.3.6.3` GitOps bootstrap. It replaces direct
aws-dev use of `deploy-aws-dev-root-app.sh` with an explicit two-phase executor.

`verify` performs only reads. `execute` repeats the same verification, requires
a separate full-scope confirmation, invokes the existing deployment once, then
rechecks protected main and the live Root resolved revision.

## Exact preconditions

The executor requires:

- clean `main`, with `HEAD`, `origin/main` and live `ls-remote` main equal to
  the supplied reviewed SHA;
- exact SHA-256 fingerprints for the aws-dev Root manifest and release file;
- the private 12-digit expected AWS account matching STS;
- ACTIVE `startup-devops-baseline-dev`, matching kubectl endpoint and
  `/readyz=ok`;
- exactly 103 Terraform state addresses and the EKS cluster address;
- valid VPC, CNPG backup, External Secrets and Route53 Terraform outputs;
- an existing non-deleted Secrets Manager container, without reading its value;
- exactly one public `aureumstack.com` zone matching Terraform;
- all seven expected Argo CD workloads fully Ready on the recorded images;
- the ALB controller Application `Synced / Healthy` on chart `1.14.0`, with its
  cluster, region and live VPC ID matching Terraform;
- no existing aws-dev Root Application or other unexpected Argo CD Application.

Any partial Root state blocks both phases and requires inspection.

## Write scope requiring separate approval

The underlying script performs more than a single `kubectl apply`. One approval
covers this complete, already existing ordered operation:

1. configure External Secrets and CloudNativePG backup IRSA ServiceAccounts;
2. apply the aws-dev Root Application tracking `main`;
3. wait for External Secrets, PostgreSQL and demo-api basic GitOps convergence;
4. apply the Terraform S3 destination to the live CNPG ObjectStore;
5. initialize or idempotently validate the Secrets Manager database credential;
6. force and then remove ExternalSecret synchronization metadata;
7. reconcile the stable `demo.dev.aureumstack.com` Route53 Alias.

The executor does not promote an Argo Rollout, run SLO/runtime qualification,
generate qualification traffic, replay a fault, promote aws-test or tear down
aws-dev.

## Later read-only verification

Only after this increment reaches protected main:

```bash
git switch main
git pull --ff-only origin main

export EXPECTED_CONTROL_PLANE_COMMIT="$(git rev-parse HEAD)"
export EXPECTED_AWS_ACCOUNT_ID='<reviewed 12-digit account>'
export CONFIRM_AWS_DEV_ROOT_PREFLIGHT='observe-reviewed-aws-dev-root-deploy'

python3 scripts/execute-v0.11.9.3.6.4-aws-dev-root-application-deploy.py \
  verify \
  --expected-control-plane-commit "${EXPECTED_CONTROL_PLANE_COMMIT}"
```

Expected status is `aws-dev-root-deploy-inputs-verified` with
`execution_authorized=false`, Root absent, 103 state addresses, Argo CD
`v3.5.2` and ALB `Synced/Healthy`. The result emits no account, ARN, bucket,
VPC, secret or hosted-zone identifier.

## Later separately approved execution

Do not infer write approval from a successful verify. After explicit review in
the active cost window, retain the preflight confirmation and set:

```bash
export CONFIRM_AWS_DEV_ROOT_DEPLOY='deploy-reviewed-aws-dev-root-application'

python3 scripts/execute-v0.11.9.3.6.4-aws-dev-root-application-deploy.py \
  execute \
  --expected-control-plane-commit "${EXPECTED_CONTROL_PLANE_COMMIT}"
```

Do not set the internal entrypoint token manually. If execution fails, preserve
Terraform and cluster state and do not rerun, promote, rollback or destroy until
the partial state has been reviewed.

Success requires the Root Application to be `Synced / Healthy`, still track
`main` and resolve exactly to the supplied reviewed SHA. That result is only a
basic GitOps/data/secret/DNS deployment checkpoint; `.3.6.5` retains separate
runtime and progressive-delivery qualification.
