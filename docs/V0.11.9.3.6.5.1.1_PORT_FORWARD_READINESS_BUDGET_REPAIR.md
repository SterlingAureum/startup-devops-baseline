# v0.11.9.3.6.5.1.1 port-forward readiness budget repair

## Second preflight result

The first post-`.3.6.5.1` read-only preflight stopped before traffic. The
repaired loopback port-forward announced its listener and handled 13 local
connections. Each one-second readiness request expired before a complete
Prometheus response arrived, and the 30-second total readiness window then
closed.

The executor exited `1`, emitted no successful JSON result and created no
runtime qualification. Its failure stderr remains private and is pinned only
by SHA-256. The subsequent process check reported no port-forward residual,
which proves the `.3.6.5.1` normal/error cleanup path worked as designed.

## Root cause

This is not the earlier API Service Proxy mismatch. The executor used the
correct `pods/portforward` transport, the listener started and connections
reached it. The remaining defect was the one-second per-probe budget, which is
too short for the observed EKS tunnel latency.

The cleanup, loopback binding, dynamic port, anonymous diagnostic file and
forced-kill fallback do not require redesign.

## Repair

The bounded budgets become:

| Boundary | Before | After |
| --- | ---: | ---: |
| Complete port-forward readiness window | 30 seconds | 90 seconds |
| One readiness HTTP attempt | 1 second | 10 seconds |
| One Prometheus API request | 20 seconds | 60 seconds |
| Graceful port-forward shutdown | 5 seconds | 5 seconds |

The final readiness failure now includes the last bounded probe error as well
as the kubectl diagnostic tail. The executor still fails closed and always
cleans the exact isolated child process.

No AWS security group or Kubernetes NetworkPolicy is expanded. The preflight
still generates no application traffic, while a separately approved execution
remains limited to the original 54 normal requests.
