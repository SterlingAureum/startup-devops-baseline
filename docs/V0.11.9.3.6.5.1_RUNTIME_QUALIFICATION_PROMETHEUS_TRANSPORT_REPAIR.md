# v0.11.9.3.6.5.1 runtime qualification Prometheus transport repair

## Observed failure

The first `.3.6.5` read-only aws-dev runtime-qualification preflight stopped
before traffic. Kubernetes reported one Ready, serving, non-terminating
Prometheus endpoint. Its Pod was Running, every container was Ready and no
container had restarted. Nevertheless, three bounded Kubernetes API Service
Proxy attempts timed out while the API Server tried to dial the Pod endpoint
on port `9090`.

The failed command emitted no JSON result. An empty redirected stdout file is
not preflight evidence, and neither execution authorization nor runtime
qualification was produced.

## Diagnosis

A separate loopback-only `kubectl port-forward` reached the same Prometheus
Service and returned `Prometheus Server is Ready.` This proves the Prometheus
runtime and its selected endpoint were available through the repository's
reviewed telemetry transport.

The `.3.6.5` executor had instead introduced Kubernetes API Service Proxy
reads. That path was inconsistent with the existing
`observability-runtime-qualification` Role, which permits read-only resource
discovery plus `create` only on the non-persistent `pods/portforward`
subresource. Opening port `9090` in an AWS security group or broadening a
NetworkPolicy is neither required nor allowed by this repair.

## Repair

The executor now:

- selects an unused local port and binds `kubectl port-forward` only to
  `127.0.0.1`;
- uses one isolated port-forward session for the complete approved execution;
- waits at most 30 seconds for Prometheus readiness with one-second probes;
- limits each Prometheus API request to 20 seconds;
- writes kubectl diagnostics only to an anonymous `0600` temporary file;
- terminates the exact child on normal return, failure or `KeyboardInterrupt`;
- escalates to an exact-process kill only when graceful termination exceeds
  five seconds;
- removes all Prometheus API Service Proxy use.

The read-only preflight still generates no demo-api traffic. The execution
still requires its separate confirmation and remains bounded to the original
54 normal requests.

## Post-merge continuation

Do not apply or run the repaired executor from a feature branch. After the
repair reaches protected `main`:

1. update local `main` and record the new full commit;
2. wait until Root and demo-api resolve that exact commit without forcing a
   workload restart;
3. restore the private account and UTC deadline inputs in the current shell;
4. create a new private preflight result and stderr file;
5. run exactly one repaired read-only `verify`;
6. review its JSON and obtain a new, separate runtime-qualification approval.

The approval issued before this code change cannot authorize execution on the
new control-plane commit. Do not reuse the empty failed stdout file as a
successful result. If fewer than 15 minutes remain in the reviewed window,
start a fresh window instead of weakening the deadline guard.

No security-group, NetworkPolicy, Root, workload, traffic, qualification,
promotion or teardown action is part of applying this increment.
