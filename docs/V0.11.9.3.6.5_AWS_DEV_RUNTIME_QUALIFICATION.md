## Purpose and status

This checkpoint implements the separately reviewed aws-dev runtime
qualification boundary. The package itself is offline-only: applying and
validating it does not access AWS, Kubernetes, Argo CD or the public demo
endpoint and does not authorize a live run.

The previous aws-dev environment was completely removed before this increment

## Why aws-dev has no promote step

The aws-dev release profile deliberately renders demo-api as a Kubernetes
`Deployment`. Progressive delivery is exercised in aws-test and aws-prod,
where demo-api is an Argo Rollout. The aws-dev qualification must not create an
AnalysisRun or call Rollouts promote, retry, abort or restart.

This checkpoint instead proves that the exact immutable Deployment is healthy,
its database and observability dependencies are ready, bounded normal traffic
produces a Prometheus request series, both SLO ratios remain within the
reviewed thresholds and no critical aws-dev alert fires.


The executor sends at most 54 successful normal requests: 18 rounds across
`/health`, `/ready` and `/version`. It waits across Prometheus scrape windows,
validates every response, then requires:

- a positive aws-dev request recording series;
- availability ratio at least `0.999`;
- latency ratio at least `0.99`;
- zero firing critical aws-dev alerts;
- the final application, database and Grafana runtime still healthy.

The executor neither reads Secret values nor writes repository evidence. Save
stdout and its SHA-256 outside the repository. Do not publish account IDs,
cluster ARNs, private logs or credentials.

## Failure and continuation

If preflight fails, do not generate traffic. Repair or review the reported
state through a separate change or operational checkpoint.

The first live preflight exposed an EKS API Service Proxy transport mismatch.
`.3.6.5.1` replaces that path with the existing loopback-only
`pods/portforward` boundary and adds bounded request and cleanup behavior. Do
not work around this failure by expanding an AWS security group or
NetworkPolicy.

If execution fails after traffic begins:

1. do not rerun automatically;
2. do not promote, retry, abort or patch the Deployment;
3. preserve live state and Terraform state;
4. capture the redacted result and relevant private diagnostics;
5. choose either a separately reviewed retry or teardown.

An expired window cannot be extended by editing old evidence. Start a fresh
window, repeat exact-main and live-state verification, and obtain a new
approval. No automatic teardown is performed when the deadline is reached.
