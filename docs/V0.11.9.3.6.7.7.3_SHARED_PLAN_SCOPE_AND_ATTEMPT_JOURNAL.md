## 精确 Terraform 删除范围

`guarded_plan_rules.managed_inventory(state)` 严格读取传入 v4 state 的 managed definitions，
支持 root、嵌套 module、count 和 for_each 地址。返回 address/module/type/name/id 私有记录。
`validate_destroy_plan(plan,state,reviewed_resources,final=...,reviewed_remote_absence=...)`
逐项核对这些记录、plan before ID、delete actions 和 after=null。

| 场景 | 判定要求 |
| --- | --- |
| targeted | 审核者明确提供当前 state 中的精确 dependency closure；不根据 module 前缀或历史50项数量推定批准。 |
| final | reviewed_resources 必须覆盖当前全部 managed state；每个地址由 delete 或显式审核的 remote absence 覆盖一次。 |
| remote absence | caller 固定 hash-bound fresh native absence evidence，再显式给出对应 drift 地址；仅凭 Terraform JSON 不足以批准。 |
| 拒绝 | 缺项/额外/重复、definition/ID漂移、create/update/replacement、after非空、未审核 drift 或 delete/drift 重叠。 |

该窄接口也拒绝 data/read/no-op 变更，比历史 final gate 更严格；遇到陌生 plan shape
停止并单独复核，不能套用历史成功结论。返回结构保持 deleted/drift 和两个 aggregate count，
其中地址只保存在私有证据。历史 EKS dependency 50项 fixture 已逐字段比较成功输出；
另以新 fixtures 验证 final 完整覆盖和 remote absence，未声称做了 native live 检查。

## Linux 持久日志

`guarded_attempt_journal.AttemptJournal` 接受显式 UTC、binding 与 repository_root。
binding 固定 environment/phase/main/inputs_sha256/state_sha256/proof_sha256/scope_sha256；
environment 必须显式为 aws-dev/test/prod。它不读取时钟、账户、价格或执行服务调用。

| API | 语义 |
| --- | --- |
| reserve(directory,binding,timestamp,repository_root=...) | 在预先创建的持久0700私有目录内，以 O_EXCL 创建0600 marker/events/head 并 fsync。任何部分创建也保留消费状态。 |
| open(directory,binding,expected_marker_sha256,repository_root=...) | 重新校验绑定、原始 marker 哈希、文件归属/权限、hash chain 和 committed head；不重置。 |
| before(operation,timestamp) | intent 先落盘、fsync，然后提交独立 head 并 fsync directory；只有返回后 caller 才可调用一次 transport。 |
| success / failure | 必须匹配唯一 pending intent；success 仍不能重复该 tag；failure 为 terminal。 |
| observed_absent | caller 已确认原生 absence 时跳过 mutation；不得将 pending intent 当作 absence 直接覆盖。 |
| snapshot | 在 flock 下读取一致日志；返回私有 operations、pending、sequence 和 hashes。 |
| complete(expected_operations,timestamp) | 成功/absence tag 集合须精确匹配且无 pending/failure；caller 独立核验所有 postconditions 后才可写 phase receipt。 |

锁锚是固定 marker inode；独立 handle 并发时每个调用先重新读完整日志和 head。
日志使用规范 JSON、严格 schema、单调 UTC 和 SHA-256 前序链；head 独立保存 sequence、
完整 log digest 和字节长度。完整行被截掉也会与 head 冲突。提交中遗留 head-next、
不完整 tail、权限/链接变化、写入或 fsync 失败均停止并保留文件，不自动补写或修复。
文件0600且单链接、目录0700，拒绝 symlink 路径、仓库内和已知 ephemeral/system roots。
这些检查不能自动证明任意路径所在介质永久可靠；caller 应使用持久 home 私有目录，
确认 Linux local filesystem 的 flock/fsync 支持并保留备份。测试在仓库外 synthetic 目录
运行真实文件 IO，未创建用户 host evidence。

一次性边界是“同一 directory + operation tag”。adapter 必须把一个持久路径和有限 tag
集合 hash-bind 到该次批准，不能换目录/改 tag 绕过 marker；本模块不是账户级全局锁。
owner 被视为可信。hash chain/head 可检测截断和不一致，不能防止同 UID 同时重写二者；
外部审核的 marker/证据哈希仍为信任锚。它不是 cryptographic audit authentication。

## 调用与恢复边界

未来 adapter 的顺序是：核验新鲜授权/时钟/范围 → 固定 journal path 并 reserve →
重新核验目标原生状态 → before barrier → 一次调用 → 独立后置核验 → success → complete。
结果不确定时保持 pending 并停止；明确失败写 failure 后停止。即使底层资源已经被删除，
也不能只看 return code 补成功回执。重新打开读取不等于获准续跑；恢复须新批准、原生只读
复核和原始 digest 绑定。持久化失败发生在真实调用之后同样保留 evidence，并停止。
没有任何 marker/reset、旧批准续期、自动重试、自动修复或 finalizer 修改选项。

本批没有把库接入历史 live adapters。下一批新建 versioned fake-transport dev/test/prod
adapters，组合 runtime rules、cleanup rules、exact plan gate 和 durable journal，并核验
实际调用順序与失败停止。prod live 演练、预算、当前价格、窗口及权限仍需独立复核。
