# v0.12.0 Production Readiness Foundation

v0.12.0 starts the final technical-capability version before the v1.0
commercial convergence. It converts the v0.11 handoff into one bounded,
machine-readable plan without creating a backend, migrating state, accessing a
cluster, or granting live execution authority.

The canonical contract is
`delivery/contracts/v0.12.0-production-readiness-foundation.json`.

## Outcome

The capstone is divided into seven implementation and acceptance increments
after this foundation:

| Increment | Outcome |
| --- | --- |
| v0.12.1 | Create and validate the encrypted remote-state foundation. |
| v0.12.2 | Migrate and recover one reviewed non-empty state without infrastructure change. |
| v0.12.3 | Converge release promotion with the separate environment lifecycle. |
| v0.12.4 | Prove the EKS and platform upgrade lifecycle. |
| v0.12.5 | Rebuild infrastructure/GitOps and recover data with measured objectives. |
| v0.12.6 | Validate production access, break-glass, capacity, availability and cost controls. |
| v0.12.7 | Close technical readiness and freeze the feature surface for v1.0 RC. |

Every increment follows an offline implementation/review checkpoint before a
separately approved live checkpoint. An approval is bound to one exact main
revision, environment, scope, time window and evidence set and is never reused
across commits or phases.

## Terraform State Boundary

The four implemented roots remain local in v0.12.0:

- `runtime-identities`;
- `environments/dev`;
- `environments/test`; and
- `environments/prod`.

v0.12.1 adds a fifth bootstrap root and an encrypted S3 backend with five
isolated state keys. v0.12.2 owns migration and recovery. State migration is a
first-class brownfield case: it requires non-empty state, immutable local
backup, preserved lineage/addresses/resource identity, lock verification and a
zero-change plan. Migration, module refactoring and platform upgrade never
share one change or execution window.

## Release and Environment Lifecycle

The existing release model remains authoritative:

1. build one immutable image;
2. prepare a reviewed aws-dev release PR;
3. qualify the exact dev release;
4. automatically prepare an aws-test Promotion PR;
5. merge after human review and complete the test Canary/qualification gate;
6. enter the protected aws-prod Environment;
7. automatically prepare an aws-prod Promotion PR; and
8. merge only after human review.

An absent environment produces `waiting_environment`. Application delivery
does not create or destroy EKS, migrate state, run a production qualification
writer, automatically merge, or automatically roll back.

## Upgrade and Recovery Boundary

Upgrade acceptance requires a reviewed compatibility matrix, deprecated-API
preflight, one-minor EKS sequencing, data-plane and add-on convergence,
controller/platform convergence, service qualification and an explicit
rollback-versus-rebuild decision. A database major upgrade is not combined
with an EKS upgrade.

The default commercial baseline remains single-region, Multi-AZ and
rebuildable. Cross-region active-active service is not a v0.12 or v1.0
requirement. Disaster-recovery acceptance covers loss of a workstation/local
state, a recoverable remote-state object version, a disposable cluster and the
GitOps/data restoration path. RTO/RPO values are approved before the live
rehearsal and measured rather than inferred.

## Documentation and AI Governance

`docs/CURRENT_AUTHORITATIVE_SURFACE.md` identifies the current supported
surface. Historical checkpoint documents and `docs/archive/` remain available
for traceability but are not rewritten into current operating instructions.

AI-assisted content follows `docs/AI_ASSISTED_CONTRIBUTION_POLICY.md` from
this checkpoint onward. Human review, source and license consideration, and
normal CI validation remain mandatory. Credentials, state, customer data and
private evidence are not supplied to an unapproved AI service.

## Explicit Non-Actions

Applying this increment does not:

- create an S3 bucket or KMS key;
- change a Terraform backend or run Terraform initialization;
- migrate, pull, push or restore state;
- access AWS, Kubernetes, GitHub or a container registry;
- create, upgrade or destroy an EKS environment;
- generate traffic or qualification evidence;
- prepare or merge a Promotion PR; or
- convert historical or synthetic receipts into live authority.

## Validation

Run:

```bash
bash scripts/validate-v0.12.0-production-readiness-foundation.sh
```

The validator checks the contract, v0.11 handoff, current state roots, remote
topology, promotion and lifecycle boundaries, documentation authority, AI
governance, privacy, and negative unsafe mutations. It performs no network,
cloud, Kubernetes, Terraform or GitHub operation.
