# v0.12.1.0.1 CI Compatibility Repair

v0.12.1.0.1 repairs two CI failures observed after the v0.12.1 remote-state
foundation merge. It changes no AWS resource declaration or runtime behavior,
does not access credentials, and grants no live execution authority.

The canonical contract is
`delivery/contracts/v0.12.1.0.1-ci-compatibility-repair.json`.

## Failure classification

The quality gate failed with `teardown-source-drift` because v0.12.1 changed
the Terraform version constraint in four existing roots. The closed v0.11
aws-test teardown contract intentionally pins those files byte-for-byte. The
teardown implementation and every other reviewed source file were unchanged.

The Terraform workflow separately stopped in `terraform fmt -check` on
`infra/terraform/aws/state-bootstrap/main.tf`. This happened before Terraform
initialization or validation and was unrelated to the absent private tfvars.

## Repair decision

The four existing roots still use local state throughout v0.12.1, so they do
not yet consume the S3 backend or its native lockfile. Their Terraform floor is
therefore restored to the exact reviewed v0.11 bytes:

- `runtime-identities`: `>= 1.8.0, < 2.0.0`;
- `environments/dev`: `>= 1.8.0, < 2.0.0`;
- `environments/test`: `>= 1.8.0, < 2.0.0`; and
- `environments/prod`: `>= 1.8.0, < 2.0.0`.

This preserves the immutable v0.11 contract instead of rewriting its hashes or
reactivating a closed teardown executor. CI remains pinned to Terraform 1.16.3,
so current validation still uses the modern CLI.

The new `state-bootstrap` root retains `>= 1.11.0, < 2.0.0`. Terraform 1.11
also remains the minimum for every root once S3-native locking is configured.
The existing-root constraint increase must occur in a dedicated
successor-compatible pre-migration checkpoint before v0.12.2 migration, not in
the same execution window as state migration.

The state-bootstrap KMS principal identifier is rendered in canonical
single-line collection form. This is formatting-only and does not alter the
generated IAM policy.

## Why tfvars are not added

`terraform fmt -check` examines Terraform source formatting and failed before
`init` or `validate`. `terraform validate` does not require a concrete value for
the required bucket-name variable. Real bucket names, account identity, tags
and credentials remain in ignored private inputs and must not be committed.

## Validation

Run:

```bash
bash scripts/validate-v0.12.1.0.1-ci-compatibility-repair.sh
```

The validator checks the exact restored historical digests, scoped Terraform
floors, formatting repair digest, v0.12.1 contract and closed v0.11 teardown
validation. When Terraform is installed it additionally runs the exact
repository-wide formatting check used by CI. No AWS, Terraform init, plan,
apply or state operation is performed.

The separate `terraform validate` workflow remains responsible for Terraform
1.16.3 initialization with `-backend=false` and configuration validation.

## Successor package boundary

The previously generated v0.12.1.1 guarded-plan package was based on the
pre-repair tree and must not be applied. After this repair is merged and both
CI workflows pass, v0.12.1.1 must be regenerated from the new protected-main
commit.
