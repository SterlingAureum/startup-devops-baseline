# v0.12.1.2.0.1 State-Bootstrap Post-Apply Recovery

v0.12.1.2.0.1 repairs one fail-closed post-apply validation defect without
repeating the successful state-bootstrap apply. The original executor passed a
KMS alias to `kms:GetKeyRotationStatus`; that API does not support a KMS alias
and requires a key ID or key ARN.
The future apply path now uses the reviewed Terraform output KMS key ARN for
both the rotation-status and key-description reads.

The recovery entry point is
`scripts/execute-v0.12.1.2.0.1-state-bootstrap-recovery.py`. It accepts only the
observed incident shape: the exact saved plan was applied, both private local
state copies are byte-identical, the expected 13 managed addresses exist, the
apply result and live-validation result were never completed, and the captured
KMS failure is `InvalidArnException`.

The canonical contract is
`delivery/contracts/v0.12.1.2.0.1-state-bootstrap-post-apply-recovery.json`.

## Safety boundary

The recovery has two phases:

- `verify` checks private paths, modes, hashes, protected-main identity, plan
  artifacts, Terraform source bytes, applied state, captured outputs and the
  exact failure shape. It runs no Terraform or AWS command.
- `execute` repeats verification, checks the separately approved AWS account,
  and performs only read-only S3, KMS and IAM-policy validation.

It cannot run Terraform init, plan, apply or destroy. It cannot migrate or
modify state, attach IAM policies, write an object to the state bucket, mutate
AWS resources, or retry the prior apply.

Preserve the original plan request, apply request, plan bundle, failed apply
output, staged working state and preserved state copy. Do not rename, edit,
delete or move those artifacts.

## Private recovery request

After this repair is merged and required CI is green, copy the tracked
placeholder to the same owner-only private parent used by the incident:

```bash
install -m 0600 \
  delivery/examples/v0.12.1.2.0.1-state-bootstrap-recovery-request.example.json \
  /private/owner-readable/state-bootstrap-recovery-request.json
```

Populate it with:

- the new exact protected-main recovery commit;
- the original incident protected-main commit and expected AWS account;
- the original private apply request path and SHA-256;
- the original private plan bundle, plan-record and binary-plan SHA-256 values;
- the preserved failed apply output directory;
- the captured `kms-rotation.stderr` SHA-256;
- the identical preserved/working applied-state SHA-256;
- a new recovery output path beneath a mode `0700` parent; and
- a UTC approval interval of at most one hour.

The recovery output directory must not already exist. Keep account identity,
resource identities, state and raw AWS output out of Git, tickets and chat.

## Command-free verification

From the clean synchronized protected-main checkout:

```bash
python3 scripts/execute-v0.12.1.2.0.1-state-bootstrap-recovery.py verify \
  --private-recovery-request /private/owner-readable/state-bootstrap-recovery-request.json
```

A successful result reports `prior_apply_evidence_verified` as true while
`recovery_execution_authorized` and `terraform_apply_authorized` remain false.
Review the redacted hashes and remaining window before granting separate
recovery authority.

## Separately approved recovery execution

Only after approval bound to the exact recovery request and applied-state hash:

```bash
unset CONFIRM_STATE_BOOTSTRAP_PLAN \
  CONFIRM_STATE_BOOTSTRAP_APPLY \
  CONFIRM_TERRAFORM_APPLY \
  CONFIRM_TERRAFORM_DESTROY \
  CONFIRM_STATE_MIGRATION

CONFIRM_STATE_BOOTSTRAP_RECOVERY=complete-read-only-state-bootstrap-post-apply-validation \
python3 scripts/execute-v0.12.1.2.0.1-state-bootstrap-recovery.py execute \
  --private-recovery-request /private/owner-readable/state-bootstrap-recovery-request.json
```

The executor reads the normal AWS credential chain, fixes the region to
`us-east-1`, rejects account drift and records all raw command output as mode
`0600` files beneath the new mode `0700` recovery directory. Public stdout is
limited to commits, hashes, counts and negative mutation assertions.

If recovery fails, preserve every incident and recovery artifact and do not
retry automatically. A successful recovery is not backend-migration authority.
v0.12.1.2.1 records redacted apply/recovery evidence before v0.12.2 performs
any state migration.

## Offline validation

```bash
bash scripts/validate-v0.12.1.2.0.1-state-bootstrap-recovery.sh
```

The validator uses synthetic state and injected AWS responses. It reads no
credentials and invokes no AWS, Terraform, Kubernetes or GitHub operation.
