# v0.12.1.2 Reviewed State-Bootstrap Apply

v0.12.1.2 implements the separately approved consumer for one fresh,
human-reviewed v0.12.1.1 saved plan. This repository checkpoint is delivered
offline. Applying the source increment does not access AWS, run Terraform, or
create the backend foundation.

The canonical contract is
`delivery/contracts/v0.12.1.2-reviewed-state-bootstrap-apply.json`.

## Required sequence

Always merge v0.12.1.2 before producing the fresh plan. A plan produced from
the previous protected-main revision is invalid because it does not prove that
the reviewed apply executor was present in the control plane. The operational
sequence is:

1. merge v0.12.1.2 and require clean, synchronized protected main plus green CI;
2. prepare the private v0.12.1.1 plan request for that exact main revision;
3. run v0.12.1.1 `verify`, obtain plan-only approval, and run `execute` once;
4. review the private JSON/text plan, gate result, source manifest and command
   stderr before their expiry;
5. populate a private v0.12.1.2 apply request with every recorded digest;
6. run v0.12.1.2 `verify`, obtain a separate apply approval, and run `execute`
   once before both the saved plan and approval expire; and
7. preserve the private state/output and record redacted v0.12.1.2.1 execution
   evidence before any v0.12.2 backend migration work.

Do not create a live plan before this implementation is merged. Do not edit an
expiry or reuse an earlier saved plan to make the sequence fit a later window.

## Exact apply boundary

The only Terraform mutation is:

```text
terraform -chdir=<private-reviewed-source> apply -input=false -auto-approve <exact-saved-plan>
```

The executor cannot run Terraform init, plan, destroy, state pull, state push,
backend migration, IAM attachment, Kubernetes, GitHub mutation or an automatic
retry. It uses the exact private source and `TF_DATA_DIR` retained by the plan
bundle.

Immediately before apply it requires:

- clean `main` with `HEAD == origin/main ==` both private requests and the plan
  record;
- the original plan request, all seven plan artifacts, and the plan record to
  match their separately copied SHA-256 values;
- the repository and staged Terraform source manifests to remain identical;
- no local bootstrap state in the repository or staged source;
- at least 15 minutes remaining in the saved-plan and apply-approval windows;
- byte-identical `terraform show -json` output that passes the exact 13-create
  plan gate again;
- the same Terraform version used for planning and the expected AWS account;
  and
- absence of the target bucket, KMS alias and five named IAM policies.

## Private apply request

Copy the placeholder only into an owner-readable directory outside the
repository:

```bash
install -m 0600 \
  delivery/examples/v0.12.1.2-state-bootstrap-apply-request.example.json \
  /private/owner-readable/state-bootstrap-apply-request.json
```

Populate it only after the fresh plan exists. Bind the exact main commit,
expected account, original private plan request, plan bundle, plan record,
binary plan, JSON/text views, gate, source manifest and Terraform-version
digests. The apply output path must be a new child of a mode `0700` directory.
The apply approval window is at most one hour and must not exceed the plan
record expiry.

Keep account identity, bucket name, KMS identity, policy ARNs, state, raw plan,
raw output and private paths outside Git, tickets and chat.

## Local verification and separate approval

Verification performs local file, Git identity, digest, permission, expiry and
plan-gate checks. It runs no Terraform or AWS operational command:

```bash
python3 scripts/execute-v0.12.1.2-state-bootstrap-apply.py verify \
  --private-apply-request /private/owner-readable/state-bootstrap-apply-request.json
```

Review its redacted hashes and both remaining-window values. A successful
verification leaves `terraform_apply_authorized` false. It is not apply
authority.

Only after a distinct approval bound to those exact hashes and expiry:

```bash
export CONFIRM_STATE_BOOTSTRAP_APPLY=apply-reviewed-state-backend-foundation
python3 scripts/execute-v0.12.1.2-state-bootstrap-apply.py execute \
  --private-apply-request /private/owner-readable/state-bootstrap-apply-request.json
unset CONFIRM_STATE_BOOTSTRAP_APPLY
```

Plan, destroy, migration and legacy apply confirmation variables must remain
unset.

## Post-apply validation

After the exact saved plan succeeds, the executor preserves a private copy of
the new local bootstrap state and requires:

- exactly the 13 reviewed managed addresses and no unreviewed state address;
- S3 versioning, bucket-owner enforcement, all four public-access blocks,
  non-public TLS-only policy, SSE-KMS and Bucket Key;
- no object version or delete marker in the new bucket;
- the expected enabled customer-managed KMS key with rotation enabled; and
- exactly five state-access IAM policies with zero group, user or role
  attachments.

The public result contains hashes, counts and booleans only. Resource names,
ARNs, account identity, state and AWS responses remain in the mode `0700`
private output directory as mode `0600` files.

## Failure boundary

Any pre-apply difference stops before mutation. If Terraform apply or a
post-apply check fails, preserve the plan bundle, apply output and local state.
The attempt must not be retried automatically, replanned, imported, destroyed
or treated as success. Perform manual state/resource reconciliation first.

Successful apply is also not migration authority. v0.12.1.2.1 records the
redacted execution evidence. v0.12.2 alone owns backend declarations, immutable
local backup, non-empty migration, lock-contention proof, zero-change planning
and object-version recovery.

## Offline validation

Run:

```bash
bash scripts/validate-v0.12.1.2-reviewed-state-bootstrap-apply.sh
```

The validator uses injected Terraform and AWS responses. It performs no live
operation and creates no backend resource.
