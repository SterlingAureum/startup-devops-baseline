# v0.12.1 Remote State Foundation

v0.12.1 implements the reviewable Terraform declaration for the remote-state
foundation. This checkpoint is complete offline implementation, not evidence
that the S3 bucket, KMS key or IAM policies exist in AWS.

The canonical contract is
`delivery/contracts/v0.12.1-remote-state-foundation.json`.

## Delivered declaration

The independent `infra/terraform/aws/state-bootstrap` root declares:

- one globally named S3 bucket with versioning;
- bucket-owner-enforced object ownership;
- complete public-access blocking;
- default SSE-KMS encryption with an S3 Bucket Key;
- a TLS-only deny policy;
- a rotation-enabled customer-managed KMS key with a 30-day deletion window;
- `prevent_destroy` on the bucket and KMS key, plus `force_destroy = false`;
- five exact state keys and their S3-native `.tflock` objects; and
- five unattached, exact-key IAM managed policies.

Terraform 1.11.0 is the minimum for the state-bootstrap and future S3 backend
path because S3-native state locking is stable from that line. CI is pinned to
Terraform 1.16.3 for deterministic validation. The four unchanged roots retain
their reviewed `>= 1.8.0` local-backend declarations during v0.12.1; a
successor-compatible checkpoint must raise them before remote initialization,
separate from state migration. DynamoDB locking is neither declared nor
supported by this baseline.

## State and lock authorization

Each root receives a separate managed policy definition. The policy can list
only its state and lock keys, can read/write only its state object, and can
read/write/delete only its `.tflock` object. The state object deliberately has
no `s3:DeleteObject` permission. KMS use is restricted to calls through S3.

The policies are not attached by this increment. An attachment grants live
state authority and must identify a reviewed operator or infrastructure role.
Application delivery automation and the existing dev/test GitHub runtime roles
must not receive these policies.

Exact backend values are materialized from the bootstrap outputs into ignored
private `*.tfbackend` files. The tracked examples contain no credential,
account number, role ARN or real bucket identity. Credentials continue to use
the normal AWS credential chain and are never written into backend files.

## Why all five roots remain local

The bootstrap root cannot initialize against infrastructure that does not yet
exist, so its first apply must retain a protected local state. The other four
roots also remain local in v0.12.1. Their `backend.tf` files are intentionally unchanged.

This prevents an implementation merge, validation command, or backend
foundation apply from silently migrating state. v0.12.2 will add the S3
backend declarations and run the first guarded, non-empty brownfield migration.

## Offline review checkpoint

Run without AWS credentials, Terraform initialization or network access:

```bash
bash scripts/validate-v0.12.1-remote-state-foundation.sh
```

When Terraform is installed, the repository-wide Terraform validation remains:

```bash
bash scripts/validate-terraform.sh
```

That script initializes every root with `-backend=false`. It downloads
providers when the local plugin cache is empty, but it must not configure the
S3 backend or migrate state.

## Separately approved live creation checkpoint

Do not run this section merely because the code was merged. Live creation
requires a clean repository at the exact protected-main revision, reviewed
private inputs, a private saved plan, a bounded UTC approval, and private
evidence storage.

Prepare an ignored input file outside Git-visible evidence:

```bash
cp infra/terraform/aws/state-bootstrap/terraform.tfvars.example \
  /private/owner-readable/path/state-bootstrap.tfvars
chmod 600 /private/owner-readable/path/state-bootstrap.tfvars
```

After filling the unique bucket name and reviewed tags, the approved plan/apply
sequence is limited to the bootstrap root:

```bash
terraform -chdir=infra/terraform/aws/state-bootstrap init \
  -backend=false -input=false

terraform -chdir=infra/terraform/aws/state-bootstrap plan \
  -input=false \
  -var-file=/private/owner-readable/path/state-bootstrap.tfvars \
  -out=/private/owner-readable/path/state-bootstrap.tfplan

terraform -chdir=infra/terraform/aws/state-bootstrap apply \
  -input=false \
  /private/owner-readable/path/state-bootstrap.tfplan
```

These are live AWS operations. They are examples of the bounded procedure, not authority to execute it.
The reviewed plan must contain only the declared S3,
KMS and IAM-policy foundation. Stop if it contains a policy attachment,
backend migration, EKS resource, deletion, replacement, or unrelated change.

After an approved apply, capture redacted/private evidence for versioning,
SSE-KMS, public-access block, TLS denial, KMS rotation, five policy ARNs and the
still-local bootstrap state. Do not publish bucket names, account identity,
principal identity, state bytes, plan bytes or AWS response payloads.

## Explicit non-actions

This implementation checkpoint does not:

- access AWS or create backend resources;
- attach an IAM policy or grant live state authority;
- modify the four existing backend declarations;
- run `terraform init`, `plan`, `apply`, state pull, state push or migration;
- create, modify or destroy EKS resources;
- use Terraform CLI workspaces to represent environments; or
- accept an empty destroyed environment as migration evidence.

The next implementation checkpoint is v0.12.2: one guarded non-empty migration,
immutable local backup and digest, lineage/address/resource-ID comparison,
lock-contention proof, zero-change plan and controlled S3 object-version
recovery.
