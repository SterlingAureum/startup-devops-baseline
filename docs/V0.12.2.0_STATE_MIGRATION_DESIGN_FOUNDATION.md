# v0.12.2.0 State-Migration Design Foundation

v0.12.2.0 defines the offline safety contract for the first non-empty local-to-
S3 Terraform state migration. It does not change a backend declaration, run
Terraform or AWS, attach an IAM policy, write remote state or authorize a live
migration.

The canonical contract is
`delivery/contracts/v0.12.2.0-state-migration-design-foundation.json`.

> Successor correction: v0.12.2.0.1 supersedes only the
> `firstMigration.localStatePath` assumption. The canonical source is the
> original private plan-bundle `source/terraform.tfstate`, cross-checked against
> the byte-identical private apply-output state copy. No repository-root state
> file is selected for migration.

## First migration scope

The first migration is limited to `infra/terraform/aws/state-bootstrap` and the
exact target key `bootstrap/terraform.tfstate`. This root already requires
Terraform `>= 1.11.0, < 2.0.0`, owns the live backend foundation and has the
reviewed non-empty 13-address state recorded by v0.12.1.2.1.

The runtime-identities, dev, test and prod roots remain local. Their historical
`>= 1.8.0` declarations are still bound by the closed v0.11 teardown source
review. Each requires a separate successor-compatible Terraform-floor change
before its own future migration; a floor change and state migration may not
share one execution window.

Only the default Terraform workspace is accepted. One root is migrated per
approval and execution window. An empty or destroyed state is not accepted as
migration evidence.

## Private preflight and immutable backup

Before any backend initialization, v0.12.2.1 must bind a clean exact protected
main, expected AWS account, Terraform version, private partial backend config,
Terraform source manifest and the current local state. The private evidence
must record:

- local-state SHA-256, lineage and serial;
- the exact 13 managed addresses and a canonical resource-identity digest;
- absence of both the target state object and its `.tflock` object;
- the state bucket object-version inventory; and
- a fresh read-only validation of the S3/KMS/IAM foundation.

Before migration, copy the local state byte-for-byte into a new mode `0600`
file beneath a mode `0700` directory outside the repository. Record its digest,
lineage and serial. The backup is retained after success and is never deleted
automatically.

## Migration command boundary

The `terraform init -migrate-state` command is the documented backend-change
operation that copies existing state. `-force-copy` suppresses migration prompts and implies
`-migrate-state`; consequently it is permitted only inside the future exact,
separately approved executor. It is not a general operator convenience flag.

The backend must use the private partial S3 configuration with
`use_lockfile = true`. Credentials must come from the normal AWS credential
chain, never the backend file. The migration window cannot run Terraform
apply, destroy, import, `state push`, address refactoring, module/provider
upgrade or platform upgrade.

Official references:

- <https://developer.hashicorp.com/terraform/cli/commands/init>
- <https://developer.hashicorp.com/terraform/language/backend/s3>
- <https://developer.hashicorp.com/terraform/language/backend>

## Post-migration proof

Success requires more than a successful `terraform init` exit code. The future
executor must retain a private remote state pull and prove:

- the remote object has a version ID;
- lineage matches the immutable local backup and serial did not regress;
- managed addresses and canonical resource identities match exactly;
- a separately saved and human-reviewed plan contains zero changes;
- a second Terraform process fails to acquire the S3-native lock while the
  first process visibly owns the `.tflock` object; and
- the lock object is absent after the contention test completes.

`terraform state pull` can upgrade the state representation for the installed
Terraform version, so raw pulled bytes are not used as the sole equivalence
proof. Lineage, serial, addresses and resource identities are compared
explicitly.

## Recovery boundary

The controlled S3 object-version recovery drill is a later, separately
approved execution window. It requires reviewed version IDs, a canonical state
lock, a fresh pre-drill remote backup and post-recovery lineage/address/
identity plus zero-change-plan verification.

No automatic retry or rollback is permitted after an ambiguous migration.
Never use `terraform state push -force`; Terraform normally refuses a push
whose lineage differs or whose destination serial is newer because either
condition can indicate unrelated or more recent state.

If initialization stops after a possible remote write, preserve the local
backup, `.terraform` backend metadata, all stdout/stderr and every S3 object
version. Stop for manual review instead of re-running migration.

Official recovery references:

- <https://developer.hashicorp.com/terraform/cli/commands/state/push>
- <https://developer.hashicorp.com/terraform/language/state/backends>
- <https://developer.hashicorp.com/terraform/cli/state/recover>

## Implementation sequence

1. v0.12.2.1 adds command-free verification and a private reviewed migration
   command plan. It may read private files but performs no live mutation.
2. v0.12.2.2 adds one separately approved bootstrap migration executor. It
   cannot apply infrastructure changes or retry automatically.
3. v0.12.2.3 performs the separately bounded lock, zero-change and controlled
   object-version recovery proof and records redacted terminal evidence.

## Offline validation

```bash
bash scripts/validate-v0.12.2.0-state-migration-design-foundation.sh
```

The validator performs deterministic contract, source, documentation, privacy
and fail-closed mutation checks. It invokes no AWS or Terraform operation.
