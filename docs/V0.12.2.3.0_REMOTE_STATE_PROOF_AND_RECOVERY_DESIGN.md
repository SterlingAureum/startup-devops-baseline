# v0.12.2.3.0 Remote-State Proof and Recovery Design

## Outcome

This increment defines the remaining proof and recovery phases for the first
bootstrap state migration. It runs no AWS or Terraform command, reads no
private evidence, changes no state or lock object, and grants no live authority.

The validated remote identity is now canonical: remote state SHA-256
`7c85df95076c480eaa0a618b78ad946be64ff2288c918d529395ff4346bcd139`,
serial `1`, 13 managed addresses, nine data addresses and semantic projection
SHA-256
`46a2fda8b522437194aab7a03b41170ff6a02f1affaa067ec76ce8a0ebada48d`.
The raw lineage remains private; only its SHA-256 is public.

## Corrected identity invariant

The v0.12.2.0 design required the remote lineage to equal the immutable local
backup and the remote serial not to regress. The completed migration proved
that Terraform established a new remote identity while preserving all
addresses, resources, outputs and semantic state content.

Those two original postconditions are superseded only for this exact validated
identity rebase. The immutable backup, address inventory and semantic equality
requirements remain in force.

## Real S3-native lock contention

The lock holder is `terraform console`, which holds the state lock while the
interactive session remains open. The executor must:

1. start the console with the already configured canonical backend metadata;
2. observe the exact `.tflock` object while the console process remains alive;
3. run a second `terraform plan -lock-timeout=0s` process;
4. accept only a state-lock acquisition failure from the contender;
5. close the console cleanly; and
6. verify that the current lock object is absent afterward while retaining its
   version history privately.

The executor may neither synthesize the lock object nor use `force-unlock`.
Early holder exit, missing lock observation, contender success or a non-lock
contender failure is terminal and cannot be retried automatically.

## Zero-change saved plan

After the lock is released, the same source and remote identity are used to
create a saved plan with detailed exit codes. Exit code `0` is required. The
binary plan, JSON view, text view, source manifest, state bindings and command
logs remain private and require separate human review. No apply is permitted.

## Controlled object-version recovery

Recovery uses its own request, approval and execution window. Before mutation,
the operator reviews the current state version ID and retains a fresh private
state pull. A canonical `terraform console` session holds the real state lock
throughout the copy operations.

The drill first copies the reviewed current version onto the same versioned key
to create a byte-identical drill version. Recovery then copies the explicitly
reviewed pre-drill version onto the same key, making a new current version while
preserving every prior version. Both copies require the source version ID, ETag
precondition, expected bucket owner, exact SSE-KMS key and S3 Bucket Key.

After clean lock release, state pull/list and another zero-change plan must
pass. The drill cannot delete state versions, use `terraform state push`, use
`force-unlock`, retry automatically or claim automatic rollback.

## Implementation sequence

1. v0.12.2.3.1 implements separately approved console-held lock contention and
   produces a zero-change saved plan for human review.
2. v0.12.2.3.2 records the reviewed lock/plan evidence and prepares a separate
   exact object-version recovery request.
3. v0.12.2.3.3 executes the byte-identical, version-bound recovery drill under
   a real Terraform lock.
4. v0.12.2.3.4 records terminal redacted evidence and closes the bootstrap
   migration Runbook.
