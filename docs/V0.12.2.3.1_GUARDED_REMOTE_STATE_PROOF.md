# v0.12.2.3.1 Guarded Remote-State Proof

This increment implements the first live proof defined by v0.12.2.3.0. It does
not repeat backend initialization or migration. It reuses the reviewed private
Terraform working directory and its existing S3 backend metadata.

## Authority split

`verify` performs no AWS or Terraform command and writes no evidence. It checks
the protected-main identity, the fresh one-hour request window, the complete
identity-rebase recovery chain, the private tfvars digest, the staged source
manifest, and the existing backend metadata. Its output does not authorize the
live proof.

`execute` additionally requires:

```bash
export CONFIRM_BOOTSTRAP_REMOTE_STATE_PROOF=prove-bootstrap-lock-and-zero-change
```

All plan, apply, migration, recovery, destroy, state-push, and other live
confirmation variables must be unset.

## Exact live sequence

1. Revalidate AWS identity, the canonical remote-state bytes, all 13 managed
   addresses and 9 data addresses, SSE-KMS, Bucket Key, and the single current
   state-object version.
2. Confirm that `bootstrap/terraform.tfstate.tflock` is absent.
3. Start `terraform console` against the already configured backend and keep it
   open while S3 proves the lock object exists.
4. Run one competing `terraform plan -lock-timeout=0s`. Exit code 1 is accepted
   only when the output contains Terraform's state-lock acquisition error.
5. Exit the console cleanly and prove the lock object is absent. No direct lock
   write, delete, or `force-unlock` is allowed.
6. Run one `terraform plan -detailed-exitcode -lock-timeout=60s` with the
   original reviewed private tfvars and save the binary plan. Exit code 0 is
   mandatory.
7. Render machine- and human-readable plans and reject drift, imports, output
   changes, or any create, update, delete, or replacement action.
8. Re-pull and re-list state, prove its bytes and object history are unchanged,
   and require exactly two new lock versions plus two lock delete markers: one
   acquisition/release pair from the console and one from the final plan.

The contender's failed acquisition must not add another lock version. Any
ambiguous cleanup stops the executor, preserves all private evidence, and
forbids an automatic retry.

## Prepare a private request

Copy the example to the same owner-readable private root used for the prior
requests. Keep the request and private tfvars at mode `0600`, all private parent
directories at `0700`, use absolute paths, bind `expectedMainCommit` to the
current protected-main SHA, and create a new output path that does not yet
exist.

```bash
cp delivery/examples/v0.12.2.3.1-bootstrap-remote-state-proof-request.example.json \
  "$PRIVATE_ROOT/bootstrap-remote-state-proof-request-attempt-01.json"
chmod 600 "$PRIVATE_ROOT/bootstrap-remote-state-proof-request-attempt-01.json"
```

The request's approval interval must be active, no longer than one hour, and
have at least 15 minutes remaining at both verification and execution.

## Verify, approve, and execute

Use an absolute request path:

```bash
PROOF_REQUEST_01="$(realpath "$PRIVATE_ROOT/bootstrap-remote-state-proof-request-attempt-01.json")"

python3 scripts/execute-v0.12.2.3.1-bootstrap-remote-state-proof.py verify \
  --private-proof-request "$PROOF_REQUEST_01"
```

After separately reviewing the redacted verification result, execute from an
isolated subshell:

```bash
(
  unset CONFIRM_STATE_BOOTSTRAP_PLAN
  unset CONFIRM_STATE_BOOTSTRAP_APPLY
  unset CONFIRM_STATE_BOOTSTRAP_RECOVERY
  unset CONFIRM_STATE_BOOTSTRAP_MIGRATION_PREFLIGHT
  unset CONFIRM_STATE_BOOTSTRAP_MIGRATION
  unset CONFIRM_STATE_BOOTSTRAP_IDENTITY_REBASE_RECOVERY
  unset CONFIRM_TERRAFORM_APPLY
  unset CONFIRM_TERRAFORM_DESTROY
  unset CONFIRM_STATE_PUSH

  export CONFIRM_BOOTSTRAP_REMOTE_STATE_PROOF=prove-bootstrap-lock-and-zero-change

  python3 scripts/execute-v0.12.2.3.1-bootstrap-remote-state-proof.py execute \
    --private-proof-request "$PROOF_REQUEST_01"
)
```

The success result remains redacted. Raw state, plan contents, AWS identities,
resource identities, object version IDs, lock details, and private paths remain
only in the private proof directory. A human must review that directory before
v0.12.2.3.2 may bind the evidence and prepare a separate object-version
recovery request.
