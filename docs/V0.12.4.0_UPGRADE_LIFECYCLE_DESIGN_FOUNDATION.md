# v0.12.4.0 Upgrade Lifecycle Design Foundation

This checkpoint starts v0.12.4 by freezing an offline upgrade-control model.
It does not select a target EKS minor, inspect a live cluster, create an
environment or authorize any upgrade. The recorded component versions are
repository declarations, not a claim about current live runtime state.

## Why the design comes first

An EKS upgrade is not one Terraform version edit. It changes a compatibility
set containing the control plane, managed node groups, EKS managed add-ons,
Karpenter, cluster controllers, GitOps controllers, CRDs, workloads and client
tools. Choosing a target before the complete set is reviewed would turn a
routine upgrade into an unbounded recovery exercise.

The first executable successor must therefore bind a fresh live inventory to
an official-source compatibility matrix. The target EKS minor and all managed
add-on and platform candidates remain deliberately unselected in this
foundation.

## Frozen repository inventory

The repository currently declares EKS `1.36`, AL2023 managed nodes, Argo CD
`v3.5.2`, Karpenter `1.14.0`, AWS Load Balancer Controller chart `1.14.0`,
CloudNativePG chart `0.29.0`, cert-manager `v1.21.0`, External Secrets `2.8.0`,
Argo Rollouts chart `2.41.1`, kube-prometheus-stack `88.5.0` and Barman Cloud
plugin `0.7.0`. EKS manages VPC CNI, kube-proxy, CoreDNS and EBS CSI, but their
versions are not pinned in Terraform and must be observed and selected
explicitly before an upgrade plan can be approved.

This is an inventory starting point, not a compatibility conclusion. v0.12.4.1
must check supported versions and upgrade constraints against current official
vendor documentation rather than inferring compatibility from repository
syntax or historical runtime evidence.

## Ordered lifecycle

The lifecycle is fail closed and advances through these boundaries:

1. Freeze the live current-version and resource inventory.
2. Review an official-source compatibility matrix for exactly one next EKS
   minor.
3. Scan repository, rendered Helm output and live API usage for APIs removed in
   the target minor.
4. Prove remote-state, backup and clean-room rebuild readiness.
5. Upgrade the EKS control plane by one minor.
6. Converge managed node groups.
7. Converge EKS managed add-ons.
8. Converge Karpenter and cluster controllers, then platform controllers.
9. Qualify data-plane behavior, services, GitOps, observability and release
   controls.
10. Record an explicit forward-fix, GitOps rollback or clean-room rebuild
    decision.

Every live phase requires a fresh request, exact protected-main binding,
separate human approval and private evidence. v0.12.4 proceeds through aws-dev
before aws-test and permits at most one disposable EKS environment at a time.
It does not perform a live aws-prod upgrade.

## Deprecated API gate

Static source search alone is insufficient. The preflight must inspect rendered
Helm manifests and live API usage, then compare the complete result with APIs
removed by the selected target minor. An unknown or unresolved API blocks the
upgrade. The scan must cover CRDs and webhook/controller compatibility as well
as ordinary workload manifests.

## Recovery boundary

Downgrading an EKS control plane is not the primary recovery path. Before a
control-plane change, incompatible components block execution. After the
control plane changes, recovery prefers a bounded forward fix; a GitOps
rollback is allowed only when the earlier declaration is compatible with the
new Kubernetes API. If identity, state or convergence cannot be trusted, the
operator stops and chooses a reviewed clean-room rebuild.

A PostgreSQL major upgrade never shares the EKS upgrade window. Remote-state
restore, state push, automatic rollback and automatic retry remain forbidden.

## Successor sequence

- v0.12.4.1: exact live/repository inventory and official-source candidate
  compatibility matrix;
- v0.12.4.2: deprecated-API and rendered-manifest preflight;
- later v0.12.4 increments: separately approved aws-dev plan/execution and
  qualification, followed by aws-test evidence and technical closure.

Clean-room infrastructure/GitOps rebuild and measured database RTO/RPO remain
v0.12.5. Repository-wide human review, physical restructuring and the final
integrated dev/test/prod commercial rehearsal remain v1.0 work.
