# v0.12.4.1.4 External Secrets 2.9.0 First-Hop Plan

## Outcome

This increment converts the verified `2.8.0 -> 2.9.0` artifact diff into a
bounded aws-dev qualification plan. It changes no chart pin and performs no
AWS, Kubernetes, Argo CD or GitHub operation.

The critical sequencing decision is that changing
`spec.source.targetRevision` is itself a live operation while automated Argo
CD synchronization is enabled. A future pin PR therefore cannot be treated as
an ordinary offline configuration update. Live preflight and server-side
dry-run must finish under one approval; pin merge and automatic sync require a
second approval; post-sync qualification is a separately bound read-only
stage. Rollback is never automatic.

## Official release review

The target identities remain chart `2.9.0` at release commit
`cc5bfbc2234ace9cb0caff4ea89c435cf517b27b` and application `v2.9.0` at
`378bdb622ed9712ef4a58370f6a17af033b7d343`. The chart and deterministic render
SHA-256 values are inherited exactly from v0.12.4.1.3.

The relevant release changes are:

- v1 ExternalSecret optional strategy defaults are no longer injected. The
  repository already pins `conversionStrategy: Default`,
  `decodingStrategy: None` and `metadataPolicy: None`, and does not use
  `templateFrom`, so the stored-object and Argo-diff risk is explicitly
  avoided.
- Secret-target `templateFrom` values are restricted to Data, Annotations or
  Labels and checked by both admission and controller logic. The repository
  has no `templateFrom` entries.
- controller-runtime and dependency updates still require live watch/cache and
  reconciliation proof. Static render compatibility cannot close that risk.
- optional scheduler/runtime-class support is not enabled. AWS replica-delete
  fixes are outside the active read-only Secrets Manager path because
  PushSecret, deletion and replication are excluded.

No upstream manual migration is announced, but absence of a migration notice
is not permission to skip the live gate.

## Approval stages

### 1. Live preflight and server-side dry-run

The future executor must bind a fresh protected-main commit, private request
digest, AWS account, `us-east-1`, cluster
`startup-devops-baseline-dev`, Kubernetes `1.36`, the verified chart archive
and the exact `2.9.0` private render. It may perform read-only observation and
one full-render server-side dry-run with name-only output. It may not persist
any object or Secret change.

`kubectl diff` is deliberately excluded because diff output can disclose
Secret material. The only accepted dry-run form includes all of
`--server-side`, `--dry-run=server`, a dedicated field manager and `-o name`.
Afterward the executor must prove that Argo Applications, ExternalSecret,
target Secret metadata and relevant resource versions did not change.

### 2. Reviewed pin merge and automatic Argo sync

Only after a successful, human-reviewed preflight may another checkpoint
prepare the one-field `2.8.0 -> 2.9.0` GitOps mutation. Merge requires its own
live approval because Argo CD will automatically reconcile it. Direct Helm
upgrade, direct non-dry-run kubectl apply and manual Argo sync are forbidden.
No `2.10.0` preparation or automatic progression is allowed in the same PR or
window.

### 3. Post-sync read-only qualification

Qualification must prove:

- both Argo Applications are Synced and Healthy and have no active operation;
- all three ESO Deployments are Available on the exact v2.9.0 image;
- main-controller IRSA, namespace-scoped RBAC, webhook and object inventory
  remain unchanged;
- the forbidden cluster-scoped and PushSecret resource families remain absent;
- ExternalSecret and SecretStore v1 remain served/storage and both objects are
  Ready;
- the existing AWSCURRENT reference remains exact and ExternalSecret
  `refreshTime` advances after sync.

Neither AWS secret values nor Kubernetes Secret data may be read. A successful
Ready reconciliation of the exact AWSCURRENT reference is the bounded proof;
no force-sync annotation, rotation or secret digest is authorized.

## Failure and recovery

Any ambiguous dry-run, sync, rollout, CRD, RBAC or reconciliation result stops
the hop and preserves private evidence. There is no automatic retry or
rollback. A rollback requires a new approval and a reviewed Git revert to the
last qualified `2.8.0` pin. It must not directly downgrade/delete CRDs or
modify the target Secret. `2.9.0` must converge and receive terminal evidence
before `2.10.0` planning starts.

The next checkpoint is
`v0.12.4.1.5-external-secrets-2.9.0-live-preflight-contract`.
