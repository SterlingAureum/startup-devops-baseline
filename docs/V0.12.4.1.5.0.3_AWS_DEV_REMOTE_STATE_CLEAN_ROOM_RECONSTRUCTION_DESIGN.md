# v0.12.4.1.5.0.3 AWS dev remote-state clean-room reconstruction design

## Outcome

The first External Secrets `2.9.0` live preflight stopped at the EKS read with
`ResourceNotFoundException`. AWS identity succeeded, but no Kubernetes command
or server-side dry-run started and no persistent mutation occurred. This is not
an External Secrets compatibility failure: the disposable `aws-dev` baseline
does not currently exist.

The next operational track therefore rebuilds `aws-dev` before retrying the
upgrade preflight. This checkpoint is design-only. It runs no AWS, Terraform,
Kubernetes, Argo CD or Helm command and grants no live authority.

## Why the historical create entrypoint is not reusable

The current development root still declares the local backend. The historical
`scripts/apply-aws-dev.sh` path predates the completed state-backend foundation
and can therefore create a new local state that is outside the current S3/KMS
and native lockfile control plane. Reusing it would make a successful rehearsal
harder to recover, review and tear down safely.

The clean-room rebuild must instead start with the exact remote key
`environments/dev/terraform.tfstate`. Because the key must be absent and there
must be no local state to preserve, initialization uses `-reconfigure`, not
`-migrate-state`. The latter is reserved for moving an existing state and is
explicitly outside this reconstruction.

## State and source boundary

- Add a partial `backend "s3" {}` declaration to the dev root in a later
  implementation checkpoint.
- Generate the backend configuration privately from the already established
  `backend_configuration.dev` bootstrap output. It remains outside Git at mode
  `0600` and contains exactly bucket, key, region, encryption, KMS key, native
  lockfile and allowed-account fields.
- Before init, prove that both the remote state object and its `.tflock` object
  are absent and that local state is absent or empty.
- Stage a private copy of the complete `infra/terraform/aws` tree, not only the
  environment directory, so relative module paths remain exact. Bind it with a
  source manifest before any plan.
- Read-only validate the existing state-bootstrap S3/KMS/IAM foundation. The
  rebuild must not mutate or migrate the bootstrap state.

## Reviewed live sequence

1. Record the redacted missing-environment evidence already observed.
2. Implement the partial dev S3 backend and the private request contract.
3. Run a separately approved, read-only clean-room absence preflight.
4. Initialize the staged source with `-reconfigure` and produce one saved create
   plan under a separate approval.
5. Review the private plan for exact creates, cost and unexpected changes.
6. Apply that exact saved plan once under a new approval.
7. Validate EKS readiness and build a private kubeconfig.
8. Bootstrap Argo CD, then converge the root applications with External Secrets
   still pinned to `2.8.0`, each under separate approval.
9. Retry the existing v0.12.4.1.5 server-side live preflight. Only after it
   passes may a later checkpoint review and merge the `2.9.0` GitOps pin.
10. Qualify post-sync health, then separately review and execute teardown and a
    residual resource/cost audit.

Every stage receives a new time window and binds its own private request and
protected-main commit. No failure is automatically retried or rolled back.

## Cost and lifecycle boundary

At most one EKS rehearsal environment may exist. The reviewed session is capped
at eight hours and the private estimate at USD 50. Teardown is mandatory for
the rehearsal but never automatic: it needs its own reviewed plan, approval and
post-teardown residual/cost evidence.

## Roadmap adjustment

Only the minimum remote-state `aws-dev` clean-room rebuild prerequisite moves
forward from v0.12.5. Database recovery, measured RTO/RPO and the broader
disaster-recovery rehearsal remain v0.12.5 work. This avoids turning the
External Secrets repair into an unbounded recovery-program rewrite.

## Next checkpoint

`v0.12.4.1.5.0.4-guarded-aws-dev-remote-state-clean-room-preflight` will add the
partial backend declaration plus command-free request verification. Its live
mode may perform only separately approved read-only AWS/S3/KMS/IAM absence and
foundation checks. It will not initialize Terraform, produce a plan, apply,
create the cluster or retry the External Secrets preflight.
