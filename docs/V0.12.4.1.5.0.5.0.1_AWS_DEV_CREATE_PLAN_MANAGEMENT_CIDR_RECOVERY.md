# v0.12.4.1.5.0.5.0.1 AWS dev create-plan management CIDR recovery

## Purpose

The first `v0.12.4.1.5.0.5` create-plan attempt initialized the reviewed S3
backend and selected the providers, but Terraform stopped at the EKS module
precondition because a public EKS endpoint had no restricted access CIDR. No
apply ran and no environment was created.

This checkpoint preserves that attempt as immutable incident evidence and
permits one separately approved saved-plan recovery using one privately supplied,
globally routable IPv4 `/32`. It is not an automatic retry.

## Exact incident boundary

The executor binds the incident main commit, private request, failed plan output,
provider lockfile and all supplied artifact digests. The failed binary plan is
explicitly ineligible for apply. Its stderr must still show the exact EKS
restricted-CIDR precondition failure, and the original pre-plan S3 history must
still show no state or lock object.

The failed source and output directories remain read-only evidence. The recovery
uses new `attempt-02` source and output directories; it never deletes, edits or
reuses the failed plan.

## Private management CIDR

`privateManagementCidr` must be one canonical, globally routable IPv4 `/32`.
Private, loopback, reserved, non-IPv4, broader prefixes and `0.0.0.0/0` fail
closed. The CIDR stays only in the mode-`0600` private request and the Terraform
process argument. Redacted verification and result JSON never emit the CIDR or
its digest.

If the operator's public address changes, create a new private request and a new
approval window. Do not edit an already verified request.

## Command-free verification

`verify` checks the protected-main identity, clean worktree, exact incident
evidence, exact predecessor chain, current Terraform source, private file modes,
private CIDR and new output locations. It runs no AWS or Terraform command and
grants no execution authority.

## Separately approved execution

After explicit approval, `execute` may:

1. read AWS caller identity and confirm the EKS cluster is still absent;
2. verify through S3 read-only history that the failed plan wrote no state and
   left exactly one clean native lockfile lifecycle;
3. copy the reviewed Terraform source into a new private directory;
4. copy the exact provider lockfile from attempt 01;
5. run `terraform init -reconfigure -lockfile=readonly` against a private backend
   copy;
6. run one saved create plan with the private
   `eks_public_access_cidrs=["PRIVATE_IPV4/32"]` override;
7. produce machine-readable, human-readable and address-inventory evidence; and
8. verify that state history remains empty and exactly one additional native
   lockfile lifecycle was cleanly released.

The execution window is up to two hours. The saved-plan review window is up to
eight hours. A future exact-plan apply receives a separate approval window of up
to three hours.

## Explicitly forbidden

This checkpoint does not authorize Terraform apply, destroy, state migration,
state push, force-unlock, direct S3 mutation, IAM attachment, Kubernetes access,
secret-value reads, automatic retry or automatic rollback. It never uses the
failed binary plan as an apply input.

Any mismatch stops and preserves both attempts. Human review of the new private
binary, JSON, text and exact address inventory remains mandatory before
`v0.12.4.1.5.0.6` can be designed or executed.
