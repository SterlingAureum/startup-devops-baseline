# v0.12.4.1.5.0.6.0.1 AWS dev post-apply read-only recovery

The exact saved-plan apply completed successfully with `90 added, 0 changed,
0 destroyed`. The original executor then stopped before state-show, EKS and S3
post-apply validation because it treated the six data addresses in
`resource_changes` as the complete final data inventory.

## Root cause and exact inventory

The reviewed plan contains 90 managed create addresses and six data read/no-op
addresses. Its refreshed `prior_state` contains seven additional data-source
addresses. Those seven addresses have SHA-256
`3d28dc57ff69f6763bd6aafe3ef78930ee177cc3d1dddc59f49d58f6a4336cb6` and
exactly equal the seven addresses that were additional in final state.

The final state is therefore the exact union of 90 reviewed managed addresses,
six reviewed data addresses and seven prior-state data addresses: 103 total,
with inventory SHA-256
`0bf45e067a30633472416fcef468381e11c90d13cfabe96eeb50f6bc2e602691`.
There are zero unexplained addresses and no missing reviewed address.

## Recovery boundary

`verify` is command-free. It binds protected main, the original private apply
request, the successful apply stdout and empty stderr, preserved state SHA,
lineage and serial, the three exact address sets, and the pre-apply S3 history.

After separate approval, `execute` may only read AWS identity, EKS status, S3
object history, Terraform version and Terraform state. It requires the live
state to remain byte-identical to the preserved post-apply state, all three
state views to contain the exact 103-address union, EKS to be `ACTIVE`, the
canonical state object to be current and the native lock to have completed one
clean version/delete-marker cycle.

This recovery never executes Terraform init, plan, apply or destroy. It never
pushes or migrates state, mutates S3 directly, force-unlocks, attaches IAM
policies, runs Kubernetes commands, reads secret values, retries, rolls back or
destroys. Any mismatch stops immediately and preserves all private evidence.
