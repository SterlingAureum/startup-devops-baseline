# v0.12.4.1.5.0.7.1.6.1 shared dev/test two-wave teardown core

## Delivered capability

This checkpoint implements the command-free decision core required by the
generalized teardown design. It does not implement an operational executor.
The core accepts in-memory JSON-like evidence and either returns a normalized
decision or fails closed.

The same core supports `aws-dev` and `aws-test`. It rejects `aws-prod` as a live
teardown profile. Environment policy supplies the exact remote-state key and
records that aws-test still requires a separate remote-state activation before
its next live create.

## State and plan gates

The core partitions managed Terraform addresses using the reviewed module
boundary:

- `module.vpc.*` is the retained network shell;
- every other managed address belongs to the first, non-network wave.

Wave one is accepted only when the saved plan deletes every non-network
address, deletes no network address, contains no drift or import, and contains
only delete actions for managed resources. After applying that future plan,
the new state must equal exactly the network subset of the prior state.

Wave two is accepted only after EKS is absent, controller-owned and unknown
dependency counts are zero, protected backend resources remain preserved, and
no safe residue remains. Its fresh saved plan must delete every remaining
network address and nothing else. The final managed state must be empty.

## Dependency classification

The post-cluster inventory must cover all twelve design families. A safe
residue record exposes only its category and SHA-256 identity binding. The
inventory may recognize the following categories:

- detached dynamic-PVC volume;
- orphan Kubernetes ENI;
- orphan EKS cluster security group.

Recognition does not grant deletion authority. Any safe residue requires a
separate future cleanup approval followed by a fresh absence inventory. An
unknown dependency or controller-owned remainder always stops wave two.

## Backend history

Plan operations must leave the canonical state version count unchanged and
complete one clean lock cycle. Apply operations must add exactly one canonical
state version and one clean lock cycle. Neither operation may add a state
delete marker. A clean S3-native lock ends with zero latest lock versions and
one latest delete marker.

These checks preserve the state backend; they never delete state, history,
lock history, KMS resources or runtime identities.

## CI and authority

Unlike historical private execution evidence, this module is active
operational source code. Its offline checker and tests are therefore included
in repository structure validation. No private evidence is loaded.

The core imports no subprocess or shell facility, exposes no executor, and
runs no AWS, Terraform or Kubernetes command. This checkpoint grants no live
read, plan, apply, residue-delete, destroy or backend-retirement authority.
