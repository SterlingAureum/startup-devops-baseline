# v0.12.4.1.5.0.7.1.6.4 shared dev/test teardown receipt approval

## Delivered capability

This checkpoint makes the redacted private-preflight receipt reviewable across
process restarts and adds the separate phase-approval record required before a
future executor can be designed. Both operations are local-only. No AWS,
Terraform, Kubernetes, S3 or state command is present.

## Append-only private store

The operator prepares one owned `0700` store containing exactly owned `0700`
`receipts` and `approvals` directories. Receipt and approval records are
canonical `0600` JSON files.

A receipt filename is its receipt SHA-256. An approval filename is the SHA-256
of the receipt it consumes. Both files use no-follow, exclusive creation,
file `fsync` and directory `fsync`; an existing name is never overwritten.
The last newline is written as the commit byte. A partial file after an I/O
failure is preserved for review and blocks automatic retry or repair.

Receipt persistence revalidates the full redacted preflight result, its caller-
supplied result digest, its content-addressed receipt digest and its active UTC
window. Persistence never creates approval.

## Separate phase approval

An approval request must bind the persisted receipt's exact environment, state
key, phase, attempt, protected-main commit and requested authority. It contains
a canonical human approval statement whose SHA-256 is independently checked.
The approval must be explicit, limited to one attempt, at most fifteen minutes,
and cannot outlive the preflight receipt.

Writing `<receipt-sha>.approval.json` consumes that receipt at the approval
layer. Exclusive creation means the same receipt cannot produce a second
approval, even if the bytes are identical. The approval record remains
unconsumed by any executor; this checkpoint implements no executor and performs
no phase action.

## Safety and CI boundary

The local CLI can only persist a reviewed receipt or record its separately
reviewed phase approval. It reads one host UTC value, strict private local input
and the strict local store. Output is redacted and no private path or resource
identity is emitted.

Active-source offline checks join structure validation. Historical private
execution evidence remains outside required CI. Approval recording does not
mean execution occurred: every result retains `liveCommandExecuted: false` and
`executionPerformed: false`. Automatic retry, rollback, state push and backend
retirement remain forbidden.
