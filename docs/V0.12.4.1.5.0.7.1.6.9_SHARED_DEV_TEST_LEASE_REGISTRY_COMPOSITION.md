# v0.12.4.1.5.0.7.1.6.9 shared dev/test lease registry composition

## Delivered capability

This checkpoint composes the closed registry runner inside the existing
append-only single-use lease lifecycle. The composition validates the active
approval, execution request, exact phase-driver digest, completion window,
complete private SHA-256 binding set and fixed-fake backend before consuming
the approval.

The lease store then creates the claim exclusively and completes both file and
directory `fsync` before the first registry backend call. The runner derives
its phase manifest and ordered operation requests internally; callers cannot
substitute either value at this entry function.

## Terminal states and replay

Successful dispatch writes one append-only outcome. A failed operation or a
malformed response also writes a terminal failure outcome before returning a
redacted stop. Claim-write uncertainty, outcome-write uncertainty, success and
failure all leave the approval permanently consumed. Re-entering with a new
backend stops on the existing claim before any backend call.

The lower-level `.6.8` function remains an offline unit boundary, but it is not
an operational entrypoint. Future command integration must call this
lease-owned function so durable claim creation cannot be bypassed.

## Implementation boundary

The only accepted backend is the exact fixed fake. The composition writes only
to the already reviewed local private claim/outcome store. It has no standalone
CLI, subprocess, SDK, credential or endpoint reader, raw command, live backend
or infrastructure authority. It cannot run AWS, Terraform, Kubernetes, S3 or
state operations and performs no automatic retry, repair or rollback.

The next checkpoint may add a strict local command boundary around this exact
composition. That command must retain the private-file protections, fixed fake,
single durable attempt and production refusal.
