# v0.7 Final Validation

## Objective

Prove both directions of the v0.7 delivery loop:

```text
validated source -> immutable image -> Promotion PR -> Argo CD -> live identity
historical state -> Rollback PR -> Argo CD -> restored live identity
```

The feature branch can validate workflow mechanics. The complete live exercise
must run on the branch tracked by the aws-dev Argo CD Application, normally
`main`.

## Phase 1: Validate the Increment on the Feature Branch

Apply the v0.7.4 increment to:

```text
feature/v0.7-cicd-gitops-promotion
```

Push it and wait for **quality-gates** to pass.

Before testing rollback, the branch needs at least two metadata-aware
values-only releases. If the v0.7.3 Promotion PR is still open, merge it first.
Then manually run **demo-api image publish** from the feature branch with:

```text
create_promotion_pr = true
promotion_base_branch = feature/v0.7-cicd-gitops-promotion
```

Review and merge that Promotion PR. Find the previous eligible release:

```bash
git switch feature/v0.7-cicd-gitops-promotion
git pull --ff-only
git log --first-parent --oneline -- \
  apps/demo-api/helm/values-aws-dev.yaml
```

Manually run **demo-api GitOps rollback** from the feature branch:

```text
rollback_to_revision = <full older metadata-aware values-only commit>
rollback_base_branch = feature/v0.7-cicd-gitops-promotion
```

Confirm the PR changes only `values-aws-dev.yaml`, then merge it. This proves
the Git workflow, but it does not prove live EKS rollback while Argo CD tracks
`main`.

## Phase 2: Forward Promotion on Main

Merge the completed feature branch into `main` while preserving its history.
Wait for main-branch quality gates and image publishing to pass. If the image
workflow does not start because the merge contains no configured image-build
path, manually dispatch **demo-api image publish** from `main` with:

```text
create_promotion_pr = true
promotion_base_branch = main
```

Review and merge the new main-targeted Promotion PR.

After Argo CD is `Synced` and `Healthy`, identify its exact revision:

```bash
kubectl get application demo-api-aws-dev \
  --namespace argocd \
  --output jsonpath='{.status.sync.revision}{"\n"}'
```

Update the local checkout and run the forward trace:

```bash
git switch main
git pull --ff-only

DESIRED_REVISION=<exact-argo-cd-revision> \
./scripts/validate-demo-api-delivery-trace.sh
```

Expected final line:

```text
demo-api delivery traceability validation passed.
```

## Phase 3: Historical Rollback on Main

Choose an older metadata-aware values-only desired-state commit from `main`
and run **demo-api GitOps rollback**:

```text
rollback_to_revision = <full historical desired-state commit>
rollback_base_branch = main
```

Review and merge the Rollback PR. Wait for Argo CD to become `Synced` and
`Healthy` again, then read its new exact revision and rerun:

```bash
git switch main
git pull --ff-only

DESIRED_REVISION=<exact rollback revision reported by Argo CD> \
./scripts/validate-demo-api-delivery-trace.sh
```

The output must show the historical source commit, SHA tag, immutable digest,
workflow run ID, desired-state commit, Argo CD revision, Pod image, and
application version. The desired-state and Argo CD revisions must match; the
image and version fields must match the historical target.

## Phase 4: Finalize

After both main-branch traces pass:

```bash
git tag -a v0.7.4-cicd-gitops-promotion \
  -m "v0.7.4 CI/CD and GitOps promotion baseline"
git push origin v0.7.4-cicd-gitops-promotion
```

Do not create the final tag before the live rollback trace passes.
