# v0.6.3 PostgreSQL S3 Backup and WAL Archiving

## Outcome

v0.6.3 adds continuous PostgreSQL WAL archiving and physical base backups
without changing the existing three-instance, two-AZ database topology.

## Component Contract

| Concern | Value |
|---|---|
| CloudNativePG | 1.30.0 |
| Barman Cloud plugin | 0.13.0 |
| Barman Helm chart | 0.7.0 |
| cert-manager | v1.21.0 |
| Object store | Amazon S3 |
| Authentication | IRSA; no static access keys |
| Bucket encryption | SSE-S3 (`AES256`) |
| Bucket versioning | enabled |
| Public access | blocked |
| Transport | TLS required by bucket policy |
| S3 prefix | `postgresql-baseline/` |
| WAL compression | lz4 |
| Base-backup compression | lz4 |
| Backup target | prefer standby |
| Schedule | daily at 02:00:00 UTC |
| Recovery window | 7 days |

The Terraform module creates the bucket and an IAM role trusted only by the
`data-platform/postgresql-baseline` ServiceAccount. Its object permissions are
limited to the database prefix. Delete permissions are included because the
Barman retention process must remove obsolete backups.

## GitOps and Environment Values

The ObjectStore manifest retains the marker
`s3://__CNPG_BACKUP_BUCKET__/postgresql-baseline`. The PostgreSQL Argo CD
Application ignores only its live `destinationPath`, with
`RespectIgnoreDifferences=true`.

After Terraform apply, `prepare-cloudnative-pg-backup.sh` annotates the
existing database ServiceAccount before the Git commit is pushed. This avoids a
race in which Argo CD could roll plugin sidecars before EKS has injected their
IRSA environment and token volume.

After the push, `deploy-aws-dev-root-app.sh`:

1. rechecks the backup bucket and role outputs;
2. idempotently re-annotates the PostgreSQL ServiceAccount;
3. applies the root Application;
4. waits for the ObjectStore and its Argo CD ignore contract;
5. patches the live destination to the Terraform-created bucket.

No AWS account ID, bucket name, role ARN, or credential is committed to Git.

## Runtime Validation

Create one physical base backup:

```bash
./scripts/run-cloudnative-pg-backup-test.sh
```

The test waits for continuous archiving, forces a WAL switch, creates a
plugin-based `Backup`, waits for completion, forces another WAL switch, and
confirms that S3 contains both base-backup and WAL objects.

Then run:

```bash
./scripts/validate-cloudnative-pg-backup.sh
./scripts/validate-all.sh
```

The validator checks the S3 security contract, IAM trust, ServiceAccount
annotation, Argo CD Applications, cert-manager, Barman deployment and CRD,
ObjectStore, ScheduledBackup, cluster plugin configuration, continuous
archiving, a completed base backup, and S3 object evidence.

## Safety and Destruction

The standalone cleanup script deletes Kubernetes database resources and EBS
volumes but leaves the Terraform S3 bucket intact.

The full destroy script requires `destroy-with-backups`. Because the aws-dev
bucket uses `force_destroy=true`, Terraform permanently deletes all current and
noncurrent backup objects. This is a development lifecycle choice, not a
production recommendation.
