# v0.6.5 PostgreSQL Application Integration and Failover

## Scope

v0.6.5 completes the CloudNativePG data-platform milestone by joining the
application and database validation paths:

```text
demo-api
  -> startup-apps/demo-api-postgresql
  -> postgresql-baseline-rw.data-platform.svc
  -> current PostgreSQL primary
```

The local kind environment keeps database integration disabled. The aws-dev
environment enables it.

## Application Identity

CloudNativePG generates `data-platform/postgresql-baseline-app` for the `app`
database owner. The application does not use the `postgres` superuser.

Kubernetes does not allow a Pod to reference a Secret in another namespace.
`scripts/sync-demo-api-postgresql-secret.sh` therefore copies only
`fqdn-uri`, without decoding or printing it, into:

```text
Secret: startup-apps/demo-api-postgresql
Key:    DATABASE_URL
```

This Secret is runtime state, not GitOps content. Re-run the synchronization
script after rotating the source credential. External Secrets and AWS Secrets
Manager remain part of v0.7.

## Application Behavior

- `/health` reports only application-process health.
- `/ready` includes PostgreSQL when database integration is enabled.
- `/db/health` returns sanitized database, user, server address, port, and
  recovery state.
- The application uses bounded connection attempts and short-lived
  connections, so it does not retain a stale connection across failover.
- Marker writes are available only through `python -m src.database` inside the
  application container. No public database write endpoint is added.

## Non-Disruptive Validation

```bash
./scripts/sync-demo-api-postgresql-secret.sh
./scripts/validate-demo-api-postgresql.sh
./scripts/validate-all.sh
```

The validator compares the source and target Secret values without displaying
them, confirms the target has exactly one data key, verifies the Deployment
reference, checks the RW Service endpoint, and proves that both demo-api Pods
connect to the current primary.

## Guarded Primary Failover

```bash
./scripts/run-cloudnative-pg-failover-test.sh
```

Type:

```text
failover-primary
```

The drill:

1. Runs the PostgreSQL and application preflight validators.
2. Records the primary Pod, UID, IP, PVC, PV, and EBS volume.
3. Writes and reads a committed marker through demo-api.
4. Deletes the current primary Pod.
5. Waits for a different replica to become primary.
6. Verifies the RW Service points only to the new primary.
7. Waits for demo-api to reconnect to that primary.
8. Reads the pre-failover marker and performs a new post-failover write.
9. Waits for the former primary to return as a replica.
10. Proves that the former primary reused its original PVC, PV, and EBS volume.
11. Re-runs persistence, backup, and application validation.

The script reports observed database promotion and application recovery times,
but v0.6.5 does not define a production SLO.

Expected final output:

```text
CloudNativePG primary failover and demo-api reconnect validation passed.
```

## Boundary

This is a Pod-level primary failure exercise. It does not terminate an EC2
instance, interrupt a database node, simulate an Availability Zone outage, or
test regional disaster recovery.

CloudNativePG documents that primary failure promotes the most up-to-date
standby, moves the `-rw` Service, and re-synchronizes the former primary with
`pg_rewind` when its PVC is available:

- <https://cloudnative-pg.io/docs/1.30/failure_modes/>
- <https://cloudnative-pg.github.io/docs/1.30/applications/>
