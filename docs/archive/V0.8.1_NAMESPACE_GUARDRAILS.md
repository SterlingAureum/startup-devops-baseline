# v0.8.1 Namespace Guardrails

## Status

Checkpoint 1 passed AWS runtime validation. Checkpoint 2 implements the CEL
admission-policy controls; its AWS runtime validation is pending. The v0.8.1
tag must not be created yet.

## Scope

This checkpoint introduces namespace-level guardrails with Kubernetes-native
controls:

- explicit GitOps ownership of the `startup-apps` Namespace;
- Pod Security Admission in `restricted` enforce, warn, and audit modes for
  `startup-apps`;
- staged Pod Security Admission for `data-platform`, using `baseline` enforce
  with `restricted` warnings and audit records;
- ResourceQuota and LimitRange controls for both business namespaces;
- positive admission testing for a restricted-compliant Pod;
- negative admission testing for privileged Pods;
- workload health checks for demo-api and CloudNativePG after enforcement.

The Pod Security Standards are pinned to `v1.30`, the oldest Kubernetes version
in the local and aws-dev environment matrix. This makes enforcement consistent
between kind and EKS. The policy version must be upgraded deliberately when the
oldest supported cluster version changes.

## Ownership model

The `startup-apps` guardrails are managed by a dedicated Argo CD Application
that syncs before demo-api.

The `data-platform` namespace, quota, and limit range remain owned by the
existing `postgresql-baseline` Application. This avoids overlapping Argo CD
ownership of the same Namespace.

During v0.8 development, the aws-dev demo-api and PostgreSQL Applications use
`feature/v0.8-production-security-baseline` so runtime validation exercises the
current security increment. They must return to `main` during final branch
alignment.

Run repository-level contract checks:

```bash

./scripts/validate-ci-quality-gates.sh
```

After pushing the checkpoint and refreshing the aws-dev root Application, run:

```bash
TARGET_REVISION=feature/v0.8-production-security-baseline \
  ./scripts/deploy-aws-dev-root-app.sh

./scripts/validate-namespace-guardrails-aws.sh
```

The AWS validation must confirm:

- all three Argo CD Applications are Synced and Healthy;
- the expected PSA labels exist on both namespaces;
- ResourceQuota and LimitRange resources are active;
- demo-api and the PostgreSQL cluster remain healthy;
- a restricted-compliant Pod passes server-side dry-run;
- privileged Pods are rejected in both protected namespaces.

## Checkpoint 2: application admission policies

Checkpoint 2 adds Kubernetes-native ValidatingAdmissionPolicy and CEL controls:

- fail-closed policies for Pods and common workload-controller Pod templates;
- immutable `sha256` digest requirements for containers and init containers;
- explicit CPU and memory requests and limits for every container;
- `Deny` and `Audit` enforcement through application-tier bindings;
- positive server-side dry-runs for compliant Pods and Deployments;
- negative tests for mutable tags, `latest`, missing requests, and missing
  limits.

The bindings select only namespaces labeled
`platform.startup.dev/tier=application`. They do not apply the generic
application policy to `data-platform`, where CloudNativePG owns generated Pod
details and requires a separate operator-aware policy design.

The strict image policy is enabled in aws-dev but not in the local kind
environment. The local workflow intentionally loads tag-addressed images
directly into kind, while aws-dev consumes registry images by immutable digest.
The policy resources remain portable Kubernetes manifests and can be enabled
locally after the local image workflow becomes digest-addressable.

Run the repository-level checks:

```bash
./scripts/validate-application-admission-policies.sh
./scripts/validate-ci-quality-gates.sh
```

After pushing and refreshing the aws-dev root Application, run:

```bash
TARGET_REVISION=feature/v0.8-production-security-baseline \
  ./scripts/deploy-aws-dev-root-app.sh

./scripts/validate-application-admission-policies-aws.sh
```

The final runtime check must prove that:

- CEL type checking completed without expression warnings;
- the existing digest-pinned demo-api remains healthy;
- compliant Pod and Deployment requests are admitted;
- mutable and `latest` image references are denied;
- missing CPU or memory requests and limits are denied;
- `data-platform` remains outside this application-policy binding.
