# v0.8.2 NetworkPolicy Enforcement

## Status

Completed. Checkpoints 1, 2, and 3 were statically and runtime validated in
aws-dev. Backup, primary failover, latest-state recovery, PITR, data integrity,
and recovery-resource cleanup were revalidated while default-deny enforcement
remained active.

## Goal

Enable and prove standard Kubernetes `NetworkPolicy` enforcement through the
Amazon VPC CNI before introducing policies for application or data-platform
namespaces.

## Observed baseline

The initial aws-dev inspection reported:

- Amazon VPC CNI `v1.22.3-eksbuild.1`;
- null managed add-on configuration values;
- both `aws-node` and `aws-eks-nodeagent` containers;
- the standard `NetworkPolicy` API and AWS `PolicyEndpoint` CRD.

The node agent and CRD can be installed while the agent runs with
`--enable-network-policy=false`. Their presence does not prove that policy
enforcement is active. The managed add-on must explicitly set
`enableNetworkPolicy` to `true`, and the behavior must be verified with real
traffic.

## Checkpoint 1 design

Terraform enables network policy on the existing
`aws_eks_addon.network["vpc-cni"]` resource. Keeping the resource address
unchanged avoids an unnecessary managed add-on replacement.

The node agent remains in standard mode. A new Pod initially has default-allow
networking while the applicable policy is programmed. Strict startup
enforcement is deferred until all platform and business traffic dependencies
have explicit policies.

The runtime validation uses a temporary, dedicated namespace and two
Deployment-managed endpoints. This follows the Amazon VPC CNI operating model
and avoids relying on standalone Pods for the enforcement decision.

The test proves the following transition:

1. the client can reach the server before a policy selects it;
2. an ingress default-deny policy blocks the same request;
3. a narrow client-to-server TCP/8080 allow policy restores connectivity.

The script also requires:

- the VPC CNI add-on to be `ACTIVE`;
- `configurationValues.enableNetworkPolicy` to be `true`;
- the `aws-node` DaemonSet rollout to complete;
- `aws-eks-nodeagent` to use `--enable-network-policy=true`;
- the enforcing mode not to be `strict`;
- the `PolicyEndpoint` CRD to exist; and
- the controller to create a namespaced `PolicyEndpoint` for the test policy.

The temporary namespace is deleted when the script exits. Checkpoint 1 does not
create or change policies in `startup-apps` or `data-platform`.

## Checkpoint 2 design

Checkpoint 2 restricts the `startup-apps` namespace with four policies:

1. default-deny ingress and egress for every Pod;
2. DNS egress to the CoreDNS Pods on TCP/UDP 53;
3. ALB ingress to demo-api on TCP/8080; and
4. demo-api egress to the `postgresql-baseline` Pods on TCP/5432.

ALB ingress is limited to the ELB-tagged public subnet CIDRs:

```text
10.20.0.0/24
10.20.1.0/24
```

The whole VPC CIDR is intentionally not allowed. With Amazon VPC CNI, ordinary
Pod addresses are also allocated from the VPC. Allowing the complete VPC would
make an unauthorized Pod indistinguishable from the load balancer at the
NetworkPolicy layer.

The AWS runtime check resolves the live demo-api ALB by its DNS name, reads the
subnets that ALB actually uses, verifies they are tagged
`kubernetes.io/role/elb=1`, and compares their CIDRs with the policy. A
Terraform or ALB subnet change therefore fails validation until the GitOps
policy is updated deliberately.

PostgreSQL egress requires both:

- the `data-platform` namespace with `platform.startup.dev/tier=data`; and
- a Pod with `cnpg.io/cluster=postgresql-baseline`.

The policy does not select the whole `data-platform` namespace as a
destination. The database namespace itself remains unrestricted in this
checkpoint; data-platform default-deny is deferred to checkpoint 3 because
CloudNativePG replication, operator management, Barman Cloud, and S3 backup
dependencies require a separate traffic map.

The aws-dev runtime matrix verifies:

- the NetworkPolicy Application reaches the current Git revision;
- AWS ELB subnet CIDRs and policy `ipBlock` entries match;
- the ALB `/health` endpoint remains reachable;
- every demo-api Pod can resolve and reach PostgreSQL;
- an unrelated namespace cannot reach demo-api; and
- demo-api cannot reach an unrelated test Service.

The negative-test namespace is deleted automatically when the script exits.
Local ingress-nginx and Prometheus traffic are outside this AWS-specific
checkpoint and remain unchanged.

## Checkpoint 3 design

Checkpoint 3 applies default-deny ingress and egress to `data-platform`, then
restores only the CloudNativePG traffic required by the current aws-dev
architecture:

1. DNS egress to CoreDNS on TCP/UDP 53;
2. demo-api ingress to the `postgresql-baseline` instances on TCP/5432;
3. CNPG Operator ingress to all CNPG instances on TCP/5432 and TCP/8000;
4. CNPG instance traffic within `data-platform` on TCP/5432 and TCP/8000;
5. baseline `join` Job egress to the Kubernetes API and PostgreSQL bootstrap
   paths, plus matching ingress to baseline instances;
6. CNPG instance egress to operator-managed PostgreSQL rw Services through the
   declared EKS Service CIDR on TCP/5432;
7. private Kubernetes API subnet ingress to instance status on TCP/8000;
8. instance egress to the Barman Cloud Plugin on TCP/9090;
9. instance egress to the Kubernetes API on TCP/443;
10. instance egress to public S3 and STS endpoints on TCP/443; and
11. `full-recovery` Job egress to the Kubernetes API and public S3/STS
    endpoints on TCP/443.

Every running database instance, including instances created by temporary
recovery Clusters, is selected through `cnpg.io/podRole=instance`. CloudNativePG
bootstraps ordinary replicas with a `cnpg.io/jobRole=join` Job and object-store
recovery with a separate `cnpg.io/jobRole=full-recovery` Job. Both lifecycle
roles receive dedicated, non-overlapping policies;
the application ingress rule still requires
`cnpg.io/cluster=postgresql-baseline`, so demo-api cannot connect to a temporary
recovery or PITR Cluster.

The first aws-dev runtime attempt proved that the Amazon VPC CNI evaluated
same-namespace replica traffic before Service destination NAT:

```text
primary Pod IP:5432                  allowed
postgresql-baseline-rw ClusterIP:5432 denied
```

The Pod-selector rule was therefore necessary but insufficient. The original
checkpoint listed the live `postgresql-baseline-rw` Service ClusterIP as an
explicit `/32` egress destination. Primary failover preserved that address
inside the original cluster.

The same pre-DNAT behavior applied to supporting Services. The original
kube-dns and Barman rules therefore included both Pod selectors and live
Service ClusterIPs as `/32` entries. Kubernetes API egress included both the
Service ClusterIP and private endpoint addresses.

The later v0.8.3 disposable-cluster rebuild proved that the PostgreSQL and
Barman `/32` values were not portable across EKS destruction and recreation.
It also exposed that regular replica bootstrap uses
`cnpg.io/jobRole=join`, which is not selected by instance policies. The
rebuild-safe correction declares the EKS Service CIDR in Terraform, uses it
only on the required Service ports, replaces transient API endpoint `/32`
entries with the declared private control-plane subnet CIDRs, and adds
dedicated baseline join policies. See
`docs/archive/V0.8.3_NETWORK_POLICY_REBUILD_FIX.md`.

The first full lifecycle run under enforcement proved that the regular
instance selector does not cover the bootstrap Job. The
`postgresql-recovery-latest-1-full-recovery` Job repeatedly started and then
failed until `BackoffLimitExceeded`, while scheduling and EBS attachment
eventually succeeded. The dedicated recovery policy now selects only
`cnpg.io/jobRole=full-recovery`. DNS is inherited from the namespace-wide DNS
rule. The Job can reach the live Kubernetes API addresses and public AWS HTTPS
endpoints, but it receives no PostgreSQL port, Barman Service, or general
internal-network access. The injected Barman recovery sidecar runs in the same
Pod network namespace and reads S3 directly with the shared IRSA service
account.

The EKS API server has both public and private endpoint access enabled.
In-cluster traffic uses the private Kubernetes API endpoint. The policy lists
the stable `default/kubernetes` Service address for pre-DNAT enforcement and
the two declared private control-plane subnet CIDRs for post-DNAT enforcement.
The runtime validation confirms that live EndpointSlice addresses remain
inside those subnets, so an EKS rebuild does not require new endpoint `/32`
values in Git.

The VPC currently has no S3 gateway endpoint or STS interface endpoint. Standard
Kubernetes NetworkPolicy operates at L3/L4 and cannot select AWS services by
DNS name. The public-AWS rule therefore allows TCP/443 to public addresses while
excluding RFC1918, carrier-grade NAT, and link-local ranges. Kubernetes API and
Barman traffic are restored separately, preventing this rule from becoming an
internal HTTPS bypass. IRSA and the S3 bucket policy continue to enforce AWS
authorization. This is still broader than an AWS-service-only rule: adding an
S3 gateway endpoint and an STS interface endpoint is the future hardening path
for keeping both services on explicit VPC routes.

The non-destructive aws-dev runtime matrix verifies:

- the NetworkPolicy Application reaches the current Git revision;
- the private Kubernetes API endpoint is enabled;
- the EKS Service CIDR and private control-plane subnets match the declared
  policy ranges;
- live kube-dns, Barman, and baseline PostgreSQL rw Service addresses remain
  inside the declared Service CIDR;
- the dedicated baseline join selector and ingress contract remain minimal;
- no temporary recovery policy can mask the permanent GitOps rules;
- the no-VPC-endpoint assumption remains true;
- the Operator, Barman Plugin, source Cluster, and all three instances remain
  healthy;
- both replicas return to streaming state within a bounded retry window;
- a replica can reach the baseline rw Service ClusterIP on TCP/5432;
- demo-api retains database access;
- CNPG instances reach DNS, Barman, Kubernetes API, STS, and S3;
- a fresh WAL record is emitted, its segment is switched, and that segment
  reaches S3 after isolation;
- an unrelated namespace cannot connect to PostgreSQL; and
- a PostgreSQL instance cannot connect to an unrelated test Service.

The negative-test namespace is deleted automatically. The runtime script does
not perform a primary failover or create recovery Clusters.

The recovery drill now polls both the Cluster condition and generated Job
status. A failed Job or unrecoverable Cluster triggers immediate output of
resource labels, Job and Cluster descriptions, all recovery-Pod container
logs, and recent events before automatic cleanup. This avoids waiting the full
recovery timeout and preserves the evidence that was previously deleted with
the temporary Cluster.
