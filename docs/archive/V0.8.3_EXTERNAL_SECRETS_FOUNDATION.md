# v0.8.3 External Secrets Foundation

## Status

Checkpoint 1 implementation complete; AWS runtime validation pending.

This checkpoint establishes only the AWS-side secret container and workload
identity. External Secrets Operator installation, SecretStore and
ExternalSecret resources, credential migration, and application cutover remain
outside this increment.

## Goal

Create the minimum AWS foundation required for External Secrets Operator to
reconcile one demo-api database Secret without static AWS credentials or broad
Secrets Manager access.

## Design

Terraform creates:

1. `startup-devops-baseline-dev/demo-api/postgresql`, an empty Secrets Manager
   Secret container;
2. an IRSA role trusted only by
   `system:serviceaccount:external-secrets:external-secrets`; and
3. a managed IAM policy scoped to the exact Secret ARN with only
   `secretsmanager:DescribeSecret` and
   `secretsmanager:GetSecretValue`.

The trust policy requires both the EKS OIDC audience
`sts.amazonaws.com` and the exact Kubernetes ServiceAccount subject. Namespace
or ServiceAccount wildcards are not used.

The read policy does not grant:

- `ListSecrets` or `BatchGetSecretValue`;
- Secrets Manager create, update, delete, tag, rotation, or push operations;
- wildcard Secret resources; or
- direct KMS permissions.

The Secret uses the AWS managed Secrets Manager encryption key. A later
production environment may introduce a customer-managed KMS key and a
correspondingly scoped `kms:Decrypt` permission as a separate security change.

## Secret-value boundary

The Terraform module intentionally omits
`aws_secretsmanager_secret_version`, `secret_string`, and `secret_binary`.
Secret values never enter Git or Terraform state.

Checkpoint 3 will migrate the existing CloudNativePG `fqdn-uri` value with a
non-echoing AWS CLI workflow. That workflow must avoid command tracing and
must validate only metadata, field presence, or hashes rather than displaying
the database URI.

## Development lifecycle

The disposable aws-dev environment defaults the Secrets Manager recovery
window to `0` so a complete Terraform destroy does not reserve the generated
name and block a clean rebuild. Persistent environments must use a recovery
window from 7 through 30 days and should manage Secret retention independently
from EKS teardown.

## Static validation

Run:

```bash
git diff --check

./scripts/validate-external-secrets-foundation.sh

./scripts/validate-terraform.sh

./scripts/validate-ci-quality-gates.sh
```

The External Secrets contract validator proves that:

- Terraform creates a container but no secret version;
- the IRSA trust is scoped through exact OIDC audience and subject claims;
- the IAM action set is exactly `DescribeSecret` and `GetSecretValue`;
- the IAM resource is the single Terraform-managed Secret ARN;
- all published Terraform outputs are non-secret identifiers; and
- the aws-dev recovery-window setting is explicit.

## AWS runtime validation

Review the plan carefully. It should add one Secret container, one IAM role,
one IAM policy, and one role-policy attachment, with no replacement of existing
EKS, CNPG, Karpenter, VPC, or FIS resources:

```bash
terraform -chdir=infra/terraform/aws/environments/dev plan

terraform -chdir=infra/terraform/aws/environments/dev apply
```

Then run:

```bash
./scripts/validate-external-secrets-foundation-aws.sh
```

The runtime validator reads only Secret metadata, IAM trust and permission
documents, and the five non-sensitive Terraform outputs. It never calls
`secretsmanager:GetSecretValue` and never prints secret material.

The final line must be:

```text
External Secrets AWS foundation runtime validation passed.
```

Checkpoint 2 must not begin until the AWS runtime validation passes.
