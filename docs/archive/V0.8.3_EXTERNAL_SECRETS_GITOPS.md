# v0.8.3 External Secrets GitOps Installation

## Status

Checkpoint 2 validated.

Checkpoint 1 is validated. The Secrets Manager container and exact-secret IRSA
read policy already exist, but the container intentionally has no secret
version yet.

## Goal

Install External Secrets Operator through Argo CD and validate the Kubernetes
and AWS identity path without activating the demo-api credential cutover.

The checkpoint ends with:

1. a pinned and healthy ESO installation;
2. a namespaced `startup-apps/aws-secrets-manager` SecretStore in `Ready=True`;
3. the existing `startup-apps/demo-api-postgresql` Secret still maintained by
   the current manual synchronization workflow; and
4. no active ExternalSecret competing for that Kubernetes Secret.

## Operator design

`clusters/aws-dev/platform/external-secrets.yaml` installs official Helm chart
`2.8.0` into the `external-secrets` namespace. The release is pinned rather
than following a floating chart version.

The main controller ServiceAccount is created by
`scripts/deploy-aws-dev-root-app.sh` and annotated with the non-sensitive
Terraform output `external_secrets_role_arn`. The Helm chart is configured with
`serviceAccount.create=false`, so Helm cannot overwrite the environment-specific
annotation and the IAM role ARN does not need to be committed to Git.

The namespace is labeled for the Kubernetes restricted Pod Security Standard.
The main controller, webhook, and certificate controller run only on the stable
Managed Node Group nodes labeled `workload=system` and have explicit resource
requests and limits.

## Kubernetes least privilege

The Helm release uses:

```yaml
scopedRBAC: true
scopedNamespace: startup-apps
processClusterExternalSecret: false
processClusterPushSecret: false
processClusterStore: false
processClusterGenerator: false
processPushSecret: false
rbac:
  serviceAccountTokenCreate: false
  servicebindings:
    create: false
  aggregateToView: false
  aggregateToEdit: false
  aggregateToAdmin: false
```

This limits the controller's Secret reconciliation to `startup-apps`, disables
unused cluster-scoped and push controllers and CRDs, removes the default
permission to mint tokens for arbitrary ServiceAccounts, and avoids adding ESO
permissions to the built-in view/edit/admin roles. The AWS provider uses the
controller Pod's IRSA identity, so no `auth.jwt.serviceAccountRef` token minting
and no static AWS access-key Secret are required.

## SecretStore design

The child Argo CD Application
`external-secrets-startup-apps` manages only:

```text
clusters/aws-dev/security/external-secrets/startup-apps/
```

It creates a namespaced `SecretStore` using `external-secrets.io/v1` and the
AWS Secrets Manager provider in `us-east-1`. It does not use a
`ClusterSecretStore`, static access key, cross-namespace reference, or wildcard
remote-secret lookup.

The store inherits the ESO controller Pod identity. AWS IAM independently
restricts that identity to the single Terraform-managed Secret ARN and only
`DescribeSecret` plus `GetSecretValue`.

## Staged ExternalSecret boundary

During Checkpoint 2, the staged ExternalSecret was not applied by Argo CD.

Its manifest is committed under:

```text
clusters/aws-dev/security/external-secrets/staged/demo-api-postgresql.yaml
```

The live child Application points only to the sibling `startup-apps/`
directory. Activating the object while the Secrets Manager container has no
version would create a permanent `SecretSyncedError` and would introduce a
second controller for the existing Kubernetes Secret without providing a
working source value.

Checkpoint 3 will first migrate the CloudNativePG `fqdn-uri` into the
`DATABASE_URL` JSON property without printing it. It will then move the staged
manifest into the synchronized directory, wait for ESO readiness, compare
non-reversible hashes, and finally retire the manual synchronization path.
The staged target uses `creationPolicy: CreateOrMerge` with
`deletionPolicy: Retain`, allowing ESO to update the already-existing Secret
without deleting it or introducing a temporary missing-Secret window.

inactive staged ExternalSecret, runtime matrix, and checkpoint status.

## Deployment

Commit and push the checkpoint before deploying so the root Application can
read every child Application and SecretStore from the selected Git revision.
Then run:

```bash
TARGET_REVISION=feature/v0.8-production-security-baseline \
  ./scripts/deploy-aws-dev-root-app.sh
```

The deployment script:

1. reads `external_secrets_role_arn` from Terraform output;
2. creates and labels the `external-secrets` namespace;
3. creates and annotates the controller ServiceAccount;
4. applies the root Application;
5. waits for both External Secrets child Applications; and
6. waits for `SecretStore/aws-secrets-manager` to become ready.

## EKS runtime validation

Run:

```bash
./scripts/validate-external-secrets-gitops-aws.sh
```

The runtime matrix verifies:

- both Argo CD Applications are synced;
- the operator Application is healthy and pinned to `2.8.0`;
- the ServiceAccount annotation matches the Terraform role ARN;
- the controller Pod received IRSA web-identity environment variables;
- the controller, webhook, and certificate-controller Deployments are ready;
- the v1 ExternalSecret and SecretStore CRDs exist;
- the controller can reconcile Secrets in `startup-apps` but not
  `data-platform`;
- the controller cannot create ServiceAccount tokens;
- the namespaced SecretStore is `Ready=True`; and
- the old target Secret exists while no ExternalSecret is active.

The final line must be:

```text
External Secrets GitOps runtime validation passed.
```

Checkpoint 3 may now activate the staged ExternalSecret after the initial
Secrets Manager value is migrated from CloudNativePG.
