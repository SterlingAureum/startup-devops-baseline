# v0.8.4 External Secrets Credential Migration and Cutover

## Status

Checkpoint 3 implementation complete; EKS runtime validation pending.

Checkpoints 1 and 2 are validated. AWS Secrets Manager, exact-secret IRSA,
External Secrets Operator `2.8.0`, and the namespaced
`startup-apps/aws-secrets-manager` SecretStore are already healthy.

## Goal

Replace the default cross-namespace Kubernetes Secret copy with an external
secret supply chain while preserving the demo-api contract:

```text
CloudNativePG postgresql-baseline-app/fqdn-uri
                ↓ guarded one-time seed
AWS Secrets Manager JSON property DATABASE_URL
                ↓ ESO controller IRSA
startup-apps/demo-api-postgresql/DATABASE_URL
                ↓ secretKeyRef
demo-api
```

No plaintext credential enters Git, logs, command arguments, or Terraform state.

## Migration safety

`scripts/migrate-demo-api-postgresql-secret.sh` requires the explicit
confirmation value `seed-from-cnpg`. It reads the CloudNativePG URI without
printing it, first selects the configured EKS cluster, loads the JSON document
through protected standard input, and creates the first `AWSCURRENT` version.

The script is idempotent:

- when no `AWSCURRENT` version exists, it creates and reads back the first
  value;
- when `AWSCURRENT` already equals the CNPG credential, it succeeds without
  creating another version; and
- when the values differ, it refuses to overwrite the remote value because
  credential rotation belongs to v0.8.5.

Terraform continues to manage only the Secret container. It does not manage an
`aws_secretsmanager_secret_version`, so the value is absent from Terraform
configuration and state.

## ExternalSecret activation

The manifest now lives at:

```text
clusters/aws-dev/security/external-secrets/startup-apps/demo-api-postgresql.yaml
```

The same Argo CD child Application already manages this directory. The object
uses a namespaced `SecretStore`, requests only the `DATABASE_URL` property from
the exact remote Secret, and targets the existing Kubernetes Secret with:

```yaml
creationPolicy: CreateOrMerge
deletionPolicy: Retain
```

`CreateOrMerge` updates the existing manually created Secret during initial
handoff without deleting it or adding an ExternalSecret owner reference.
The missing owner reference preserves the target if the ExternalSecret is
removed, while `Retain` preserves it if the provider value is unavailable.

The remote value must be migrated before the commit containing the active
ExternalSecret is pushed. This avoids a `SecretSyncedError` interval in the
existing environment.

## Normal deployment and clean rebuild

`scripts/deploy-aws-dev-root-app.sh` no longer calls the legacy Kubernetes
Secret copy. After CloudNativePG creates `postgresql-baseline-app`, it invokes
the guarded idempotent AWS migration and waits for the ExternalSecret and target
Secret before validating demo-api.

This also supports a clean environment: the first reconciliation may wait while
CloudNativePG creates its application identity, but the deployment script seeds
AWS and forces ESO synchronization before the application validation completes.

## Legacy rollback boundary

`scripts/sync-demo-api-postgresql-secret.sh` remains only as a break-glass
fallback. It requires:

```text
CONFIRM_LEGACY_SECRET_SYNC=external-secret-suspended
```

and refuses to run while `ExternalSecret/demo-api-postgresql` exists. This
prevents ESO and the legacy script from becoming simultaneous writers.

## Static validation

Run before the migration:

```bash
git diff --check

./scripts/validate-external-secrets-foundation.sh
./scripts/validate-external-secrets-gitops.sh
./scripts/validate-external-secrets-migration.sh
./scripts/validate-ci-quality-gates.sh
```

The migration contract checks the active v1 ExternalSecret, namespaced store,
single JSON property, `CreateOrMerge + Retain`, guarded non-overwriting seed,
retired default copy path, break-glass protection, `.gitignore` exceptions,
runtime rebuild matrix, and checkpoint status.

## Ordered cutover

Seed AWS before committing or pushing the active ExternalSecret:

```bash
CONFIRM_EXTERNAL_SECRETS_MIGRATION=seed-from-cnpg \
  ./scripts/migrate-demo-api-postgresql-secret.sh
```

Then commit, push, and reconcile the selected Git revision:

```bash
TARGET_REVISION=feature/v0.8-production-security-baseline \
  ./scripts/deploy-aws-dev-root-app.sh
```

## EKS runtime validation

Run the guarded validation:

```bash
CONFIRM_EXTERNAL_SECRET_REBUILD=delete-and-recreate \
  ./scripts/validate-external-secrets-migration-aws.sh
```

It verifies:

- Argo CD and the ExternalSecret are synced and ready;
- CNPG, `AWSCURRENT`, and the Kubernetes target are identical without printing
  their values;
- the target contains exactly `DATABASE_URL` and is labeled as ESO-managed;
- `CreateOrMerge` did not add an ExternalSecret owner reference;
- IAM simulation returns `implicitDeny` for an unrelated Secret ARN;
- deletion of only `startup-apps/demo-api-postgresql` is recovered by ESO with
  a new UID and the same protected value; and
- both demo-api replicas remain connected to the current PostgreSQL primary.

Existing demo-api Pods retain their already-loaded environment while the
Kubernetes Secret is briefly absent. The script forces ESO synchronization and
does not proceed until the target is recreated.

The final line must be:

```text
External Secrets migration runtime validation passed.
```

Do not mark v0.8.4 delivered or create its tag until this line is observed.
