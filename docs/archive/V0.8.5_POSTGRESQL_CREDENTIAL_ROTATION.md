# v0.8.5 PostgreSQL Credential Rotation

Status: Checkpoint 2 implementation delivered; AWS activation validation
pending.

## Checkpoint 1: Candidate Credential Staging

Checkpoint 1 creates a high-entropy replacement `DATABASE_URL` and stores it
only as an `AWSPENDING` version of the existing Terraform-managed AWS Secrets
Manager Secret.

It deliberately does not alter the PostgreSQL role, move `AWSCURRENT`, trigger
an ExternalSecret refresh, change the Kubernetes Secret, or restart demo-api
Pods. Keeping those actions out of this checkpoint prevents an unsafe partial
cutover: demo-api receives `DATABASE_URL` through an environment variable and
cannot observe a changed Kubernetes Secret until its Pods are rebuilt.

The activation sequence belongs to Checkpoint 2 and must remain one guarded
operational transaction:

1. validate the staged candidate and current application health;
2. change the PostgreSQL `app` role password through protected standard input;
3. move Secrets Manager stages so the candidate becomes `AWSCURRENT`;
4. force and verify External Secrets reconciliation without persistent GitOps
   annotations;
5. replace one demo-api Pod at a time and verify database health after each;
6. compensate back to the previous password and Secret version if cutover
   cannot complete.

Checkpoint 2 implements this sequence as one guarded command. The aws-dev
release uses `Deployment/demo-api` with two replicas (`rollout.enabled: false`),
so the reload helper deletes one original Pod, waits for its replacement to
load the expected credential digest and pass `/db/health`, and only then moves
to the next original Pod. After the database password changes, original Pods
may remain `Running` while becoming `NotReady` because they still hold the old
environment variable. The activation workflow therefore invokes the helper in
an explicit `credential-transition` mode that permits this expected source
state but still requires every new Pod to become Ready and database healthy.
The same mode lets compensation recover a partially replaced, mixed-credential
Pod set. It never changes the Deployment Pod template.

Because PostgreSQL maintains one password for this login role, changing that
password invalidates new connections from every old Pod immediately. This is a
bounded cutover, not a zero-downtime rotation claim. A future dual-role design
would be required to keep both old and new login credentials valid during the
transition.

## Safety Contract

- Never enable shell xtrace while running credential operations.
- Plaintext credentials travel only through process memory and protected
  standard-input pipes.
- Secret values are not printed, committed to Git, or written to Terraform
  state.
- Staging refuses to replace an existing `AWSPENDING` version.
- The URI scheme, username, host, port, database path, query, and fragment are
  preserved; only the password changes.
- The generated password uses at least 48 URL-safe random bytes.
- `AWSCURRENT` and `AWSPENDING` must remain distinct versions.
- The active ExternalSecret remains explicitly pinned to `AWSCURRENT`.
- Discard removes only the `AWSPENDING` label and never deletes the Secret
  container or moves `AWSCURRENT`.
- Activation refuses to start unless both Argo CD Applications are
  `Synced / Healthy`, the ExternalSecret is Ready, the target Secret matches
  `AWSCURRENT`, and every demo-api replica is Ready and Available.
- The workload helper defaults to strict healthy-source validation. Only the
  guarded activation and compensation paths select `credential-transition`,
  after the database mutation has made old or mixed-credential Pods
  legitimately NotReady.
- The PostgreSQL password is changed before any Secrets Manager stage moves,
  then tested using a new candidate-authenticated connection.
- Moving `AWSCURRENT` retains the original version as `AWSPREVIOUS`; the
  temporary `AWSPENDING` stage is removed only after promotion.
- The temporary `force-sync` annotation is removed after ESO convergence so
  the GitOps Application can return to `Synced / Healthy`.
- Every replacement Pod must load the expected `DATABASE_URL` SHA-256 digest
  and connect to the current primary before the next Pod is removed. Any
  previously verified replacement must remain Ready throughout the remaining
  transition.
- A partial cutover automatically attempts to restore the old PostgreSQL
  password, version stages, ESO target Secret, and workload Pods. It keeps the
  candidate under `AWSPENDING` for investigation or retry.
- After the first external rotation, the CloudNativePG-generated application
  Secret is a legacy bootstrap credential. AWS Secrets Manager `AWSCURRENT`
  and the ESO target Secret become the active source-of-truth chain.

## Stage a Candidate

This changes Secrets Manager by adding one isolated candidate version. It does
not require an Argo CD deployment because no GitOps manifest changes in this
checkpoint.

```bash
CONFIRM_POSTGRESQL_CREDENTIAL_STAGE=stage-awspending \
  ./scripts/stage-demo-api-postgresql-credential.sh
```

Expected final output:

```text
PostgreSQL credential candidate staging passed.
AWSPENDING version: <version-id>
AWSCURRENT, PostgreSQL, ExternalSecret, Kubernetes Secret, and demo-api were not changed.
```

## Validate the Staged State

The AWS validator is read-only. It compares SHA-256 digests and URI structure
without printing either credential.

```bash
./scripts/validate-postgresql-credential-rotation-aws.sh
```

Expected final output:

```text
PostgreSQL credential rotation Checkpoint 1 AWS validation passed.
AWSPENDING is isolated; AWSCURRENT and the live Kubernetes credential remain unchanged.
```

Leave the valid candidate staged when proceeding directly to Checkpoint 2.

## Activate the Candidate

Run this only after the Checkpoint 1 AWS validator passes. The command performs
the database mutation, stage promotion, ESO synchronization, and workload
reload as one guarded workflow:

```bash
CONFIRM_POSTGRESQL_CREDENTIAL_ACTIVATION=activate-awspending \
  ./scripts/activate-demo-api-postgresql-credential.sh
```

Expected final output:

```text
PostgreSQL credential activation and workload reload passed.
The candidate is AWSCURRENT; the original version is retained as AWSPREVIOUS.
No AWSPENDING stage or temporary force-sync annotation remains.
```

Do not separately invoke the reload helper during normal activation. It is an
internal guarded primitive shared by activation and automatic compensation.

If activation exits unsuccessfully, read its compensation result before doing
anything else:

- `Automatic compensation passed` means the original password and
  `AWSCURRENT` are active again, all Pods were reloaded back, and the candidate
  remains `AWSPENDING`.
- `AUTOMATIC COMPENSATION DID NOT COMPLETE` is a hard stop. Inspect PostgreSQL
  authentication, Secrets Manager labels, the ExternalSecret and all demo-api
  Pods before retrying or making another change.

## Validate the Activated State

After successful activation, run the read-only validator:

```bash
./scripts/validate-postgresql-credential-activation-aws.sh
```

It proves that:

- `AWSCURRENT` and `AWSPREVIOUS` are distinct and no `AWSPENDING` remains;
- only `AWSCURRENT` can open a new PostgreSQL connection;
- the ESO target and every demo-api process contain the `AWSCURRENT` digest;
- the legacy CNPG bootstrap credential is no longer the active credential;
- both GitOps Applications are `Synced / Healthy`;
- both demo-api replicas pass the existing primary-connectivity validator.

Expected final output:

```text
PostgreSQL credential rotation Checkpoint 2 AWS validation passed.
AWSCURRENT authenticates, AWSPREVIOUS is retained but inactive, ESO is converged, and every demo-api Pod loaded the new credential.
```

## Discard the Candidate

Use this only when abandoning or regenerating the candidate:

```bash
CONFIRM_POSTGRESQL_CREDENTIAL_DISCARD=discard-awspending \
  ./scripts/discard-demo-api-postgresql-credential.sh
```

AWS Secrets Manager retains the resulting unlabeled version for its normal
cleanup lifecycle. The active credential remains unchanged.

## Checkpoint Boundary

Checkpoint 1 proves candidate generation, secure transport, version-stage
isolation, and a reversible no-impact staging path. Checkpoint 2 implements and
validates the guarded cutover plus workload reload. It intentionally retains
`AWSPREVIOUS`; a separately guarded, real rollback exercise belongs to
Checkpoint 3 and must not be performed until Checkpoint 2 validation passes.
