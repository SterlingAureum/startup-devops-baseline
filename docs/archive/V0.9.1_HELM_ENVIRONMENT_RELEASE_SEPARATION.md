# v0.9.1 Helm Environment and Release Separation

Status: Static implementation complete; local CI and live aws-dev confirmation
remain acceptance steps.

## Goal

Separate stable environment configuration from the immutable application
identity that crosses promotion boundaries. This prevents a release PR from
copying or changing a target environment's hostname, resource sizing, Secret
reference, database configuration, ingress behavior, or application mode.

## Delivered Structure

```text
apps/demo-api/helm/values/
├── environments/
│   ├── aws-dev.yaml
│   ├── aws-test.yaml
│   └── aws-prod.yaml
└── releases/
    ├── aws-dev.yaml
    ├── aws-test.yaml
    └── aws-prod.yaml
```

For every AWS render, Helm loads the environment file first and the release
file second. Environment files contain runtime settings and image pull policy.
Release files contain only:

```text
image.repository
image.tag
image.digest
release.applicationVersion
delivery.sourceRepository
delivery.sourceCommit
delivery.workflowRunId
```

The aws-test and aws-prod release files are seed identities for static
rendering. They do not constitute evidence-backed runtime promotions.

## Compatibility and Safety

The active aws-dev values were split without changing replicas, ALB/TLS
annotations, hostname, resources, probes, application mode, database Secret,
image identity, or delivery metadata. The old mixed values file was removed to
avoid two competing sources of truth.

The existing image workflow and rollback workflow remain aws-dev-only in this
increment. Both now modify only the aws-dev release file and render it together
with the unchanged aws-dev environment file. Ordered dev-to-test-to-prod
promotion is deliberately deferred to v0.9.3.

## Static Acceptance

Run:

```bash
./scripts/validate-demo-api-values-separation.sh
./scripts/validate-ci-quality-gates.sh
```

The quality gate must lint and render local, aws-dev, aws-test, and aws-prod;
validate digest identity and release metadata; prove promotion and rollback
diff isolation; run unit tests; and validate the hardened runtime image.

## Optional Live aws-dev Confirmation

After merging the v0.9.1 desired state into the branch tracked by Argo CD,
wait for the Application and confirm its ordered value files:

```bash
kubectl -n argocd wait \
  --for=jsonpath='{.status.sync.status}'=Synced \
  application/demo-api-aws-dev \
  --timeout=10m

kubectl -n argocd get application demo-api-aws-dev \
  -o jsonpath='{.spec.source.helm.valueFiles}'
```

Confirm that `demo-api-aws-dev` is `Synced` and `Healthy`, loads both ordered
values files, retains the same image digest and `/version`, and continues to
serve the established HTTPS and PostgreSQL paths. The existing v0.8 final
validator may be rerun for the HTTPS, PostgreSQL, Secret, and security baseline.

`validate-demo-api-delivery-trace.sh` remains intentionally restricted to a
release-only promotion or rollback commit, so do not pass the multi-file
v0.9.1 migration commit to it. Rerun that trace after the next aws-dev release
PR. No aws-test or aws-prod resource should exist as a result of this increment.
